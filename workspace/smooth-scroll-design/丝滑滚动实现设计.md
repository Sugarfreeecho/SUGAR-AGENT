## 0. 一句话概括

丝滑滚动不是"一个滚动函数"，而是三层正交机制叠在原有"贴底滚动"之上：

| 层 | 解决的问题 | 手段 |
|---|---|---|
| ① 文本揭示节奏器 | token 块成批到达 → 文字"一坨弹出" | 按积压量做逐帧比例释放（`computeSmoothRevealCount`） |
| ② 滚动跟随控制器 | `scrollTop` 一次性跳变 → 内容瞬移/抖动 | 单 rAF 循环 + 保留速度的阻尼跟随（`smoothFollowController`） |
| ③ 轨迹行高度动画 | 整行插入/折叠引起布局突变 | WAAPI 高度动画（`animateSmoothTraceRowHeight`） |

折行与整行高度变化共用一套跟随运动；文本揭示节奏与滚动速度不再耦合。所有权和手势语义仍以读者意图优先。

---

## 0.1 先回答一个常见困惑："换行"属于哪一层？

"换行"（文本自动折行）本身不是一个独立的层，它被拆成三件不同的事，各归各的：

| 问题 | 归属 | 说明 |
|---|---|---|
| 在哪一个字断开、折到下一行？ | **纯 CSS 排版**（不在本设计的 JS 里） | 轨迹文本用 `white-space: pre-wrap; word-break: break-word`（`app.css` 2297–2303），断行位置由浏览器排版引擎算；流式期间 `.feed-chunk.is-streaming` 取消高度上限（`max-height: none; overflow: visible`），所以折行会真实撑高容器 |
| 什么时候发生一次折行？ | **① 文本揭示层** | 它逐帧把字符写进 DOM，写到行尾浏览器就折行；折行的"节奏"由揭示节奏决定 |
| 折行把内容顶高后，视口怎么跟？ | **② 跟随控制器** | 底部目标变化后从当前速度继续滑行，最多写入 20px/帧 |
| 整行插入/折叠造成的高度变化？ | **③ 行高动画**（动画本身）+ **② 跟随控制器** | WAAPI 改变高度；跟随器仍使用同一套阻尼运动 |

一句话：**折行由浏览器排版，揭示器决定折行何时发生，跟随器决定视口如何移动。** 行高动画只负责整行元素的高度；两种高度变化由同一个跟随器处理。

`smooth-stream.js` 文件头明确统一规则：
```js
// Text wrapping and whole-row layout changes use the same finite glide.
```

**术语小抄**（把后文难懂的词翻译一下）
- "底部目标" = `max(0, scrollHeight - clientHeight)`；高度变化时跟随器重新定向。
- "阻尼跟随" = 保存位置和速度，目标变化时自然加速或减速；固定软弹簧（刚度 180）让每段收尾自然放缓（约数百毫秒）。

## 1. 设计目标与硬约束

**目标**（对应 UseCase 清单 UC-503 / UC-504）
- 模型流式输出"文字平滑滚动，非一坨弹出"；渲染与状态解耦，切会话不崩。
- 长会话滚动锚点稳定（回看不跳），TOC/Todo 面板定位准确。

**硬约束**（被测试固化的契约，见 §12）
1. 关闭开关后必须完整回落到 legacy 行为，不允许功能缺失。
2. 历史加载的原生平滑动画与实时跟随**互斥**：同一时刻只能有一个 `scrollTop` 写入者。
3. 流结束不留缓动尾巴；final 卡片必须走"确定性贴底"，不允许与缓动竞争。
4. 统一跟随参数：固定刚度 180（临界阻尼，ω=√180≈13.42/s）、单帧上限 20px；折行与整行使用同一规则。
5. 遵守 SPEC 17.2：流式文本批量 flush，避免每个 token 触发布局。

## 3. 常量与运动模型

```js
SMOOTH_STREAM_CONFIG = {
  revealDivisor: 8,          // 揭示比例基准（积压的 1/8）
  referenceFrameMs: 16.67,   // 参考帧长
  followTargetEpsilonPx: 0.25, // 目标变化/到位阈值
  followStiffness: 180,        // 固定刚度（DeepSeek 同款软弹簧；ω=√180≈13.42/s）
  maxFollowStepPx: 20,         // 单帧跟随写入上限
  unpinWheelPx: 8,           // 读者离开手势阈值
  gestureWindowMs: 800,      // 离散手势的累计窗口
}
```

折行和整行都以各自 port 的底部为目标。跟随器保存浮点位置与当前速度；目标变动时延续速度，避免重启动画造成突兀。阻尼响应为常数（ω=√stiffness），不随落后距离增强——这是 DeepSeek 同款的"软"：慢启动、长收尾；20px/帧上限只在大位移时防爆冲。没有 text/row 参数差异或固定速度地板。

## 4. 文本揭示层（节奏器）

### 4.1 释放量公式

```js
computeSmoothRevealCount(backlog, dtMs) =
  min(backlog, max(1, ceil((backlog / 8) * (dtMs / 16.67))))
```
- 每帧至少揭示 1 个 code point（保证"总会动"）；
- 积压越多释放越快（按 1/8 比例的自适应速率），积压清空后自然结束；
- `dtMs` 归一化到参考帧，慢帧自动多释放，避免明显脱节。

### 4.2 Unicode 安全切分

`takeSmoothTextPrefix(text, charCount)` 按 **code point** 游标推进（`codePointAt`，代理对按 2 个 UTF-16 单元跳过），返回 `{segment, rest, count}`——emoji 不会被拦腰截断，测试用例 `'A😀中'` 取 2 得 `'A😀'`。

### 4.3 调度（session-scroll-history.js）

`scheduleLlmDeltaFlush(ctx, runSessionId)`：
- 单飞 rAF（`l.llmDeltaFlushRaf` 非空直接返回），一帧只做一次 flush；
- `dtMs = clamp(now - llmRevealLastTs, 1, 120)`（首帧用 16.67）；
- reasoning / response 两个 pending 缓冲**各自独立**消费，互不争抢；
- flush 后若仍有积压则继续排队，形成连续"逐帧推进"；
- 揭示节奏只决定内容何时写入；跟随器直接观察高度变化，不读取揭示速率。

### 4.4 写入策略（避免每帧重建 DOM）

`writeLlmStreamText(scroller, raw, part)`：
- `_llmRawText` 保留**未截断原文**，UI 走 `truncateLogTextForUi(trimSurroundingBlankLines(...))` 投影，两者分离；
- 若可判定为"纯尾部追加"（现有首子节点即文本节点、且完整包含旧串前缀）→ `node.appendData(...)`，计数 `text.nodeAppends`；
- 否则才整体替换 `textContent`，计数 `text.nodeReplacements`。
- 这对诊断很有用：`nodeReplacements` 升高说明追加假设被破坏（例如思考标签回流、截断触发），是排查"揭示卡顿"的第一指标。

## 5. 跟随控制器（核心：`createSmoothFollowController`）

### 5.1 结构与状态

- `states: WeakMap<port, state>` 与 `activePorts: Set` 管理视口；所有视口共用一个跟随 rAF。
- `animatedTop` 是浮点权威位置；浏览器回写的 `scrollTop` 不参与运动积分。
- `followVelocityPxPerSec` 保存当前速度；目标变化时继续使用，使速度连续。
- `lastFloor`、`lastFloorChangeMs` 记录目标及上次变化时间；`lastWrittenTop`、`ownedUntil` 保留写入所有权判断。
- `following`、`readerDetached` 和手势字段沿用原有语义，详见 §6。

### 5.2 每帧算法

1. 清理已断开的 port；计算 `floor = max(0, scrollHeight - clientHeight)`。每帧只读视口尺寸，不扫描 `.feed-item`。
2. 目标变化超过 0.25px 时记下变化时间，但保留当前位置和速度。行高连续变化也会连续运动。
3. 对 `lag=floor-animatedTop` 计算阻尼响应 `response=Math.sqrt(followStiffness)≈13.42`（每秒，常数）；用临界阻尼的封闭形式求该帧自然位移与末速度。单次折行由极小速度起步（19px 首帧约 0.41px），全程同一刚度、不随距离加速。
4. 实际位移取自然位移，再受 20px/帧上限约束；无到位期限——收尾完全由弹簧物理决定（19px 约 483ms、200px 约 684ms 收敛到 0.25px 阈值）。
5. 若期限或上限改变了自然位移，用**实际位移 / 帧长**更新速度；否则沿用阻尼模型的末速度。到位阈值为 0.25px，到位后速度归零，轻量 rAF 观察者保留至流或所有权结束。

临界阻尼在每帧内采用常数 `response` 的精确解，避免因刷新率或长帧使欧拉积分抖动。期限是按剩余距离动态计算的到位约束，没有固定的低速地板。底部因折叠缩小时，先服从浏览器的可滚动范围夹持并清零速度。

### 5.3 收尾与性能

- 常规单行高度变化约 483ms 收敛到阈值（软弹簧固有节奏）；大积压若受 20px/帧上限限制，允许更长时间追完。
- 不再根据 streaming 标记等待“高度稳定”，也不再一次性清除尾差。
- 删除旧的轨迹行全量扫描和 `follow.traceScans` 计数；外层 chat 与内层 process body 各读自己的 `scrollHeight/clientHeight`。
- `follow.frameGap`、`follow.work` 仍衡量跟随循环；文本揭示继续独立按积压释放。

### 5.4 验收边界

`node tests/js/smooth_stream_runtime.cjs --report` 的 Node fake DOM/rAF 模拟（16.67ms/帧）：

| 场景 | 到位时间 / 停顿 | 峰值滞后 | 最大单帧跟随位移 |
|---|---:|---:|---:|
| 单次折行 19px | 483.4ms；首帧 0.41px | — | 1.56px |
| 慢速两次折行 19px | 每次 483.4ms；随后各停 45 帧 | — | 1.56px |
| 每 33ms 折行 19px | 连续跟随 | 84.95px（4.47 行） | 9.51px |
| 行高连续 12 帧各增 10px | 停止增长后 550.1ms | 71.34px | 7.48px |
| 单次增高 200px | 683.5ms | — | 16.42px |

这些数值来自模拟 rAF 和滚动容器，不能代替真实浏览器的主观观感检查。

20px 上限约束**实时跟随器写入**。final 卡片、SSE 收口、历史定位与关闭特性后的 legacy 路径保留各自的立即贴底语义。若既有滞后超过单帧上限的追赶容量，会优先遵守单帧上限（允许更长的追赶时间）；浏览器在可滚动范围骤缩时也可能自行夹住 `scrollTop`。

## 6. 读者意图优先（unpin 与重接管）

### 6.1 四类"离开"手势（`bindPort`）

| 手势 | 判定 | 备注 |
|---|---|---|
| 滚轮 | 向上 `deltaY` 累计 ≥ 8px | `passive` 监听，不阻塞滚动 |
| 触摸 | 上拉位移累计 ≥ 8px | 与滚轮共用 `awayPx` 累计器 |
| 拖滚动条/按住 | `pointerdown` 后 `scrollTop` 比按下时上移 > 2px | 抓滚动条场景 |
| 键盘 | `ArrowUp` / `PageUp` / `Home` | |

离散手势通过 `gestureTimer`（800ms 窗口）聚合：窗口内多次小动作会累加，避免"抖动一下就被解绑"或"抖半天才解绑"两个极端。

### 6.2 unpin 的副作用

`unpin(port, state)`：置 `following=false`、`readerDetached=true`，移除所有权标记，调用 `state.onUnpin`。
上层传入的 `releaseMainFollow` 会**同时取消另一个容器**（chat ↔ process body）——保证"读者接管一个视口"不会让另一个视口继续自作主张。

### 6.3 重接管门禁

- `readerDetached` 期间 `request()` 一律被拒（除非显式 `force`）；
- 只有 `isSmoothStreamPortNearBottom()` 判定读者**真正贴底**（`isNearBottom(port, 2)`，2px 内）时才 `clearReaderDetached()`；
- 这样刻意规避了"宽阈值"（原逻辑 56/72/96px）与读者意图的冲突：宽阈值会让人误以为还能自动跟随。

### 6.4 三种"停止"的语义区分

| API | 语义 | 是否算读者手势 |
|---|---|---|
| `unpin`（内部） | 读者接管，进入 detach；需贴底才可恢复 | 是 |
| `cancel(port)` | 程序性停止（final 卡片、历史加载、测试用例） | 否——不置 `readerDetached` |
| `reset(port)` | 会话边界：cancel + 清空手势状态/回调 | 否 |

这个区分被测试断言保护（`cancel` 后 `unpin` 计数不得增加）。

## 7. 所有权标记与样式协同

```css
.chat-container { scroll-behavior: smooth; overflow-anchor: none; }
.chat-container[data-smooth-follow-owned],
.process-aggregate-body[data-smooth-follow-owned] {
    scroll-behavior: auto;      /* 关键：禁止浏览器原生平滑接管我们的逐帧写入 */
    overflow-anchor: none;      /* 关键：禁止 scroll anchoring 与跟随互抢 */
}
.feed-item[data-smooth-trace-layout-owned] {
    overflow: clip !important;
    will-change: height, opacity;
}
```

- 跟随期间给容器打 `data-smooth-follow-owned`，把浏览器的原生平滑与锚定全部让位给控制器；
- `ownedUntil = now + 100`：写后 100ms 窗口内、且 `scrollTop` 与 `lastWrittenTop` 相差 ≤2px 时，`isOwnedScroll()` 判定为"程序写入"。该接口已在控制器上暴露，当前仓库内尚未出现外部消费点（预留：供滚动事件处理区分程序/用户滚动）。
- 行高动画期间给行打 `data-smooth-trace-layout-owned`（详见 §8），用于 CSS 裁切与动画清理；跟随运动不依赖此标记。

## 8. 轨迹行高度动画层

### 8.1 三个入口

| 函数 | 场景 | 参数 |
|---|---|---|
| `animateSmoothTraceRowInsertion(row)` | 新行插入，从 0 长到目标高，附 0.45→1 透明度 | duration 190ms |
| `mutateSmoothTraceRowHeight(row, action)` | 折叠/展开等"前后测量"包装 | duration 230ms |
| `settleSmoothTraceHeightAnimations(root)` | 流结束/挂起前立即结算所有行 | 直接 cancel |

缓动统一 `cubic-bezier(0.22, 1, 0.36, 1)`（强出场缓动，快起慢收）。

### 8.2 与滚动控制器的耦合

- 动画期间行被标记 `[data-smooth-trace-layout-owned]`，用于 CSS 裁切和 `settleSmoothTraceHeightAnimations` 清理；
- 插入和折叠动画每帧改变 `scrollHeight`，跟随器观察 `floor` 并当帧重定向，无需额外通知或另一套运动参数。

### 8.3 明确排除（避免与基准/历史冲突）

写入点 `createProcessFeedRow()` 中：
```js
if (!isHistoryHydrate && !isInitialLiveStatusRow) animateSmoothTraceRowInsertion(row);
if (isInitialLiveStatusRow) finishStreamScrollIfFollow(ctx, runSessionId);
```
- **历史 hydrate 不播插入动画**（历史回放是一次性批量渲染）；
- **当前 body 的首条 live status 行不播插入动画**，而是直接触发一次"流结束收敛"——它是本次运行的"贴底基准行"，先浪费 190ms 动画会拖坏首次贴底体验。

## 9. 边界隔离：历史加载 / final / 会话切换 / SSE 收口

### 9.1 历史平滑滚动的会话级闩锁

- `historySmoothScrollSessionId`：记录"正在执行原生平滑到底"的会话；
- `isHistorySmoothScrollActive()` 是全局闩锁，**所有实时跟随路径**（`request`、`scrollContentAreaIfFollow`、`followStreamProcessScroll`、自动加载更早历史）在闩锁开启时直接 return；
- `beginHistorySmoothScroll()` 先 `cancelSmoothStreamFollowForHistoryLoad()`（清 chat + process body 两个跟随者），确保写入权唯一。

### 9.2 等待条件（`waitForChatScrollAfterHistoryLoad(sessionId, 'smooth-bottom')`）

- 监听 `scrollend` + rAF 兜底：底部且静止 ≥ 96ms → 成功；
- 未贴底且静止 ≥ 180ms → **最多重定目标 1 次**（`retargetCount < 1`），防止无限抖动；
- 硬超时 3.2s；
- 用户 `wheel` / `touchstart` / `pointerdown` → 立即结束（判失败）；
- 运行中会话 → 立即 `setScrollTopImmediate` 到底并成功结束（运行会话来不得慢动画）；
- 清理时校验 `scrollEpoch === switchSessionEpoch`，防止**旧会话的回调误清新会话闩锁**。

### 9.3 历史 hydrate 的时序契约（session-management.js）

```
prepareWorkspaceImageLayout → waitForHistoryImageLayout → finishHistoryHydration
→ bindExistingLogInteractions → applyChatScrollAfterHistoryLoad
→ waitForChatScrollAfterHistoryLoad → finalizeExistingLogLayout
```
滚动定位必须晚于图片布局准备、早于布局收尾——否则图片异步撑高会把刚定位好的视口顶走。契约由 `tests/test_feature_flags.py` 的索引顺序断言固定。

### 9.4 其他收口

| 场景 | 处理 |
|---|---|
| final 卡片渲染 | `cancelSmoothStreamFollowForFinal(ctx)`：取消 chat（仅当 final 属于当前可见 stream）+ 当前 process body，随后 legacy 立即贴底 |
| 会话切换 | `cancelSmoothStreamFollowForSessionSwitch()`：取消 rAF、`reset` chat 与所有 `.process-aggregate-body` |
| 历史加载开始 | `cancelSmoothStreamFollowForHistoryLoad()` |
| SSE 运行结束 | `endRunForClient` 中 `finishStreamScrollIfFollow(ctx, sid)` 必须早于 `clearSessionRunStateIfMatch`（测试断言顺序）——先结算滚动，再销毁 run ctx |

## 10. 双层滚动容器协作

```
.chat-container（外层对话区，chatContainer）
  └── .process-aggregate-body（内嵌执行过程视口，可折叠）
```
- 两个 port 共用一个跟随 rAF，但各自读取自己的底部目标；不再扫描轨迹行；
- 任一 port 被读者接管 → `onUnpin` 互斥取消另一个；
- `liveAutoFollow` 双门禁：对话区 72px、过程区 96px **同时**在底部附近才允许自动跟随（避免把正在读下半屏的用户拖走）；
- 跟随前自动展开当前过程组（移除 `is-collapsed`、同步 `aria-expanded`）；
- 内层 `.feed-chunk-scroller` 的滚轮"穿透转发"是另一条旧链路：`smoothScrollBy(el, dy)` 做 3 帧二次缓动（easeOutQuad），只服务于滚轮链式转发，不属于流式主链路。

## 13. 设计取舍与已知边界

1. **统一阻尼模型**：折行和整行只需观察底部目标，不再维护通道归因、速度地板和揭示速率反馈。
2. **速度连续**：目标每帧变化时保留当前速度，避免反复重启缓动段造成忽快忽慢；缓起减少单次折行的首帧跳感。
3. **软弹簧稳态滞后与位移上限**：固定刚度下持续增长内容的跟随稳态误差 = 2v/ω（常规流式 1–4 行/s 时 <1.5 行；高速长段 4–5 行属物理特性，可上调 `followStiffness` 收紧）；单帧 20px 上限仍约束大位移，不允许单帧爆冲。
4. **原有边界不改**：读者离开后不抢回，只有真正贴底才重新接管；历史动画与实时跟随互斥；流结束与 final 仍立即结算。
5. **浏览器夹持**：若折叠令可滚动范围直接小于当前位置，浏览器可能强制夹住 `scrollTop`。20px 限幅只约束控制器主动写入的实时跟随位移。

`isOwnedScroll()` 仍是预留接口。WAAPI 缺失时行高直接改变；历史滚动的 `scrollend` 仍有 rAF 兜底。

## 附录 A：收尾拖尾修复决策（2026-09-28）

旧实现的 `text` 通道没有最低速度：单次 19px 折行约 132 帧（2.2 秒）才缩到 0.25px 以内。旧的“高度稳定后一次走完”要求流式标记已退出；工具等待或网络间隙中标记仍在，因此拖尾直接暴露。

第一版修复采用 160ms 的 ease-out cubic 限时段。它解决了拖尾，但试用反馈显示首帧较快，单次 19px 折行首帧移动约 5.34px、133.4ms 到位，仍有跳感。

改为保留速度的临界阻尼跟随：单次 19px 折行首帧约 2.26px、216.7ms 到位；每 33ms 新增一行时，速度自然接续，峰值滞后 1.41 行。230ms 到位期限和 20px 单帧上限并存；大位移超出单帧容量时继续限幅追赶。`snapToBottom`、final 立即路径和关闭特性后的 legacy 路径依既有语义执行。

## 附录 B：软弹簧改造（2026-09-28，DeepSeek 对齐）

动机：试用反馈希望跟随更"软"——对齐 DeepSeek 手机端观感（`spring(180)` 固定刚度、临界阻尼、无到期期限）。

变更：删除 `followResponseBase / followResponsePerLagPx / followDeadlineMs`，改为固定 `followStiffness: 180`；响应 ω=√180≈13.42/s 为常数（去掉距离增强与 230ms 到期期限）；20px/帧上限保留为大位移安全阀；`lastFloor / lastFloorChangeMs` 字段随期限逻辑一并删除。

实测（`node tests/js/smooth_stream_runtime.cjs --report`）：单次折行 19px 首帧 0.41px、483.4ms 收敛；每 33ms 一行（约 570px/s）峰值滞后 84.95px（4.47 行，与稳态误差 2v/ω≈85px 理论吻合）；单次 200px 683.5ms。

trade-off：软弹簧稳态落后 = 2v/ω（v 为内容增长速率）。常规流式（1–4 行/s）滞后 <1.5 行；高速长段（>10 行/s）4–5 行是物理必然。若需更跟手可上调 `followStiffness`（240–320 对应更紧的滞后与更短的收尾）。
