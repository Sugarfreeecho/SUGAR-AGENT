## 4. 结论

1. **只看今天（9/11）**：DSH 中位 3.12s、MyAgent·e2e 中位 4.96s，DSH 快 **1.84s**。
2. **收敛到同一钟点窗**（11–16 点）差 1.95s；**把上下文规模分布对齐后**仍差 1.80s。所以差距不是「今天采样不均」或「MyAgent 上下文更大」造成的。
3. **不在客户端栈**（§5）：本地同连接基准里 Python SDK 只比 Node 贵 ~13 ms；生产 `stream_created`（收到响应头）中位 **4–5 ms**，连接是热的、响应头秒回。MyAgent 的 `pre_api` 组装中位也只有 0.07s。
4. **在请求内容**：工具数量 27 vs 61（DSH 的 27 个 schema 约 28.5 KB）、提示词结构不同；§2.1 显示每个规模桶 DSH 都快 1.3–2.5s。
5. **受控探针**（§3，无工具、同提示词）：真实组合差 691 ms，且差值 **100% 落在连接建立**上——因为探针每轮都是新进程冷连接。**探针没有工具维度，所以它解释不了生产里那 1.9s。**

### 怎么读这组数

- 「DSH 快 1.9s」是**观测差**：同端点、同模型、同钟点窗、规模对齐后依然成立；但它不等于「DSH 客户端更优」。
- 探针那 0.7s 是**冷连接**产物；生产里 99.7% 的请求连接是热的，这部分基本不存在。
- 剩下约 1.2–1.9s 最可能来自**请求内容**（工具 schema 61 vs 27、提示词构造），但**我还没有隔离证明它**——探针缺一个工具维度，验证方案见 §6 的 P1-2。

- DSH 的 465 个 step 里，主会话 262 个（中位 3.39s）、子代理会话 203 个（中位 2.89s）。只看主会话仍差 2.00s。

## 5. 客户端栈的真实代价（实测，非推断）

`ttft-probe/sse_range.py` + `bench_node.mjs` / `bench_py.py`：本地 canned SSE，响应头立即返回、延迟 30 ms 后发首个 delta，同一个热连接连打 120 次。

| 栈 | 首 token 中位 | 减去 30 ms 服务端延迟 = 纯客户端开销 |
|---|---:|---:|
| `node` 原生 fetch + 手写 SSE | 31.8 ms | **1.8 ms** |
| `python` openai SDK + httpx | 44.9 ms | **14.9 ms** |

→ 纯客户端**解析/分派**开销差 ~13 ms，可以忽略。

真实会话里 MyAgent 的 `stream_created`（httpx 拿到响应头）分布：

| 连接+响应头耗时 | 请求数 | 占比 |
|---|---:|---:|
| <100 ms | 776 | 99.7% |
| ≥4000 ms | 2 | 0.3% |

中位 **4–5 ms**。→ 生产里连接是热的，`stream_created` 占首 token 的 **0.1%**。

冷连接代价确实存在（探针每轮新进程）：`py:myagent − node:dsh` 的 `t_headers` 配对均值 **+694 ms**，而 `server_think` 差值只有 −23 ms（噪声）——**探针测到的差距 100% 是连接建立**。

生产里只有重连时才付这笔钱：739 对相邻请求中 **36.1%** 前面有 ≥5 s 空档（httpx 默认 `keepalive_expiry = 5.0 s` 会丢弃池化连接）：

| 前序空档 | n | 首 token 中位 |
|---|---:|---:|
| <1 s | 258 | 4978 ms |
| 1–5 s | 214 | 5418 ms |
| 5–15 s | 141 | 5515 ms |
| 15–60 s | 89 | 5134 ms |
| >60 s | 37 | 5699 ms |

冷热差 +212 ms（中位）/+301 ms（均值），且**不随空档单调**——所以 keep-alive 是次要因素。

## 6. 优化方案

按「证据强度 × 收益」排序。P0 是有实测支撑的，P1 需要先做实验再决定。

### P0-1 把 httpx 的 keep-alive 从 5 s 提高（几乎零风险）

```python
# agent_harness.py:837 附近
executor_http_client = RequestResponseLogger(
    timeout=OPENAI_HTTP_TIMEOUT,
    limits=httpx.Limits(
        max_connections=100,
        max_keepalive_connections=20,
        keepalive_expiry=300.0,   # 默认 5.0，工具执行动辄 5-30s，几乎每次都重连
    ),
)
```

依据：httpx 默认 `keepalive_expiry=5.0`（已实测打印）；36.1% 的请求前面有 ≥5 s 空档；冷连接实测贵 ~694 ms。预期收益：**重连请求省 ~0.2–0.7 s**，摊到全体约 **+0.07–0.25 s**。

### P0-2 确认没有别处在重建 client

`executor_http_client` 是模块级单例、transport 也有 `_executor_transport_cache`，但 `AnthropicMessagesTransport.__init__`（`transport.py:1744`）在没传 `http_client` 时会 `httpx.Client(timeout=60.0)` 新建一个。加一条断言/日志确认该路径没被走到：

```python
# 建议在创建处记录一次，便于事后统计重连次数
logger.info("http_client_created id=%s keepalive=%s", id(client), client._transport._pool._keepalive_expiry)
```

### P1-1 工具 schema 瘦身（收益最大，但需先验证）

实测差异：**DSH 27 个工具 / schema 28.5 KB；MyAgent 61 个工具**（778 条里 771 条）。
而且 §2.1 显示同规模桶 DSH 快 1.3–2.5 s，所以这是当前**最可疑**的一项。

但必须诚实说明两点：
- 首 token 与**未命中** token 数几乎无关（Spearman −0.02），与**总 prompt** 相关（+0.62），所以机制不是「prefill 变慢」，更可能是排队/推理启动。
- 我**没有**做过「同样任务、只改工具数量」的对照，所以不能断言瘦身能拿回 2 s。

建议动作（按成本递增）：

1. 先量：把 61 个工具的 schema 大小算出来（`context.tools` 只有计数，需要额外记录字节数）。
2. 再试：给 `subagent_tool_filter` / 工具注册加一个「按任务相关性裁剪」的开关，把常用路径压到 30 个以内。
3. 后验：用下面的 A/B 验证。

### P1-2 用工具维度扩展探针（这是唯一能给因果结论的实验）

现有 `run_probe.py` 是 2×2（栈 × 报文形态），**没有工具维度**，所以解释不了生产差距。加一维 `tools ∈ {0, 27, 61}` 即可定位：

```bash
# 在同一进程内、同一热连接上跑三个工具档位，交错随机顺序，每档 N>=20
# 关键：复用同一个 client，避免把冷连接代价算进工具对比
python ttft-probe/tools_probe.py --arms 0,27,61 --trials 20 --out ttft-probe/tools.json
```

判定标准：如果 `tools=61` 比 `tools=27` 慢 ≥1 s，则 P1-1 的收益被证实，值得动工具集；如果差异 <0.3 s，就把精力转向提示词结构与排队，别动工具。

### P1-3 关掉/收紧首 token hedge

`OPENAI_FIRST_TOKEN_HEDGE_TIMEOUT_SEC` / `OPENAI_FIRST_TOKEN_HEDGE_MAX_RETRIES`（`webui.py:6815`）会并发发第二个请求。它可能缩短长尾，但也会**抢占上游配额、让正常请求变慢**。建议记录 hedge 触发次数，和 TTFT 一起看；如果触发率高，先关掉再测 P90。

### P2 低优先级

- `max_tokens=50000`：778 条全是这个值，与 TTFT 无已知机制关联，可在 P1-2 里顺带扫一档。
- 切 HTTP/2（`httpx.Client(http2=True)`）：需要 `h2` 依赖，且服务端未必支持；在连接已热的前提下预期收益接近 0，不建议为此投入。
- 换掉 openai SDK 改手写 SSE：本地基准显示只值 ~13 ms，**投入产出比最差**，不要做。

### 建议的执行顺序

1. 落地 P0-1（一行改动，当天可验证）。
2. 跑 P1-2 的工具维度实验（一次 N=60 的探针，约 60 次调用）。
3. 按实验结果决定 P1-1 是否值得动工具集；同时统计 P1-3 的 hedge 触发率。
