# MyAgent 为什么整体慢 ~30%

排查时间：2026-09-11（UTC+8）
模型：`deepseek/deepseek-v4.1-flash`，端点 `https://api.commandcode.ai/provider/v1`

---

## 结论

**找到了一个你完全能控制的旋钮：MyAgent 的模型档案把 `reasoning_effort` 设成了 `max`。**

这不是"服务商区别对待"，是**MyAgent 主动要求模型思考更多**，而思考要花时间。

受控实验（同一条热连接、同提示词、随机顺序、每臂 8 次）：

| 臂 | 请求参数 | 首 token | **总耗时** | 思考字数 | 输出 token |
|---|---|---:|---:|---:|---:|
| **A（MyAgent 现行）** | `thinking.enabled` + `reasoning_effort: max` | **3009 ms** | **6762 ms** | **1930** | **706** |
| B（DSH 现行） | 两个字段都不发 | 2621 ms | 5428 ms | 1628 | 646 |
| C | `thinking.enabled` + `reasoning_effort: high` | 2676 ms | 5401 ms | 1380 | 563 |
| D | `thinking: disabled` | 2649 ms | 4824 ms | 1098 | 459 |

**A 臂在全部四项指标上都是最差的。** 统计检验（bootstrap 95% CI）：

| 对比 | 总耗时差 | 判定 |
|---|---|---|
| A − C（max vs high） | **+1362 ms**，CI [−2883, −45] | **显著**（p=0.015） |
| A − D（max vs 关闭） | **+1938 ms**，CI [−3421, −210] | **显著**（p=0.015） |
| A − B（max vs 不发字段） | +1335 ms，CI [−2782, +202] | 边缘（p=0.042） |
| A 的首 token | +333 ~ +388 ms | 边缘（p=0.03~0.07） |

**换成 `high` 或干脆不设，每次请求省约 1.3 秒（≈ 20–25%）。**

---

## 为什么是"多干活"而不是"被降速"

关键证据：**吐字速度四个臂完全一样。**

| 臂 | tok/s 中位 |
|---|---:|
| A（max） | 220.1 |
| B（不发字段） | 226.3 |
| C（high） | 217.7 |
| D（关闭） | 198.2 |

token 的产生速度没变，变的是 **token 的数量**（706 → 459）和**思考的字数**（1930 → 1098）。

所以慢的原因是：**effort=max 让模型想得更多，想得越多、输出越长、总时间越长。** 这是"干的活更多"，不是"被服务器怠慢"。

## 需要更正我之前的说法

我之前根据生产数据说"MyAgent 解码速度比 DSH 慢 20–27%，说明服务端区别对待"。

**这次受控实验没有复现那个差距**：A 臂（MyAgent 真实参数）220 tok/s，B 臂（DSH 参数）226 tok/s，几乎相同。

所以那条结论要撤回。更可能的解释是：MyAgent 因为 `effort=max` 产生了更多思考内容，**请求的组成不同**，导致我在生产数据里看到的"解码窗口"不可比。我当时把它归因给服务端，是过度解读。

**目前能站住的只有两条**：
1. `reasoning_effort: max` 让每次请求多花约 1.3 秒（本文，受控实验，显著）
2. 首 token 在生产数据里确实有 1.9 秒差距 —— 但控制实验只复现出 0.3–0.4 秒，**剩下的部分我解释不了**，不再归因给服务商。

## 附带发现：时间都花在哪

按 run 汇总（排除超长闲置 run 后，36 个 run）：

| 项目 | 占比 |
|---|---:|
| LLM 等待 + 生成 | **65.5%** |
| 工具执行 | **20.2%** |
| **未归账（harness 自身开销）** | **7.3–10.0%** |
| prompt 组装 `pre_api` | 1.4% |

两个可以查的点：

1. **未归账 7–10%** —— 这部分不属于任何已记录的阶段，可能是事件推送、日志、状态落盘、锁等待。
   按中位 210 秒的 run 算，约 **15–21 秒**没有归属，值得单独插桩。
2. **工具执行 20%** —— 其中我看到过 `ripgrep timed out after 30 seconds` 这类整段浪费（一次 30 秒）。
   工具侧是独立的优化方向。

（注：如果把全部 38 个 run 一起算，工具占比会显示 72.5% —— 那是一个 8 小时的闲置 run 造成的偏差，不代表常态。）

## 建议动作

### 第一步（立刻可做，风险需评估）

把模型档案里的 `reasoning_effort` 从 `max` 改成 `high`，或清空让它走服务端默认：

```jsonc
// model_profiles.json，profile 63193ce01d724a0084a1fd850c7f397b
"reasoning_effort": "high",   // 原为 "max"
```

预期：每次请求省 ~1.3 s（~20–25%）。
**代价**：思考变少，复杂任务的答案质量可能下降。**必须做质量对比再定**，不能只看速度。
建议在你的常规任务集上跑一轮 A/B，同时记录答案质量和耗时，再决定。

### 第二步（可选，收益中等）

查那 7–10% 的未归账开销。做法：在 run 循环里对"工具结束 → 下一次 API 发出"这段加一个显式计时，
现在这段被记成了 `round_gap_ms`（中位 1155 ms/run）但未纳入总账。

### 第三步（独立方向）

工具执行占 20%，且存在 30 秒级别的 grep 超时。这和推理速度无关，是另一条线。

### 明确不建议做的

- 改客户端网络栈（openai SDK / httpx）—— 实测只值 13 ms，已排除
- 加请求头 / 减工具数量 —— 两组受控实验（30 tokens 与 100k tokens 上下文）都是阴性
- 找服务商理论 —— 按你的判断，且本文的受控实验也不支持

---

## 证据边界

- 本实验 n=8/臂，随机顺序、热连接、同提示词，**A 臂显著慢于 C/D 臂**；A vs B 为边缘显著。
- 该实验用的是**合成小任务**（约 40 tokens 上下文）。生产请求是 100k+ tokens，
  effort 的绝对影响可能更大也可能更小，**需要拿你自己的任务复测**。
- "质量是否下降"**完全没有测**。这是决定要不要改的前提。
- 中间那 1.5 秒首 token 差距的成因仍未查明，本文不再归因给服务商。
