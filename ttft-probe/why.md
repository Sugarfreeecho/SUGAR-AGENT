# 为什么同一个模型，TTFT 会不一样

排查时间：2026-09-11（UTC+8）
对象：DSH（我）与本仓库 MyAgent，模型 `deepseek/deepseek-v4.1-flash`，端点 `https://api.commandcode.ai/provider/v1`，**两侧同一把 API key**

---

## 结论

**差距是真实的、在服务端、随上下文长度放大，而且不在任何客户端可见的东西上。**

具体三条：

1. **请求头与工具载荷都不是原因** —— 已做随机化实验，四个臂的差异全部落在噪声内（§3）。
2. **差距随上下文长度增长** —— 会话内回归，MyAgent 的 TTFT 斜率是 DSH 的 **约 3 倍**（12.7 vs 4.4 ms/1k tokens）；小上下文下两边都在 ~3.4 s 的地板上，几乎无差（§4）。
3. **不只首 token 慢，出 token 也慢 20–27%**（同上下文、同一天）—— 这一项客户端绝无可能影响（§5）。

**唯一还没排除、且有明确机制解释力的候选**：`x-opencode-*` 请求头在**长上下文下**影响网关的缓存亲和/路由。低上下文探针测不出它，因为短前缀根本没有亲和可言（§7）。

## 2. 已排除的候选（12 项）

| # | 候选 | 检验 | 结果 | 判定 |
|---|---|---|---|---|
| 1 | 客户端栈（openai SDK+httpx vs Node fetch） | 本地热连接连打 120 次 | Node 1.8 ms vs Python 14.9 ms → **差 13 ms** | 排除 |
| 2 | 连接未复用 | 生产 `stream_created` | 中位 **4–5 ms**，99.7% <100 ms | 排除 |
| 3 | harness 组装 prompt | MyAgent `pre_api.total_ms` | 中位 **66 ms** | 排除 |
| 4 | 账号/档位不同 | 两端 key 做 sha256 | 前 16 位**完全相同** | 排除 |
| 5 | 并发排队 | 重建双方在飞区间 | MyAgent **0.03**（98% 独占）vs DSH **1.03**（最多 4）→ DSH 并发更高却更快 | 排除（方向相反） |
| 6 | 报文形态/参数 | 2×2 探针拆连接段与服务端段 | 服务端段 +95 / −23 / −98 / +75 ms，符号翻转 | 排除 |
| 7 | 代理 | 环境变量 / 注册表 / httpx mount | 全空，`ProxyEnable=0` | 排除 |
| 8 | 工具数量 61 vs 27 | MyAgent 内 35 工具 vs 61 工具，同上下文 | 4261 vs 4354 ms（+93 ms） | 排除 |
| 9 | 上下文更长 | 20k 分档 | 每档仍差 1.0–2.6 s | 排除 |
| 10 | 未命中 token 多 | 匹配上下文比对未命中 | 160–200k：DSH 855 vs MA 866（几乎相同），仍差 716 ms | 排除 |
| 11 | 时段/上游波动 | 同一天同一小时 | 11 点 −2.58 s；15 点 −1.87 s | 排除 |
| 12 | 跨天混淆 | 只取 9/11 重算解码 | 每档仍是 **73–80%** | 排除 |

第 6 项要特别说明：探针里 `py` 臂比 `node` 臂慢的 ~0.7 s，**100% 落在连接建立段**
（`t_headers` 配对均值 +694 ms，`server_think` 仅 −23 ms）。探针每轮新进程付的是冷连接钱，
而生产 99.7% 的请求连接是热的 —— **这笔钱在生产里不存在**。我早前把它归因成"客户端栈慢 1 秒"是错的。

## 3. 随机化实验：请求头 × 工具载荷

`ttft-probe/header_probe.py`：同一条热连接（每种头设置一个 client）、同一提示词、随机交错顺序，
4 臂 × 10 轮 = 40 次真实调用。

| 臂 | 请求头 | 工具 | ttft 中位 | tok/s 中位 | 输出 tokens |
|---|---|---:|---:|---:|---:|
| A | 无 | 0 | 3444 ms | 327.3 | 812 |
| B | `x-opencode-*` | 0 | 3080 ms | 338.2 | 582 |
| C | 无 | 61 | 3525 ms | 314.4 | 476 |
| D | `x-opencode-*` | 61 | 3625 ms | 373.8 | 738 |

bootstrap 95% CI（5000 次重采样，基线 = A）：

| 对比 | TTFT 差 | 判定 |
|---|---|---|
| B − A（请求头） | −365 ms，CI [−1040, +500]，p(>0)=0.25 | **无可检测效应** |
| C − A（工具） | +81 ms，CI [−538, +1006]，p(>0)=0.61 | **无可检测效应** |
| D − A（两者都有） | +180 ms，CI [−438, +777]，p(>0)=0.60 | **无可检测效应** |

解码速度：B +11、C −13、D +47 tok/s，只有 D 的 CI 不含 0，但**方向与假设相反**（应该更慢才对），
在 6 次比较下属于典型的假阳性。

**结论：在这次实验的条件下（约 30 tokens 上下文），请求头和工具载荷都测量不到影响。**
顺序效应检查：前半 3459 ms / 后半 3505 ms，上游没有明显漂移。

### 3.2 长上下文版（100k tokens）

因为生产请求是 100k+ tokens，而前缀缓存的亲和性只在长前缀下才有价值，所以把同一实验搬到长上下文：
固定一段 ~100k tokens 的前缀，在所有臂间**逐字复用**（让缓存命中），4 臂 × 8 轮 = 32 次调用。

| 臂 | 请求头 | 工具 | prompt tokens | 缓存命中 | 未命中 | TTFT 中位 | tok/s 中位 |
|---|---|---:|---:|---:|---:|---:|---:|
| A | 无 | 0 | 80526 | 80384（99.8%） | **142** | 4890 ms | 331.6 |
| B | `x-opencode-*` | 0 | 80526 | 80384（99.8%） | **142** | 4971 ms | 351.8 |
| C | 无 | 61 | 93425 | 93184（99.7%） | **241** | 4775 ms | 349.0 |
| D | `x-opencode-*` | 61 | 93425 | 93184（99.7%） | **241** | 4606 ms | 321.2 |

32 次调用**全部命中**缓存，无一冷启动。bootstrap 95% CI（基线 A）：

| 对比 | TTFT 差 | 判定 |
|---|---|---|
| B − A（请求头） | +81 ms，CI [−463, +634]，p(>0)=0.66 | **无可检测效应** |
| C − A（工具） | −115 ms，CI [−484, +790]，p(>0)=0.49 | **无可检测效应** |
| D − A（两者都有） | −284 ms，CI [−601, +201]，p(>0)=0.18 | **无可检测效应** |

解码速度同样全部跨 0。顺序效应正常（前半 4907 / 后半 4742 ms）。

### 3.3 长上下文实验意外暴露的事实

把 §3.1 和 §3.2 并排看：

| 条件 | 未命中 tokens | TTFT |
|---|---:|---:|
| 30 tokens 上下文 | ~30 | 3.1–3.6 s |
| **100k tokens 上下文** | **142** | **4.6–5.0 s** |
| DSH 生产（116k 上下文） | 800–3500 | **3.0 s** |

**未命中只有 142 tokens，TTFT 却要 4.9 s** —— 比未命中 800–3500 tokens 的 DSH 生产请求还慢 1.9 s。

=> **TTFT 的主项不是 prefill 计算量**，而是**与总上下文长度成正比**的某个服务端开销。
这也解释了 §2 第 10 项（未命中 token 与 TTFT 几乎无关，Spearman −0.02）。

### 3.4 空闲间隔也不是原因

"后端 KV 被换出、下一个请求要重新载入"是上面结果的自然猜想。用生产数据免费验证：
会话内配对，回归 `TTFT ~ 提示词 + 距离上一次请求的空闲秒数`（n=754）：

| 项 | 系数 | t | 判定 |
|---|---:|---:|---|
| 提示词 | **+12.7 ms / 1k tok** | **10.99** | **显著** |
| 空闲间隔 | +1.4 ms / 秒 | 0.79 | 不显著 |

**间隔不显著，上下文长度高度显著。** 所以不是"缓存被换出"这么简单的故事。

## 4. 真正的线索：差距随上下文增长

小上下文探针里四个臂都在 **3.1–3.6 s**，彼此无差。而生产里 DSH 在 116k 上下文下 TTFT 仍是 ~3.0 s。
所以差距是**随上下文产生的**。

### 4.1 会话内回归（排除会话/时段混淆）

对每个会话单独回归 `ttft ~ prompt_tokens`，会话身份、工具集、路由、时段全部固定：

| MyAgent 会话 | n | 上下文范围 | 斜率 ms/1k | R² |
|---|---:|---|---:|---:|
| 82169eb8 | 288 | 17.5k–332.6k | 20.23 | 0.146 |
| f7fdabd5 | 76 | 17.5k–117.4k | 28.58 | 0.133 |
| d8ebc6ad | 67 | 148.6k–201.8k | 50.32 | 0.261 |
| 3feec161 | 112 | 17.5k–234.5k | 10.47 | 0.128 |
| ebda829d | 63 | 17.5k–124.5k | 14.81 | 0.332 |
| **中位** | | | **12.74** | |

| DSH 会话 | n | 上下文范围 | 斜率 ms/1k | R² |
|---|---:|---|---:|---:|
| session-47250bb0 | 143 | 8.6k–289.0k | 36.65 | 0.185 |
| session-6fc3c8e9 | 118 | 8.6k–217.5k | 4.83 | 0.069 |
| c6ec2e03 | 61 | 9.4k–184.5k | 9.92 | 0.133 |
| a894cb85 | 49 | 9.3k–147.2k | 2.60 | 0.011 |
| 8083629e | 40 | 9.3k–220.0k | 4.43 | 0.195 |
| **中位** | | | **4.43** | |

**MyAgent 的会话内斜率中位是 DSH 的 2.9 倍。** 这是同一会话内部的对比，
不可能是"会话间差异"或"时段差异"造成的。

### 4.2 差距的分解

在 120k 上下文处，斜率差贡献 `(12.74 − 4.43) × 120 ≈ 1.0 s`；
剩下的 ~0.9 s 是常数项（DSH 的 p05 地板 2429 ms vs MyAgent 3464 ms）。

## 5. 硬证据：解码速度也慢

如果差距只关乎"首 token"（排队、prefill），开始出 token 后速度应该一致。实测**不是**。

| 提示词 tokens | DSH tok/s | MyAgent tok/s | MyAgent/DSH |
|---|---:|---:|---:|
| 0–40k | 268.3 | 211.7 | **78.9%** |
| 40–80k | 266.5 | 204.7 | **76.8%** |
| 80–120k | 266.9 | 198.9 | **74.5%** |
| 120–160k | 257.8 | 215.9 | **83.7%** |
| 160–200k | 252.2 | 206.6 | **81.9%** |
| 200–240k | 241.0 | 207.7 | **86.2%** |

**只取 9/11 重算**（排除跨天混淆）：73.0 / 75.1 / 77.1 / 80.0 / 80.5% —— 结论不变。

排除计量误差：
- `turn_ready − stream_exhausted` 中位 **1 ms**（p90 3 ms）→ 解码窗口干净
- 回归 `decode_ms = a + b·output_tokens`：MyAgent R²=0.953，DSH R²=0.979
- 同上下文（120–160k）单独回归：**MyAgent 5.33 ms/token（187.6 tok/s）vs DSH 3.60 ms/token（277.6 tok/s）**

**解码速度由服务端的 KV 长度与批处理决定，客户端代码、请求头、工具载荷都影响不了它。**

## 6. 所以原因在哪

把 §2–§5 合起来：

- 客户端能影响的一切（栈、连接、组装、并发、参数、**请求头、工具载荷**）**都测过，都排除**，
  且请求头与工具载荷在 **30 tokens 和 100k tokens 两种上下文下各测一遍**，全部阴性；
- 客户端**无法**影响的量（每 token 解码速度）却差 20–27%；
- **未命中 token 只有 142 个时，TTFT 仍要 4.9 s** —— prefill 计算量被彻底排除；
- 空闲间隔也不显著（§3.4）；
- 两边 URL、API key、模型 id 完全相同。

**结论：TTFT 的主项是一个与「总上下文长度」成正比的服务端开销（MyAgent 约 12.7 ms / 1k tokens，
DSH 约 4.4 ms / 1k tokens，差 2.9 倍），外加一个常数偏移。它与请求声明的内容无关。**

### 物理上最像什么

12–18 µs / token 这个量级，与**服务端对整段输入做分词 + 前缀哈希匹配**的开销高度吻合。
这类工作是 O(总上下文) 的、**无法被前缀缓存跳过**，而且**与未命中 token 数无关** ——
正好对应全部实测现象（随上下文增长、与未命中无关、与请求头/工具无关）。

至于为什么 DSH 的每 token 开销只有 MyAgent 的 1/3，我没有证据。可能因素：
分词后的字节构成（JSON 转义密度、CJK 占比）、请求体的组织方式、或落到的后端不同。
**这是推测，不是结论。**

## 7. 下一步（尚未运行）

要真正定位，需要看到服务端的处理阶段，而日志给不了。可行的替代做法：

1. **同 key 同端点的对照内测**：用同一个脚本、同一分钟内交替发出"D SH 真实请求体"与
   "MyAgent 真实请求体"（各抓一份真实 payload），看每 token 开销是否稳定复现。
   这需要一个能抓到真实请求体的探针（MyAgent 目前不记录 messages 与工具 schema）。
2. **直接问 provider**：带上 §3.3 那张表（142 个未命中 token 换 4.9 s、解码慢 20–27%、
   同 key 同端点），这是很干净的问题描述。
3. **换端点验证**：如果换成直连或其他网关后每 token 开销改变，就落到网关/路由上。

不建议再做的：继续在客户端侧找原因（§2 已全部排除），或再跑请求头/工具的 A/B（两个上下文各测过一遍，均阴性）。

## 8. 证据边界（必须说清楚）

- **已证明**：不是客户端栈、连接复用、并发、凭据、代理、请求头、工具载荷、未命中 token 量、
  空闲间隔、时段、跨天造成的。
- **已测量**：TTFT 随总上下文增长，MyAgent 12.7 ms/1k vs DSH 4.4 ms/1k（会话内回归，t=10.99）；
  解码速度同上下文下慢 20–27%（同一天复核仍成立）。
- **未证明**：具体机制。§6 的"分词/前缀哈希"是量级吻合的推测，**不是结论**。
- 长上下文探针（§3.2）的绝对水平（4.9 s @80k）比 DSH 生产（3.0 s @116k）还慢，
  说明除上下文项外还有我没识别出的成分（可能是时段，也可能是探针场景本身）。
- 探针用的是合成前缀与合成工具，不等于真实对话内容。
- DSH 只有 9/11 一天日志；MyAgent 记录里没有完整 messages 与工具 schema。
