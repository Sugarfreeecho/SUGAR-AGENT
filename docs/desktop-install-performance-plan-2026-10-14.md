# 桌面版安装耗时分析与优化方案

日期：2026-10-14。分析对象为 SugarAgent 的 Windows x64 NSIS 安装包。

## 结论

主要成本来自大量小文件的创建、复制和清理。当前安装模板先将整个应用解压到 `%TEMP%` 下，再将全部文件复制到安装目录；覆盖安装还会逐文件搬移旧应用。首次启动则同步复制整套技能模板。降低压缩等级不能同时解决这些问题。

建议先合并飞书 SDK 和 PPT 图标这两大文件来源，再优化覆盖安装时的同卷旧文件搬移和首次启动的模板铺设。本机隔离对照中，ZIP 直解未获得速度改善，且归档体积增加约 27%，因此不建议直接修改默认安装格式。

以下统计记录优化实施前的产物。分析之后已落实 SDK / PPT 图标归档与松散字节码清理，并按用户后续要求生成 1.5.4 安装包；工程实施见第 6 节，最终结果见第 7 节。

## 1. 实物统计与版本边界

本地最新完整安装包为 `packaging/build/dist/SugarAgent-Setup-1.5.3-x64.exe`，生成于 2026-10-13。源码版本与 2026-10-14 的新载荷为 1.5.4，尚未生成对应安装包。以下安装包统计直接读取 1.5.3 内嵌的 `app-64.7z`，没有将调试启动产生的工作目录误计为分发内容。

| 项目 | 实测值 |
|---|---:|
| 1.5.3 安装器体积 | 264,511,283 B，约 252.3 MiB |
| 内嵌应用归档体积 | 263,934,151 B，约 251.7 MiB |
| 安装包内应用文件数 | 46,075 |
| 应用文件展开体积 | 718,355,706 B，约 685.1 MiB |
| 小于 4 KiB 的文件 | 38,979，占 84.6% |
| 飞书 SDK `lark_oapi` | 21,454 个文件，约 42.3 MiB |
| PPT 技能 `templates/icons` | 11,632 个文件，约 9.5 MiB |
| Python 字节码缓存 | 15,571 个文件，约 56.3 MiB；与 SDK 文件数重叠 |
| 新版 1.5.4 载荷 | 45,882 个文件，约 362.0 MiB；不含 Electron |

飞书 SDK 与 PPT 图标合计占安装文件数约 71.8%，是最值得处理的两项。图标数量来自现有本地技能模板，而非 Electron 或 Python 本身。

原始清单：`.analysis/desktop-install-analysis-20261014/installer-inventory.json`。

## 2. 已确认的耗时路径

### 2.1 新安装会完整写出应用两次

本地 `app-builder-lib` 26.15.3 的 `templates/nsis/include/extractAppPackage.nsh`：

1. 将内嵌归档写到 `$PLUGINSDIR/app-64.7z`。
2. `Nsis7z::Extract` 将整个应用解压到 `$PLUGINSDIR/7z-out`。
3. `CopyFiles /SILENT` 将整个应用复制到 `$INSTDIR`。
4. 退出安装器时还需要回收临时目录。

应用数据约 685 MiB，因此仅展开与最终复制就需要写出约 1.34 GiB 的文件内容，另外还有归档写入及数万次文件创建、目录操作。安装到 D: 而 `%TEMP%` 位于 C: 时，这些步骤还会访问两个卷。

`asar: true` 仅覆盖 Electron 外壳代码。Python、应用后端与技能模板通过 `extraResources` 放在 ASAR 外，因此现有 ASAR 配置没有合并这 4.6 万个文件。

### 2.2 覆盖安装增加逐文件搬移

`templates/nsis/uninstaller.nsh` 的 `un.atomicRMDir` 递归遍历旧程序文件，并逐个 `Rename` 到 `$PLUGINSDIR/old-install`。跨卷搬移文件会增加复制与删除成本；同卷也仍有数万次路径操作。当前补丁保留了回滚能力及 `workspace/.config/.sugaragent`，优化时应保留这些行为。

### 2.3 首次启动再次同步复制技能模板

`packaging/electron/main.js` 的 `seedWorkspace()` 用 `fs.cpSync` 铺设全部技能，再启动 Python 后端。当前新版模板有 13,188 个文件，约 108.2 MiB，其中 PPT 图标占 11,632 个。用户勾选安装完成后立即运行时，会连续经历安装落盘和这轮启动复制。

### 2.4 字节码缓存需要有选择地处理

依赖安装、自检会生成大量 `.pyc`，而载荷准备脚本只在复制应用和技能时过滤缓存，没有对最终 `site-packages` 做统一处理。完全删除 `.pyc` 能减文件，但可能让导入开销与缓存写入转移到首次启动。更合适的方向是将纯 Python SDK 合并为可直接导入的 ZIP，并正确布局与 Python 3.10 匹配的字节码。

### 2.5 放大因素与已有优化

本机 Defender 的病毒防护与实时保护均开启，可能放大大量文件创建、读取和复制的成本。当前尚未用文件事件跟踪量化它的占比，不能把全部耗时归因于防病毒软件。

无更新渠道时不再复制整份安装器到 updater 缓存，这项优化已存在；无需重复实施。NSIS 安装阶段没有联网安装 pip 依赖，`prepare-payload.mjs` 中的 pip 操作发生在构建机。

## 3. 推荐实施方案

| 顺序 | 改动 | 预期收益 | 实施成本与验收重点 |
|---|---|---|---|
| 1 | 将 `lark_oapi` 合并为可直接导入的 ZIP | 约 21,454 个落盘文件变为一个归档 | 中；SDK 导入、飞书长连接与消息收发、字节码与资源访问兼容性 |
| 1 | 将 PPT SVG 图标合并为归档，按图标读取或提取 | 约 11,632 个文件变为少量归档和索引；首次启动也少复制这一批 | 中；同时适配图标选择、同步、SVG 内嵌与 PPTX 导出 |
| 2 | 升级备份改为安装目录同卷的隔离目录，按受管理目录整体移动 | 避免跨卷旧文件复制及大量逐文件搬移 | 较高；保留回滚日志，覆盖占用、磁盘不足、取消与中断恢复 |
| 2 | 首启仅铺设必要技能文件，重资源由技能首次使用时初始化 | 缩短安装完成至可用界面的等待 | 中；保持离线可用、技能发现、用户修改与重复启动的正确性 |
| 3 | 文件数减少后，再评估同卷暂存并移动或 ZIP 直解 | 进一步消除整应用的重复复制 | ZIP 本轮未提速且包体增大；同卷移动需定制模板与失败恢复 |

SDK 与图标两项按归档清单估算，可将应用落盘文件数从 46,075 降到约 13,000，减少约 72%。这是文件数收益，不能直接等同为安装时间缩短 72%。

### 3.1 SDK 合并的边界

优先只处理已确认体量最大的纯 Python SDK，保留依赖的 `.dist-info` 元数据。通过明确的 Python 搜索路径挂载归档，验证 `lark_oapi`、消息请求类型与 `lark_oapi.ws`。若保留字节码，应使用 ZIP 导入支持的布局，而非简单保留 `__pycache__` 目录。

`.pyd` 和 DLL 仍需放在磁盘上。不能将整个 `site-packages` 机械压入 ZIP，也不能靠把它塞入 Electron ASAR 让 CPython 直接使用。[Python 3.10 ZIP 导入文档](https://docs.python.org/3.10/library/zipimport.html)明确说明动态模块不能从 ZIP 导入。

### 3.2 图标合并需要同步适配读取代码

当前图标选择服务与 `icon_sync.py` 等脚本直接读取 `templates/icons/<库>/<名称>.svg`。归档化必须同步提供兼容的查找、读取与单图标提取入口；不能只修改打包过滤器。保留目录索引和完整图标库，以维持离线能力。

安装结束或首次启动时不应立即全量展开图标，否则只是把等待转移到下一阶段。

### 3.3 ZIP 直解属于候选方案

候选配置位于 `packaging/electron-builder.config.cjs` 的 `nsis` 段：

```js
useZip: true,
differentialPackage: false,
```

两个选项须一起设置：本地构建器在 `differentialPackage` 未关闭时仍选择 7z。已核对[官方 NSIS 文档](https://www.electron.build/v26/docs/nsis/)和本地实现。

ZIP 的直接解压分支没有 7z 分支同样的临时复制及重试逻辑，须完成失败场景验收再发布。当前没有自动更新渠道，关闭差分归档不会影响现有手动覆盖安装；将来引入自动更新时需要重新选择。

本轮对照的 ZIP 归档为 334,651,140 B，约 319.1 MiB，比原 7z 归档增加约 26.8%。7-Zip 的 ZIP 直解耗时 226.086 秒，未优于 7z 展开加 Python 复制的 204.878 秒。因此这两个选项只作为后续对照候选，不建议直接应用到默认配置。真实 `nsisunz` 插件可能有不同表现，仍应以安装器对照验收为准。

若 ZIP 的体积代价过高，可保留 7z，但定制为在目标卷的暂存目录解压、按受管理目录移动，并补齐失败恢复。这条路线代码与维护成本更高。

### 3.4 旧版本升级的过渡限制

覆盖安装调用的是已经安装的旧卸载器。因此，即使新包优化了卸载器，从 1.5.3 首次升级时仍可能执行旧版的逐文件搬移；优化在之后的升级中才完整生效。不能只测试“新包覆盖新包”后就宣称所有旧版升级均已提速。

## 4. 对照测量与验收

隔离基准脚本：`.analysis/desktop-install-analysis-20261014/benchmark.py`。它读取现有安装包内嵌归档，只在分析目录执行解压、复制和 ZIP 对照，不运行安装器、不写产品注册表。

本地归档 I/O 计时见同目录 `benchmark.json`。该结果使用缓存过的 D: 数据、7-Zip 24.09 和 Python 复制函数，只说明归档与文件操作的成本，不能替代真实 NSIS 插件、C: 临时目录及覆盖升级的端到端计时。

| 隔离测量阶段 | 单次耗时 |
|---|---:|
| 7z 完整校验，不写出应用文件 | 9.279 秒 |
| 7z 解压全部应用文件 | 165.009 秒 |
| Python 复制全部展开文件到另一目录 | 39.869 秒 |
| ZIP 直接解压全部应用文件 | 226.086 秒 |
| 构建同内容 ZIP 归档，Deflate 等级 7 | 165.212 秒；发生在构建机，不计入安装耗时 |

解压落盘与额外复制合计约 205 秒，显著高于不落盘的内容校验。两种 7z 操作不是完全等价的计算过程，因此不将两者的差值全部归因于某一种磁盘或防护开销。

ZIP 与 7z 单次测量顺序固定，也未控制防护扫描缓存，不能据此推导所有机器上 ZIP 必然更慢；但目前没有支持切换默认格式的实测收益。

分析目录嵌套较深，最初的 Python 复制探针遇到 Windows 长路径问题；改为显式使用扩展路径后完成复制。该失败不作为安装器失败证据，也不计入上述成功耗时。正式方案仍须覆盖长安装路径验收。

正式验收采用相同机器、相同内容，按新装/同卷升级/跨卷升级分别测量，保留实时防护。拆分记录：安装器初始化、旧版处理、归档释放、解压、复制、注册完成、首次启动铺设、后端就绪。每种条件至少三次，区分冷启动与缓存条件。

推荐首轮目标为：落盘应用文件数不超过约 13,000，安装耗时中位数较当前包降低至少 50%，安装后首次可用时间不变差。它们是待验收目标，不是当前已经实现的性能承诺。

功能验收覆盖工作目录与配置保留、飞书消息收发、PPT 图标及导出、中文安装路径、被占用文件、磁盘不足和取消/失败恢复。只改变一个优化项的对照样本用于归因，最后验证组合方案。

## 5. 分析数据保留

基准测试生成的展开目录、复制目录与对照归档合计约 3.2 GiB，位于 `.analysis/desktop-install-analysis-20261014/`。自动审批拒绝了临时文件清理命令，只返回 `blocked by policy`，因此这些数据仍保留。可回收的对象是 `expanded`、`copied`、`copied-longpath`、`zip-expanded`、`app-64.7z` 和 `app-deflate.zip`；保留 `benchmark.py`、`benchmark.json`、`archive-sizes.json` 与 `installer-inventory.json` 即可保留分析依据。

## 6. 工程更新（暂不打包）

已将第一优先级两项优化接入下一次载荷准备：

- `archive-runtime.py` 将完整飞书 SDK 合并为带预编译字节码的 ZIP，通过 `.pth` 自动导入，保留并更新依赖元数据中的 `RECORD`。
- PPT 图标合并为 ZIP 和完整名称索引，只对载荷技能副本适配图标同步、SVG 解析及确认预览。源工作区技能保持原状，图标按使用提取，自定义项目图标优先保留。
- 载荷清单记录归档信息，构建前后检查布局，防止使用旧载荷或带入已展开图标。安装器压缩格式与用户数据保留规则保持原状。

验证：14 项测试通过，1 项目录符号链接测试因本机权限不支持而跳过；涉及生成卸载测试 exe 的检查按“暂不打包”要求未运行。完整真实输入隔离验证确认便携 Python 自动从归档导入 SDK，并构造飞书客户端、长连接客户端及消息请求对象；11,631 个 SVG 全部可检索，使用 5 个仅提取 5 个。SDK 验证没有连接飞书或发送消息。

已验证源代码与资源兼容性；安装耗时改善仍待后续真实安装器构建与对照验收。本次未运行 `prepare-payload.mjs` 或 `electron-builder`，现有 `build/payload`、`win-unpacked` 和 1.5.1 / 1.5.2 / 1.5.3 安装包均未重建。同卷升级搬移属于后续优化项。
