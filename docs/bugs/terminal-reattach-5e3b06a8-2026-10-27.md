## 代码中复现的入口

1. `maybeTakeOverActiveRuntimeSession` 只看 Runtime 心跳中的会话 ID。旧心跳可以在终态之后返回；原实现立刻把 `stream_active` 设为 true，然后强制 attach，同时发起但不等待详情刷新。
2. `attachSessionEventStream` 在历史加载或尾部补页前检查本地 reader，异步返回后未重新检查原 run 是否已终态、是否已有更新的 reader。`force` 还会绕过活动状态检查。
3. 新建观察流进入 `runsBySession` 后，selector 优先把本地 reader 当作运行中；对账中的 `streamAlive` 守卫保留仍在读取但未见终态的连接，空闲超时为 120000 ms。

这两个入口可以独立在完整构建页面中复现错误重连。现场没有记录这次 attach 的调用栈，不能把两个入口中具体哪一个先执行当成已观测事实；原流程退出后的新 `/stream` 和两分钟后的 `missing-terminal` 均有直接日志证据。

心跳接管入口的旧逻辑可追溯到 `d022831f`（2026-09-14）。之前的终态保护修复覆盖了摘要写入和通知，但漏了接管入口直接写运行状态及异步 attach 的空隙。本次属于补齐遗漏，不能把上次“综合修复”理解为所有入口已覆盖。

## 本次修改

- 接管先等待原本就会发起的详情刷新；仅在仍有活动 run、页面未切换、本地没有 reader 且 run 未终态时才 attach。取消心跳对 `stream_active=true` 的无条件写入。
- attach 等待历史/尾部加载后重新验证原 run 的终态和当前 reader，防止关闭后复活或覆盖新 reader。
- 对每个会话的待建流任务去重，避免两个异步 attach 同时通过最初检查。
- 复用原有请求，没有增加发送前检查、轮询频率或定时器。
