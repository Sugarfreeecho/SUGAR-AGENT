# 长会话 ask／审批待处理标记丢失

## 根因

- 后台会话的 SSE reader 会因连接预算或断线被释放。会话列表通过 `/sessions/changes` 和 `/sessions/state` 对账，但 ask／审批的创建、解决、取消、过期事件不在状态缓存失效集合中，无法及时唤醒列表。
- `sessionPendingHumanCounts()` 一旦发现本地交互缓存已加载，就永久优先使用它。后台会话漏收事件后，即使服务端摘要已经包含待处理事项，旧的空缓存仍会隐藏黄色标记；反向也会导致处理后的标记残留。

## 修改

- 将两类交互的上述八种事件接入既有状态缓存失效及长轮询通知。
- 列表、全局待处理数量统一读取会话摘要；实时交互和 inbox 刷新继续更新同一份摘要。没有摘要时才读取本地交互记录。
- 列表请求开始时记录交互更新代数。请求期间收到实时事件或完成 inbox 刷新时，晚到的旧列表响应不能覆盖这次更新；随后发出的列表请求仍可恢复漏收状态。失败的 inbox 请求不增加更新代数。
- 覆盖状态接口的诊断路径、普通路径和旧接口回退路径，沿用现有通知与轮询机制。

## 验证

- 修改前：新增测试中八种事件均未更新通知游标；真实浏览器中的 ask 和审批标记均未出现，共 10 项失败。Node 测试也复现了旧交互缓存遮蔽新摘要。
- 修改后：定向回归 93 项通过，覆盖 HTTP 通知与缓存恢复、真实页面的会话状态收敛、未读结果、通知和交互卡片编辑器。
- Node 顺序测试覆盖 ask／审批、创建／解决、两种列表请求路径，以及 inbox 成功／失败与列表响应交错；既有列表长轮询脚本通过。
- 更广的测试集合中另有三项已有脚本失败：`stream_connect_timeout_runtime.cjs`、`runtime_status_takeover.cjs`、`tool_pending_history_recovery_runtime.cjs`。在内存中移除本次前端修改后，三者仍报相同错误；涉及旧夹具缺少 `sessionStreamAttachments` 及 takeover 的旧断言。
- Vite 生产构建与 `scripts/check_frontend_dist_sync.py` 通过。

## 生效

前端产物已重建。后端重启并刷新现有页面后加载完整修复；本次未重启运行中的服务。
