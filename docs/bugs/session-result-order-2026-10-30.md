# 会话结果乱序回流修复

## 问题与原因

SugarAgent 的第一版修复按页面首次收到 run 结果的先后顺序维护结果历史。页面先收到新 run 的成功，后收到此前未观察到的旧 run 失败时，会把旧 run 当成最新结果；之后正确的新结果快照反而被过滤。反向顺序也会把真实失败错误显示为成功。

只在测试中预先让页面观察旧结果，无法覆盖这个问题。独立审查在全量快照、单条刷新和成功/失败两个方向上复现了四个失败。

## 修改

- 在已有的后端 run 启动顺序上增加持久化基数，裁剪最近 64 条记录时保持每个 run 的序号不变。普通运行和 continuation 均登记启动顺序。
- 会话摘要携带 `unread_result_run_order`、`unread_result_last_run_id`；实时终态、持久终态 payload 和会话变化通知携带同一个 `result_run_order`。读取会话保留顺序与最后结果身份，索引重建、导入和进程重启后仍可使用。
- 前端依据后端序号比较不同 run，旧快照或旧终态第一次出现时也不能覆盖更新的结果。更高序号的结果（例如其他标签页完成的运行）正常更新；同一 run 的明确失败仍保持失败。
- 缺少序号的陌生 HTTP 结果不能通过到达时间取得更高优先级，也不会污染本地排序历史。初次加载和旧版实时事件仍可读取；完整排序保护要求加载新版后端。
- 在清除活动状态、确认已读之前过滤已过期的终态，避免旧事件对新状态产生副作用。

没有增加轮询或发送前探测，没有清理真实会话历史或批量消除已有失败标记。

## 验证

- 审查时保存的四个独立复现现已全部通过。
- Node 回归覆盖首次收到旧结果、成功和失败两个方向、全量/单条刷新、新标签页结果、已读后回流、旧终态及同 run 失败优先级。
- 隔离浏览器验证真实 CSS 圆点颜色，新增上述四个首次收到旧结果的场景。
- Python 验证序号在裁剪、已读、索引重建和重启后保持稳定；三个 HTTP 摘要入口与实时终态通知使用相同序号。运行收尾测试验证普通终态与 Goal 各种结果的持久/live payload 一致。
- 扩展回归：197 passed，3 failed。三个失败是 `stream_connect_timeout_runtime.cjs`、`runtime_status_takeover.cjs`、`tool_pending_history_recovery_runtime.cjs`；对它们读取的前端源文件替换为原始 HEAD 后，仍然出现相同失败。未扩大本次修改范围去修复这些已有 SSE 接管测试。
- 六个相关 Node 运行时脚本单独通过。前端生产构建和 `check_frontend_dist_sync.py` 均通过。

## 生效

后端需要重启以加载 Python 修改，页面需要刷新以加载重新构建的前端。此次未自动重启后端、重发任务或操作用户会话。
