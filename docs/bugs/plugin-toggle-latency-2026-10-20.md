# 插件开关耗时与加载反馈

## 原因

启用、禁用单个插件时，原请求链路包含了与目标插件无关的工作：

1. `set_plugin_enabled()` 调用全局缓存失效，释放所有插件任务租约，关闭所有
   插件工作进程并丢弃其描述缓存；随后刷新又重新启动、描述这些插件。
2. 缓存失效会等待后台目录扫描或 Hook 重建完成，等待上限为 60 秒。
3. 开关 API 无条件调用 MCP `force_reload()`，逐个关闭全部 MCP 连接。
   这既可能等待无关服务退出，也使后续工具查询重新连接这些服务。
4. 生命周期刷新强制加载一次插件，后台服务启动又强制加载一次；有会话的
   开关请求在审计中继续发现、强制加载。同步扫描还占用了 Web 事件循环。
5. 前端已经有同一插件的重复提交保护，但忙碌时仅把 tooltip 改为“处理中”，
   状态文字仍为“已启用/已禁用”，动作区在鼠标离开后消失，没有明显加载反馈。
   POST 完成后还要等待扩展列表 GET，且该 GET 失败原先也会被报告为状态更新失败。

这些是代码路径与隔离验证确认的问题；本次没有切换用户正在使用的插件来测量
线上端到端耗时。原请求的具体慢阶段可由新增日志和响应头继续确认。

## 修复

- 开关操作只释放目标插件的宿主任务租约、工作进程、工具绑定和 deferred
  结果租约，保留其他插件的工作进程、描述缓存及租约。全局重载仍保留原语义。
- 后台目录刷新、Hook 重建记录启动时的目录版本。失效后旧版本的结果不能
  回填缓存，因此单插件开关无需等待无关后台刷新完成。
- 只有声明 MCP 服务的插件才需要刷新其 MCP 连接，且按完整插件命名空间
  前缀清理，保留其他插件及独立配置的连接；重新发现继续使用现有按需路径。
- 生命周期复用同一份加载结果启动后台服务，审计复用本次已验证的目录，
  启用状态文件每次审计读取一次；同步目录加载移到工作线程。
- API 记录 state、lifecycle、mcp、audit、total 阶段耗时，同时返回
  `Server-Timing` 响应头，供日志和浏览器开发者工具定位实际慢阶段。
- 前端立刻禁用已点击的按钮，持续显示转圈和“正在启用/禁用”；鼠标离开后
  提示仍可见，8 秒后增加“请稍候”。POST 成功后显示“正在刷新列表”，并保留
  后端已确认的开关状态。刷新失败会明确提示“插件已启用/禁用，但列表刷新失败”。
- 操作结束或出错均清理忙碌标记和计时器。迟到的旧目录请求不能覆盖新目录，
  操作完成事件保持点击时的会话 ID，避免用户切换会话后通知错误的会话。

## 测量与验证

本机对 12 个仓库插件做只读目录扫描：未插桩的两次结果为 112.8、114.4 ms；
带 profiler 的首次扫描为 156.5 ms。重复扫描增加延迟，但不足以单独解释
数秒甚至更久的等待。

另在临时目录创建两个最小 Python SDK 插件，使用真实持久工作进程，预热后
执行四次目标插件禁用/启用；计时范围为状态更新和工作进程刷新，不含 MCP、
浏览器或真实会话审计：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 四次切换耗时中位数 | 443.89 ms | 275.99 ms |
| 无关工作进程被重启的次数 | 4 / 4 | 0 / 4 |

该小规模隔离基准中位数下降约 38%；它不代表所有插件或实际页面的固定耗时。
目标插件自身需要释放资源、退出或启动时仍需等待真实完成，前端会持续显示进度。

157 项相关测试通过，包含目标清理隔离、后台旧结果拒绝回填、MCP 连接隔离、
单次目录加载、审计复用、此前的执行会话误停回归，以及前端成功/失败/刷新异常、
重复点击和旧响应覆盖等路径。深色、浅色主题均通过真实 Chromium DOM 检查，
截图位于 `.analysis/plugin-toggle/loading-dark.png`、`loading-light.png`。

`npm run build`、`python -X utf8 scripts/check_frontend_dist_sync.py` 及修改文件的
`git diff --check` 通过。后端重启并刷新页面后加载本次修复。
