# 审批卡片：压实前后的取数方法、分析与误判修复

> 适用版本：Runtime V2，`PROJECTOR_VERSION = 11`，提交 `b0e5dd2` 及之后。
> 用途：在一台**新机器**上核对历史上的"红色审批"是否已被本次优化正确覆盖。

---

## 0. 一句话结论

红色审批（forced approval）在会话记录里**不是一处**，而是**五处**；只读 `events.jsonl` 会漏掉已压实会话的全部历史审批。判定"红不红"读 `approval_level == "danger"`，但 2026-08 之前的记录没有这个字段，需要按 `security_rule_id` 推断。

本次修复后，本机 86 条历史红色（窗口 `2026-10-01 ~ 2026-11-08`，32 个会话）中：**17 条降级为黄色、4 条为误报彻底消失、65 条仍为红色**。

> 2026-11-10 追加「删除与其它红线分离」（见 4.6）后，同一起点（`--since 2026-10-01`，97 条）为：
> **96 条降级为普通审批、1 条仍红**（`Remove-Item -Recurse -Force C:\Windows\Temp\prereq_tree`）。

> 数字会随会话增长而变。核对时务必**固定窗口**（见 5.3 的 `--until`），否则每次跑出来的总数都不一样——分析动作本身也会产生新的审批。

## 1. 卡片数据存在哪里

### 1.1 五种存储形态（必须全部覆盖）

| # | 形态 | 识别方法 | 审批数据位置 |
|---|---|---|---|
| 1 | 原始 Runtime V2 日志 | 首行不是 `runtime_snapshot_compacted` | `events.jsonl` 中的 `approval_requested` / `approval_resolved` |
| 2 | **已压实日志** | 首行是 `runtime_snapshot_compacted` | 首行 `payload.snapshot.approvals`（以 `approval_id` 为键） |
| 3 | **压实后又续跑** | 压实日志的第 2 行起还有内容 | 基线快照 **+** 之后追加的 `approval_*` 事件 |
| 4 | 子代理日志 | `sessions/<父>/subagents/<agent>/events.jsonl` | 同 1/2，子代理也会被压实 |
| 5 | 旧格式会话（无 `events.jsonl`） | 目录里只有 `ui_events.json` / `work_messages.json` | 递归搜含 `approval_id` 的字典 |

> 本机实测：631 个根日志里 128 个已压实；只读 `approval_requested` 得到 25 条，补全后是 86 条。

### 1.2 两个必踩的坑

**坑一：快照里同一张卡片存了两份。**
`payload.snapshot` 同时有 `approvals`（全部）与 `pending_approvals`（仅未决）。直接 grep 字面量 `"approval_level":"danger"` 会得到 288 处（全时段），而按 `approval_id` 去重后，10 月以来只有 86 条。

**坑二：`latest.json` 不能直接 `json.load`。**
单文件可达 270 MiB，`json.load` 会 OOM。需要读快照时用 `ijson` 流式，或干脆只读 `events.jsonl`。

### 1.3 字段表（`approval_requested.payload`）

| 字段 | 含义 | 备注 |
|---|---|---|
| `approval_id` | 唯一 id | **去重键**；重试会生成新 id |
| `approval_level` | `danger` / `warning` / 缺失 | 前端 `human-interactions.js:1269` 只认 `=== 'danger'` → `is-danger` 红卡 |
| `status` | `pending` / `resolved` / `cancelled` / `expired` | |
| `decision` | `allow_once` / `allow_session` / `allow_always` / `deny` | 与 `status` 合并判断结果 |
| `security_rule_id` | 命中的策略规则 | **落库字段**，分析以它为准 |
| `rule_id` | 卡片级规则 id | 历史记录里缺失，本次起落库 |
| `destructive_kinds` | 命中的危险模式 id 列表 | **本次新增** |
| `destructive_labels` | 中文标签列表 | **本次新增** |
| `destructive_summary` | 标签拼接，直接上屏 | **本次新增** |
| `title` / `subtitle` / `message` | 卡片文案 / 拦截原因 / 命令预览 | `message` 形如 `run_shell("command": "...", ...)`，**会被截断** |
| `consequence` | 后果说明 | 危险卡片会带"命中规则：…" |

### 1.4 旧记录没有 `approval_level` 怎么办

2026-08 之前的卡片只有 `security_rule_id`。推断规则与当时一致：

```
security_rule_id ∈ {process.destructive, session.workspace_switch}  → 红
否则                                                              → 黄
```

本机 88 条缺字段记录全部落在 2026-07，`security_rule_id` 为 `external.read`、`network.default_deny`、`process.external` 等，**没有一条是强制审批规则**，即不存在漏计。
审计脚本已内置该推断，输出为 `danger(inferred)`。

### 2.2 手工最小复现

```python
import json
from pathlib import Path

def is_compacted(path):
    with path.open(encoding="utf-8", errors="replace") as fh:
        return '"runtime_snapshot_compacted"' in fh.readline()

def approvals(log):
    if not is_compacted(log):
        # 原始日志：requested 与 resolved 按 approval_id 合并
        req, res = {}, {}
        for line in log.open(encoding="utf-8", errors="replace"):
            if "approval_" not in line:
                continue
            ev = json.loads(line)
            p = ev.get("payload") or {}
            if ev.get("type") == "approval_requested":
                req[p["approval_id"]] = p
            elif ev.get("type") == "approval_resolved":
                res[p["approval_id"]] = p
        for aid, p in req.items():
            yield {**p, **{k: v for k, v in res.get(aid, {}).items() if v not in (None, "")}}
        return
    # 压实日志：首行快照 + 后续追加
    with log.open(encoding="utf-8", errors="replace") as fh:
        base = json.loads(fh.readline())
        for aid, row in ((base.get("payload") or {}).get("snapshot") or {}).get("approvals", {}).items():
            yield row
        for line in fh:              # ← 别漏了基线之后续跑的事件
            ev = json.loads(line)
            if ev.get("type") == "approval_requested":
                yield ev["payload"]
```

关键点三条：**首行判定、基线 + 追加、按 `approval_id` 去重**。

### 2.3 从卡片文本还原真实命令

`message` 是预览串，命令本身是其中的一个 JSON 字符串字面量：

```python
import json
DEC = json.JSONDecoder()

def extract(message: str) -> str:
    i = message.find('"command": ')
    if i < 0:
        return ""
    try:
        value, _ = DEC.raw_decode(message[i + len('"command": '):])
        return value if isinstance(value, str) else ""
    except ValueError:
        return ""      # 预览被截断，无法还原
```

不要用正则去配引号——命令里会有转义的 `\"`，只有 `raw_decode` 能正确处理。截断的预览无法还原，统计里要单列"无法解析"。

## 3. 分析方法

### 3.1 为什么它会变红（归因链）

`app/security/runtime.py::classify_tool` 里的判定：

```
deletion        = _DELETE_COMMAND.search(命令) 命中
destructive     = dangerous_matches(命令) 非空  or  deletion
workspace_delete = deletion and not external and not 其它危险模式
红卡            = destructive and not workspace_delete
```

展开成三条子路径：

| 路径 | 条件 | 结果 |
|---|---|---|
| A | `deletion` 且目标在**工作区外**，目标是具体文件/目录 | 普通审批 `delete.review`（2026-11-10 起） |
| A' | `deletion` 且目标是磁盘根、家目录/家目录父级、`C:\Windows`、`Program Files*` 等系统树 | 红（合理） |
| B | `deletion` 且命令还含 `format`/`shutdown` 等非删除红线 | 红（合理） |
| C | `destructive` 成立但 `deletion` 不成立 | 红——**多半是识别缺陷或误报** |

路径 C 就是这次要消灭的对象。

> 2026-11-10 起，`deletion` 的判定拆成「只看删除语句里的路径」（`_delete_targets_text`），
> 因此回放时 `destructive=True, workspace_delete=False` **不再等于红**：是否强制要看
> `PolicyEngine.decide` 的 `rule_id` 是否落在 `FORCED_APPROVAL_RULES`。`audit_red_impact.py`
> 已改为直接调用策略引擎。

### 3.2 必须用"会话自己的 work_dir"回放

`external` 是相对**该会话当时的工作目录**算的。拿全局 `workspace/` 去回放，所有沙箱会话都会被误判成"工作区外"。正确做法是读 `sessions/<id>/metadata.json` 的 `work_dir`。

```python
from security.runtime import classify_tool
meta = classify_tool("run_shell", {"command": cmd}, session_work_dir).metadata
```

读 `meta["destructive"]` / `meta["workspace_delete"]` / `meta["external_workspace"]` / `meta["destructive_kinds"]`，即可判定这条在**新规则下**会是什么颜色。

### 3.3 输出含义对照

| 回放结果 | 含义 | 是否要处理 |
|---|---|---|
| `destructive=True, workspace_delete=True` | 新规则下是黄色，普通删除确认 | 已改善，无需处理 |
| `destructive=True, workspace_delete=False` | 仍是红色 | 抽查是否有误判 |
| `destructive=False` | 新规则下不再拦截 | 误报已修掉 |
| 命令为空 | 预览被截断 | 需从原始日志补 |

## 4. 本次修复了什么

### 4.1 删除检测补上语句边界（`app/security/runtime.py`）

```python
# 之前
r"(?i)(?:^|[;&|])\s*(?:rm|rmdir|del|erase|remove-item)\b"
# 现在
_STATEMENT_SEPARATOR = r"(?:^|[;&|\n{])\s*"
r"(?im)" + _STATEMENT_SEPARATOR + r"(?:rm|rmdir|del|erase|remove-item|git\s+rm)\b"
```

**为什么**：PowerShell 用换行分隔语句，`{` 后常跟一条语句。原正则只认 `^` 和 `; & |`，导致

```powershell
Set-Location "D:\..."
Remove-Item -Recurse -Force _pristine_check
```

和 `if(Test-Path $p){ Remove-Item ... }` **完全不算删除**。后果是双重的：即使删的是工作区内的 `__pycache__`，也一直是最严格的红卡；而记录的原因只能是笼统的"破坏性命令"。

**影响面**：工作区内删除 → 黄色 `process.workspace_delete`（可"始终允许同类"），红色量下降。

### 4.2 匹配前剥离"数据区"（`app/agent_tools.py`）

新增 `_danger_scan_text()`，只剥离**可证明是数据**的部分：

| 目标 | 正则 | 例子 |
|---|---|---|
| 搜索模式参数 | `_SEARCH_ARGUMENT_RE` | `Select-String -Pattern '…RMDir…'`、`grep 'rm -rf'` |
| here-string 内的字符串字面量 | `_HERESTRING_RE` + `_INNER_STRING_RE` | `@' … "Shell rm -rf / rmdir are blocked." … '@` |
| 方法调用式 shutdown | `(?<![.\w])(?:shutdown\|reboot\|poweroff)(?!\s*\()` | `server.shutdown()` |

**刻意不剥离**（防止漏检）：

- here-string **主体本身**（常被管道给解释器执行）
- `bash -c "…"`、`powershell -Command "…"` 的内容
- 任何引号外的命令词

所以 `bash -c "rm -rf /"` 仍然是红色——这条有单测守着。

同时 `deletion` 判定也改用剥离后的文本，避免把 grep 关键词当成删除。

### 4.3 危险模式带 id 和中文标签（`app/agent_tools.py`）

原来是一串裸正则，现在每条一个 `(kind, label, pattern)`：

```python
DELETION_DANGEROUS_SPECS = (
    ("delete.rm_recursive", "递归删除 rm -r/-rf", r"\brm\s+-[rf]{1,2}\b"),
    ("delete.del_force", "强制删除 del /f 或 /q", …),
    ("delete.rmdir_recursive", "递归删除目录 rmdir /s", …),
    ("delete.remove_item_recursive_force", "递归强制删除 Remove-Item -Recurse -Force", …),
)
NON_DELETE_DANGEROUS_SPECS = (
    ("disk.format", "格式化磁盘 format", …),
    ("disk.partition", "分区/磁盘操作 mkfs 或 diskpart", …),
    ("disk.dd", "裸写磁盘 dd", …),
    ("system.power", "关机/重启 shutdown/reboot/poweroff", …),
    …
)
```

`dangerous_matches(cmd)` 返回全部命中项。未命中任何模式、但确实是删除的命令（如 `Remove-Item -Force`），用 `_delete_label()` 兜底成 `delete.command` / "删除 Remove-Item"，保证**每条红卡都有说法**。

### 4.4 落库 `rule_id` 与命中模式（`app/agent_loop.py` / `security/runtime.py`）

`classify_tool` 把这些写进 metadata：

```python
"destructive_kinds":   ["delete.remove_item_recursive_force"],
"destructive_labels":  ["递归强制删除 Remove-Item -Recurse -Force"],
"destructive_summary": "递归强制删除 Remove-Item -Recurse -Force",
```

`_security_approval_spec` 把它们放进 spec，两处 `wait_tool_ui_approval_after_emit`（普通审批 + 自动审查覆盖）都写进 `metadata`，最终由 `human_interaction.create_approval` 落到 `approval_requested`。

卡片副标题由此变成：

> 拦截原因：递归强制删除 Remove-Item -Recurse -Force（Destructive command requires approval.）

`consequence` 也会以"命中规则：…"开头。自动审查模型（`security/reviewer.py::_intercept_reason_for_request`）用同一套标签，不再输出笼统的"破坏性命令"。

> 前端未改动：`subtitle` / `consequence` 是既有渲染字段，新文案直接生效。`human-interactions.js` 仍按 `approval_level === 'danger'` 决定红卡样式，未受影响。

### 4.5 附带的测试修正

`tests/test_agent_goal.py` 原断言 `/accounted_usage_ids`，而上一轮提交已改为更省空间的追加形式 `/accounted_usage_ids/-`。已改为前缀匹配。

### 4.6 删除与其它红线分离（2026-11-10，`app/security/policy.py`）

红色审批此前等于 `destructive and not workspace_delete`，也就是「工作区外的删除」一律红。
现在把**只删文件**从红色通道里拿出来：

```python
ordinary_deletion = deletion_only_destructive(request) and not deletion_hits_protected_target(request)
if destructive and not workspace_delete and not ordinary_deletion:
    red
```

- `deletion_only_destructive()`：`destructive_kinds` 全为 `delete.*`（含 `format`/`shutdown` 等即不满足）。
- `deletion_hits_protected_target()`：`deletion_targets` 命中磁盘根、家目录/家目录父级、
  `C:\Windows`、`Program Files*`、`ProgramData`、`/etc` 等系统树即保持红。
- `_delete_targets_text()`：只从**删除语句内部**取路径。同一条命令里删一个 flag 文件、
  又启动 `C:\Windows\System32\OpenSSH\ssh.exe` 时，后者不算删除目标。
- 删除不再生成 `rm:*` 前缀规则（`suggest_rule_pattern` 对 `deletion` 返回 `None`），
  避免降级后一次授权永久放行任意删除。

同批修复 `_POLICY_TAMPER` 误伤：只读命令提到 `app/security`、`permission_mode`
（如 `git status -- app/security/policy.py`、`grep -rn permission_mode app`）不再被判篡改；
写入、重定向、调用解释器仍为 `policy_change` → DENY。

### 5.4 判定标准（重点）

拿到 `audit_red_impact.py` 的输出后：

| 输出项 | 期望 | 不达标怎么办 |
|---|---|---|
| `不再是审批（误报）` | ≥ 0，逐条看样本是否都是"关键字出现在文本里" | 有遗漏 → 见 5.5 的清单 |
| `降级为黄色` | 工作区内的清理都应落在这里 | 为 0 且历史里明显有区内清理 → 说明新锚点未生效 |
| `仍为红色` | 逐条看 `--verbose` 明细 | **任何一条是"区内清缓存/删临时文件" → 未覆盖** |
| `命令无法解析` | 应为 0 | >0 说明有卡片被截断，需回原始日志补命令 |

`仍为红色` 的正确长相（2026-11-10 之后本机只剩 1 条：`Remove-Item -Recurse -Force C:\Windows\Temp\prereq_tree`，
目标落在 Windows 树内）。同窗口 96 条降级为普通审批，包括：

- 删 `C:\Users\...\AppData\Local\Temp\...`、`%LOCALAPPDATA%\electron-builder\Cache\...`
- 删 `D:\AI\AI Agent\_sugaragent-uninstall-test`（项目根之外）
- `taskkill msedge` 后删 Edge profile
- `Remove-Item -Force` 删单个文件（目标在工作区外）

若同一窗口仍红条数远大于「系统树/根目录」的直觉数量，先看 `--verbose` 明细里的目标路径，
再确认 `deletion_targets` 是否把无关路径（例如命令里启动的 exe）算成了删除目标。

### 5.5 已知未覆盖 / 边界（看到这些不必惊慌，但要记录）

| 情况 | 现状 | 说明 |
|---|---|---|
| here-string **写到文件**（未执行）里的 `shutil.rmtree` | 仍判为删除 | 保守选择：主体不剥离 |
| `python -c "…"` / `-Command "…"` 的内容 | 完全不剥离，其中的 `rm -rf` 等字面量算作删除 | 刻意保守（这段会被执行）。本机 11-09 的 4 条自检命令即因此被拦——**自测请写成脚本文件** |
| 目标路径当前已不存在 | `external` 判定会浮动 | 统计会 ±1 来回 |
| 一行里多语句用逗号/圆括号分隔 | 新锚点不覆盖 | 目前只认 `^ ; & \| \n {` |
| `cmd /c` 拼接、Base64 编码命令 | 不剥离也不展开 | 维持原有 `_DYNAMIC_RE` 路径 |
| 2026-08 前的记录 | 输出 `danger(inferred)` / `unknown` | 按 `security_rule_id` 推断 |

### 5.6 发现未覆盖时，把这三样发回来

1. `approval_id` 与 session id
2. 完整命令（用 2.3 的 `extract()` 还原，不要手抄）
3. `classify_tool` 回放出的 metadata 四个值：`destructive` / `deletion` / `workspace_delete` / `external_workspace`

有这三样就能定位是"锚点没覆盖"、"误报没剥离"，还是"确实该红"。
