## 39 · 子代理页右上角上下文读数

**触发路径**：`switchSession(child)` → `updateSessionTitle()`；之后任何会话列表变化（run 状态、未读、改名、其他会话活动）都会再次调用 `renderSessionListIfChanged → renderSessionTitleFromStore → updateSessionTitle`。活跃时几秒一次。

| 条件 | 优化前 | 优化后 |
|---|---|---|
| 打开子会话，且该会话有历史快照读数 | 打开瞬间可能画对，下一次列表刷新立刻变「— / —」 | 稳定显示 `~223.6k / 512k`、百分比与进度条 |
| 子会话处于寻址态、空闲（没有 SSE 事件） | 没有任何路径回填 → 永久「— / —」，hover 拆解卡打不开 | 每次重绘都按子会话缓存重画；有读数即显示，hover 卡可用 |
| 子会话从未跑过/快照无读数 | 永久「— / —」 | 仍是「— / —」，但打开后补取一次 `/context_tokens`；拿到值即显示 |
| 同一个无读数子会话被反复重绘 | —（本来就不请求） | 只补取一次（每会话一个标记），不会变成后台轮询 |
| 子会话运行中（有 `context_tokens` SSE） | SSE 事件会刷新读数 | 不变；与缓存重绘叠加，结果一致 |
| 普通（非子代理）会话 | 正常 | 不变 |

实现：`frontend/src/app/modules/message-rendering.js`
- `updateSessionTitle()` 寻址分支：`applyContextTokenLabelForCurrentSession()` 取代 `setContextTokenLabel(null, null)`；无值时 `scheduleContextTokensAfterPaint()` 仅一次。
- `session-scroll-history.js`：`setContextTokenLabel` 在无值时仍会自行退化为空值，所以「有就画、没有就空」不会互相打架。

## 40 · 后台子代理完成后的主会话续跑

**判定核心**：结果行 `parent_run_id` 指向的父 run 是否还活着（`session_lifecycle.is_run_active(sid, run_id)`）。
- 活着 → 交给该 run 在下一次 ReAct 迭代按 run-id `claim`（不提前改锚点，避免重复投递）。
- 已死（正常结束/取消/异常/进程重启）→ 视为「晚到结果」，锚到当前最后一条 final，并可唤醒父会话。

| 条件 | 优化前 | 优化后 |
|---|---|---|
| 子代理在父 run 运行中完成 | 父 run 下一轮 claim 并注入 | 不变（owner run live → 不动锚点） |
| 子代理在父 run **正常结束之后**才完成 | 行无 `after_final_index`；旧代码用投影 final 的 `run_id` 比对，而投影 final 不带 run_id → `finished_runs` 恒空 → 永远不可续跑 | 归属 run 已死 → 锚到当前 final → 监视器扫描（≤30s）或 run 结束延迟 1s 唤醒 → 注入「[后台 Subagent 已完成]」 |
| 父 run 被**取消**（用户点停止）时结果尚未投递 | 取消路径跳过 SessionEnd 钩子 → 不锚定 → 永远 pending | `_finalize_agent_run_lifecycle` 的 finally 里补锚定；有 pending 则延迟 1s 唤醒 |
| 父 run **失败**（模型/网络错误）时结果尚未投递 | 同上（失败路径不锚定） | 同上；失败 run 若没有 final，则等下一轮结束后再锚（见下一行） |
| 结果锚在**早先一轮**（用户已发新消息） | `anchor < last_idx` 直接跳过 → 结果丢失 | 归属 run 已死 → 重新锚到当前 final 并续跑（结果不再丢） |
| 锚点指向**更晚的一轮**（历史被裁剪/回滚过） | 不可达 | 仍跳过，避免把旧结果倒灌进当前轮 |
| 进程重启后残留 pending 行 | 进程内任务表为空也照样跳过 → 永久 pending | `is_run_active` 为假 → 视为晚到 → 启动扫描后 30s 内续跑 |
| 结果被显式 `collect`/清理 | 删除行 | 不变 |

**实际发生过的例子**（会话 `49128182-38a9-4171-ac2f-1656548c73d1`）：父 run `888e6047` 于 2026-10-29 06:37:01 结束，子代理 `ab724835` 06:56:07 才完成 → 优化前 `delivery_state: pending` 挂了 9 天，监控每 30s 对 4.9 MB 会话做一次约 215 ms 的投影空转。优化后重启即被消费：`pending_results.json` 变 `[]`，事件流出现 `[后台 Subagent 已完成] …`（seq 2745）并发起续跑。

**时序**：结果落盘 → `notify_pending` 入队 → 0.5s 节拍的 runner 尝试 `_continue` → `prepare_pending_subagent_continuation` 判断/锚定 → 提交 `session.continue` → 注入并 `consumed` 删行。run 刚结束时会晚 1s 再唤醒（此时 `is_run_active` 才会变假）；另有 30s 兜底扫描，所以应用当时没开着也不会丢，下次启动后补投。

**权衡**：为保证「不丢」，晚到结果可能被注入到「之后某一轮」的末尾（只发生一次，注入后即消费）；若锚点已指向更晚的一轮（历史被裁剪），则不注入，避免语义错乱。

## 41 · 改写/删除消息触发历史截断

**客户端**：`truncateSessionOnServer` 先 POST（带 `request_id` 收据）→ 202 受理 → 轮询 `/truncate/status`（上限 180s）。
**服务端**：受理前做 run 栅栏 → `_truncate_session_events_once` 里再校验一次 → 取锁（60s 超时）→ 解析边界 → 写 `visible_range_changed`。

| 条件 | 优化前 | 优化后 |
|---|---|---|
| 空闲、边界可见（正常改写） | 成功 | 成功（多了一次几乎零成本的栅栏检查） |
| 旧 run 还在跑（点了停止后立刻发送） | 直接截断；与旧 run 的写入并发 → 事务忙/半行/边界漂移，偶发 400；旧 run 之后的 final 还会重新出现在 UI | 受理前回 409 `run_active` + `retry_after_ms`；客户端在 20s 内按 1.2~3s 间隔自动重试，run 停下后成功；超过 20s 提示「请先停止当前任务」 |
| run 在栅栏检查之后、截断之前启动 | — | 内层栅栏再判一次；仍被拒绝则返回同一个 `run_active` |
| 第一次截断已落盘，但响应丢失/客户端超时后重试 | 目标 seq 已被隐藏 → `resolve_truncate_boundary` 返回 `None` → 400 `truncation failed` → **永久失败直到刷新** | `already_applied`（有裁剪操作且 `visible_max < target ≤ log_max`）→ 直接成功，幂等 no-op |
| 事实已落盘，快照写入失败（Windows 文件锁/权限等） | 异常被吞成 debug 日志 → 返回 False → 400；重试进入上一行的永久失败 | 抛 `HistoryWriteCommittedError` → 上层按「已提交」返回成功（快照下次读取时按事件流重建），并记 warning |
| 另一个历史操作（裁剪/分支/迁移）持锁 | 无上限 `threading.Lock` → 请求可能挂很久 | 60s 超时 → 503 `history_op_busy`（前端提示稍后重试），实际通常远小于此 |
| 仍有待答的 `ask_user` | 409 `pending human interaction` | 不变 |
| 目标 seq 不存在、且从未发生裁剪（脏请求/错索引） | 400 `truncation failed` | 仍是 400（不会误判成「已生效」） |
| 同一目标重复点击（同一 `request_id`） | 复用同一收据，不重复提交 | 不变；新增：`run_active`/`history_op_busy` 会重置收据，稍后可重新发起 |
| 分支 `/branch` | 不检查 run（只读源会话，允许运行中分支） | 不变；仅新增锁超时 → 503 |
| 失败提示 | 常见无原因的「无法同步服务器，改写未生效。」 | 按错误码分别提示：运行中/服务端忙/结果待确认/未知；中英文都有 |

**关键取舍**：`/truncate` 现在会拒绝「还有 run 在跑」的历史改写。删除消息同理——以前可能删到一半被旧 run 写回来，现在会等或提示先停止。

## 42 · 分支会话的工作目录

**触发**：`POST /sessions/{id}/branch` → 复制源会话 `metadata.json` → 追加索引行 → 返回 `session` 摘要；前端 `sessionStore` 更新并打开分支。

| 条件 | 优化前 | 优化后 |
|---|---|---|
| 源会话有非默认工作目录 | `metadata.work_dir` 继承正确；但索引行没有 `work_dir` → `GET /sessions/{id}` 与分支响应的 `session` 投影成**默认目录**；前端 upsert 后标题栏/侧栏分组也显示默认 | 索引行写入 `work_dir`；分支响应、`/sessions/{id}`、侧栏分组立即正确（`work_dir_is_default=false`） |
| `/branch` 之后立刻刷新侧栏 | 路由不失效 `/sessions/state` 缓存，`/sessions/changes` 不推 revision → 可能长时间保持错误 | 路由成功后立即失效缓存，下一拍即重建 |
| 分支创建时有旧列表快照在途 | 快照到达可能覆盖/剔除新分支行 | 前端 `protectFromSnapshots` 保护到服务器快照包含它为止，随后 `loadSessions({force:true})` |
| 源会话用默认目录 | 显示默认目录 | 不变 |
| 源会话带运行态残留（`active_run_id`、`interrupt_requested`、`run_start_order*`、`subagent_ids`、`unread_result*`、`truncate_backups`、`llm_compress_prefix_backups`、`draft`、`auto_archived*`、恢复标记等） | 整份复制到分支：分支像「还在跑」、带着源会话的子代理与未读结果 | 这些字段在创建时被清掉；只继承 `work_dir`、`authorized_dirs`、`model_profile_id`、`prompt_language`、`system_context*`、`session_runtime_config` 等配置类字段 |
| 已经存在的老分支（索引行缺 `work_dir`） | 一直显示默认目录，直到某次 `list_sessions` 重写索引 | `get_session_summary` 发现缺失时回读一次 metadata 补齐（每会话每进程一次），并写回内存索引 |
| 源会话 `authorized_dirs` 为空 | 回退成 `session_work_root(meta)`（继承目录） | 不变，且该目录一定覆盖 `work_dir` |

**字段继承清单**：保留 `name(重命名) / work_dir / authorized_dirs / model_profile_id / prompt_language / system_context / system_context_mode / session_runtime_config / runtime_config_revision / model_switch_history / reasoning_effort`；清空上面「运行态残留」一栏列出的 23 个键（见 `_BRANCH_DROPPED_METADATA_KEYS`）。

## 已知边界

1. **续跑依赖后端进程在跑**：结果落盘时会立即尝试唤醒；进程不在时保留 pending，下次启动的首次扫描（≤30s）补投。
2. **晚到结果最多注入一次到之后的某一轮**：这是「不丢」的代价；若用户已经裁剪掉相关历史，宁可跳过也不倒灌。
3. **截断 run 栅栏会让你多等一会儿**：正在运行的会话删除/改写消息，会先等旧 run 停下（最多 20s 自动重试），而不是像以前那样硬来。
4. **分支不再复制运行态**：如果之前依赖「分支继承父会话的 unread/子代理列表」，现在不会了——这是有意的修正。
5. 会话 `49128182` 的续跑本身因模型端点连接失败（`gpt-6.1-sol` / `gpt-6-luna` `APIConnectionError`）而失败，属环境问题；结果已写入模型上下文，不会重复投递。
