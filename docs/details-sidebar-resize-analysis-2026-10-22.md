# 右侧详情栏宽度拖拽与宽窄切换问题定位

后续状态：本文保留修复前的诊断数据；问题现已修复，当前回归用例为 `tests/test_details_resize_browser.py`，变更见 [修复记录](CHANGELOG-2026-10-22-详情栏拖拽与附件追问.md)。

日期：2026-10-22。基于当前工作树源码，仅分析与复现，未修改业务代码或构建产物。

结论：主要问题集中在 `frontend/src/app/modules/dock/embedder/right-column.js` 与 `frontend/src/styles/dock.css`。已经用真实 Dock 模块、真实 iframe 和浏览器鼠标事件复现：拖动边界滞后、连续拖拽跳宽、跨 iframe 丢失松手事件，以及宽窄窗口切换后聊天区被挤没。

## 1. 拖拽仍执行收展动画，内容边界与拖拽条分离

位置：

- `dock.css:366`：外层 `.dock-rightbar` 始终执行 `width 300ms` 过渡。
- `dock.css:379`：内部 `.dock-surface` 直接使用目标宽度，没有对应的宽度过渡。
- `right-column.js:576`：拖拽直接更新 CSS 宽度变量，没有进入禁用动画的拖拽状态。
- `right-column.js:580`：下一次拖拽从外层当前动画宽度读取起始值。

复现：窗口宽 1440px，详情栏初始 460px。将左边缘向左拖 160px。

实际结果：状态与内容宽度立即变为 620px，外层轨道仍约 460px，然后用 300ms 追上。拖拽条位于外层左边缘，所以会与内容左边缘相差近 160px。向左扩展时内容覆盖聊天区，向右收窄时则可能出现轨道占位与内容不一致的空隙。

如果第一轮拖拽结束后马上再次抓住拖拽条，起始宽度取到的是动画中间值，而不是刚保存的目标值。实测第一轮为 620px，第二轮仅移动 1px，目标却变成 462px；具体中间值随帧时序变化。

对照：只在诊断页面临时设置 `.dock-rightbar { transition: none !important; }`，同样拖动后外层、内容、拖拽条立即对齐为 620px。

建议：收起/展开保留动画；拖拽期间关闭外层宽度过渡，并在开始拖拽时统一起始宽度。已有 `.is-instant` 样式只用于全屏按钮，当前拖拽没有使用它。补上拖拽状态时，需要避免松手恢复动画再次产生宽度追赶。

## 2. 未捕获指针，跨 iframe 后丢事件，松手后仍能继续拖宽

位置：`right-column.js:576–592`。

当前只在父窗口注册 `pointermove` / `pointerup`，未调用 `setPointerCapture`。鼠标进入 iframe 后，事件在 iframe 内分发，父窗口收不到。

复现：打开一个插件页面，在详情栏左边缘按下鼠标，向右移动 130px，进入插件 iframe，在 iframe 内松手，再移回聊天区。

实测：

- 进入 iframe 后详情栏仍是 460px，父窗口没有收到这次移动。
- iframe 收到了 `pointermove` 和 `pointerup`，父窗口没有收到 `pointerup`，因此拖拽监听没有移除，宽度也没有持久化。
- 鼠标移回聊天区时，事件的 `buttons` 已是 `0`，残留的移动监听仍将宽度改为 540px。

这对应“向右拖不动”“松手后还粘着拖”“之后宽度莫名变化”等现象。复现使用同源 iframe，跨域不是前提。桌面 Electron webview 的独立 guest 输入行为未在本次验证中覆盖。

对照：只在诊断页面给 sash 的 `pointerdown` 加上 `setPointerCapture(event.pointerId)`，同样操作能将宽度缩至 330px，正常接收到松手并保存；松手后移回聊天区，宽度仍保持 330px。

同一函数还缺少取消与中断清理：没有 `pointercancel`、`lostpointercapture`、窗口失焦处理，没有按 `pointerId` 过滤，也没有单一活动手势保护。向页面注入 `pointercancel` 后，继续移动仍会改变宽度，已经验证取消路径没有清理。

建议：复用 `renderer/gesture.js:33` 的 `dockFollowPointer` / `dockCreateGestureController`，使外层宽度拖拽与内部 Dock 分隔线使用相同的指针捕获、单指针过滤和取消清理机制；同时明确窗口失焦、收起、模式切换时的结束规则。已有 `dockRightState.dragging` 字段未被这条拖拽链路使用。

## 3. 拖拽、窗口缩放和模式恢复使用不同的宽度约束

位置：

- `right-column.js:564`：`dockRightClampWidth` 只限制在 320px 至 `min(960px, 72vw)`。
- `right-column.js:529`：`dockRightWouldCrushWorkspace` 扣除左侧会话栏后，要求聊天区至少 560px。
- `right-column.js:427`：只有窗口正在变窄、窗口宽至少 768px、且当前不是全屏时，才执行聊天区保护并收起详情栏。
- `right-column.js:551`：模式只按窗口宽是否小于 768px 切换；没有重新夹取宽度。

因此有两条独立的绕过路径：

1. **直接拖宽绕过聊天区保护。** 在 1440px 窗口、左侧栏 220px 时，将详情栏拖到 940px，聊天区仅剩 280px。拖拽并未调用 560px 最小空间检查。
2. **窄屏恢复绕过限制。** 在 1440px 窗口保存详情栏宽 900px，再将窗口变为 760px，详情栏进入全屏。随后将窗口扩大到 1000px，详情栏恢复 push 模式，但仍保留 900px。此时按现有 clamp 本应最多 720px；因为窗口在变宽，自动收起检查也不会执行。实测聊天区宽度为 0px，右栏还有部分内容超出可视区。

首次从存储加载时执行一次 clamp，无法保证后续窗口、左侧栏或模式变化后的宽度仍有效。

建议：统一计算 push 模式实际可用空间，在拖拽、恢复宽度、重新展开、窗口尺寸变化及退出全屏等入口应用相同约束。用户偏好宽度与当前可显示宽度应分开保存。若当前窗口无法同时满足详情栏最小宽度和聊天区最小宽度，采用现有收起策略或统一的全屏策略，不应继续挤压聊天区。

## 4. 附带发现：手动全屏也会被普通 resize 撤销

`right-column.js:551` 没有区分用户主动全屏与窄屏自动全屏。手动点全屏后，只要发生一次 resize 且窗口宽度仍至少 768px，就会切回 push。实测将窗口从 1440px 调到 1438px 即退出全屏。

这是当前代码注释明确描述的策略，应与产品预期核对；本报告将其列为相关行为，不把它与前述已确认的拖拽缺陷混为一项。若要保留手动全屏，应单独记录进入全屏的原因。
