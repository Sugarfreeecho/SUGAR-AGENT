## 2. 候选与优先级

### P1：glob 遍历

- 当前 `app/agent_tools.py:3888` 的文件系统回退先把全部匹配收集为列表，再排除 TempOutput，再截断返回。递归过程中没有提前剪掉 TempOutput 子树。Windows 索引只支持部分模式，且索引缺失/空结果仍回退遍历。
- 明确慢例：会话 `4bc203cb-adb5-4a8e-8ada-c9f299c3e7c6`，run `7a73ba1d-1d38-4c47-af45-715dd10063fb`，iter 13，2026-10-22 23:47:24–37。查询 `**/.config/plugins*.json`，根为仓库 workspace，结果为 `No matching files found`，调用计时 12,378ms；事实 seq 29626/29627/29630 可核对参数与结果。
- 方向：优化目录遍历与固定路径段匹配，在进入目录前剪除当前语义已排除的 TempOutput；对大量命中支持有界枚举。需要保留隐藏文件、链接、模式匹配和敏感路径过滤语义。
- 对无匹配样本，仅提前截断结果不会加速；必须改善遍历。若改为有界枚举，不能继续声称知道精确省略数量。
- 判断：实际慢例和扫描结构已确认；可消除多少时间尚需分段基准。

### P1：history_context 搜索与引用读取

- `app/history_context.py:326` 的 global 搜索每次递归发现会话日志并排序；`:402` 逐个扫描归档和事件 JSONL。已有原文预筛，不能误称每行都必然 JSON 解码。
- `:460` 按 seq 读单条事实仍从日志头查找；归档分页每次先拼好完整文本再切片。
- 近 48 小时两个 global 搜索样本的工具包络为 217,570ms 和 164,131ms，分别来自会话 cd4fa1af / 5e3b06a8。参数已通过 model_assistant 事实核对。这是跨版本历史样本，未证明全部耗时发生在扫描函数内部。
- 方向：提前维护可重建的搜索文档/会话清单索引；引用读取复用现有 seq 定位机制；归档缓存按来源身份失效。搜索索引允许后台维护，但当前事实后缀必须补查，并保留原有匹配、去重、顺序和可恢复引用。
- 判断：源码中的重复扫描已确认；收益优先在大规模 global 查询验证。

### P1：update_todo / Goal 工具的同步状态提交

- `plugins/session-todo/host.py:23` 和 `plugins/agent-goal/host.py:12` 在 async handler 内直接调用同步状态读写。发生锁或磁盘等待时，会阻塞承载它们的事件循环；这不意味着所有工具都串行执行。
- `app/runtime_v2/extension_state.py:251` 的 set_latest 先 get，再 compare_and_set；正常无冲突情况也有两个事务入口和两次来源准备。
- Goal 的读取已经使用 read_consistent_view，并仅复制 Goal 行；不应再把“整个快照深复制”列为未修复原因。
- 方向：沿用现有取消安全的 fact-commit worker，把磁盘工作移出事件循环并等待事实提交成功；研究原子写入口，合并重复事务/来源检查。不得取消并发冲突、所有权、来源身份或恢复保障；Todo 内存更新/失败回滚顺序也必须保持一致。
- 判断：阻塞代码路径已确认，单次节省量尚未测量；主要收益可能是其他并发任务的响应性。

### P2：read_file 分段读取

- `app/agent_tools.py:3077` 首次范围读取为了准确总行数会读到 EOF。总行数缓存命中后虽能在范围结束时停止，仍从文件头读取；连续读取靠后的片段会反复经过前缀。
- 新日志 63 个调用中位数 23ms，P95 2,105ms。不能据此把全部尾部耗时归到数行操作，尚缺函数叶子计时。
- 方向：可失效的稀疏字节偏移索引、复用行数统计、在文件产生或空闲时预建索引。必须保留当前 1,000 字符虚拟行、UTF-8 替换、范围输出及来源变化检查。若要更改精确总行数显示，则属于另一个产品语义决定。
- 判断：重复前缀读取已确认；小文件本来很快，主要验证大文件连续分段读取。

### P2：写工具和 run_shell 的 change-review

- `plugins/change-review/store.py:697` 仍执行 Git inventory；`:886` 检查完整 inventory 的文件签名。声明式写入批次合并已存在，不应重复把“加批次合并”列为新改进。
- 复核窗口 batch_flush 123 次，总 2,564.6ms，均值约 20.9ms；最慢 282.159ms，其中 inventory 163.199ms。before/apply_patch 最大 201.35ms，其中 index_write 103.201ms。说明要同时关注 inventory 与索引保存，不能只看签名循环。
- 方向：先定位重复 index 保存，再评估安全失效的 inventory 缓存或增量目录变更维护。根目录 mtime 不足以覆盖 Git index、ignore、深层目录增删等变化；mtime-only 文件内容快筛也不安全。
- 判断：可优化，但近期数据不支持把它描述成普遍数秒瓶颈。并行签名开关已存在，不能承诺盲目开 8 线程就更快。

### P3：job_output 的无变化持久化

- `app/execution_services/jobs.py:362` 已用有界内存输出缓冲和游标，恢复也只读磁盘尾部。不是每次读取整个输出文件。
- 默认消费读取即使没有新输出，仍执行 _persist_job；offset 显式读取则不更新消费游标。
- 方向：仅在游标、待交付结果、通知状态等真正改变时写入，减少空轮询产生的事务。不能延后实际消费确认以损坏重启后恢复语义。
- 判断：优化路径明确，调用量和潜在收益低于前三项。wait=true 的等待本身必须从性能口径排除。

## 3. 当前不优先的项目

- grep：已有 ripgrep 快路径、达到结果上限提前停止和超时处理；复核样本 P50 52ms、P95 338ms。先处理具体慢例，再决定是否继续投入。
- ls：默认已关闭逐文件行数统计；当前 4 个调用只有 38–56ms，样本较少。
- run_shell：调用计时包含命令自身运行，应分开测启动、输出交付、退出收尾和 review，不能把整个命令时长称作可省开销。
- browser_evaluate / MCP：现有聚合记录不能区分 JS 内主动等待、页面实际工作、服务调用与宿主排队，不据总时长认定实现低效。

建议实施顺序：glob → 状态工具同步提交隔离 → history_context 索引/定位 → read_file → change-review 剩余重复工作 → job_output 空写消除。每项先冻结来源和计时口径，再报告测得收益。
