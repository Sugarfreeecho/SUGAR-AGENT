# 长会话性能验证与优化方案

日期：2026-10-14（Asia/Shanghai）。初次分析基线：`ead39b7`。分析阶段没有修改生产运行逻辑、前端构建或真实会话；新增可复跑的诊断脚本和本报告。

同日后续：已按用户要求完成第一项执行行查找优化，正式改动与复测见 [优化记录](execution-row-index-2026-10-14.md)。下文保留优化前的分析证据。

**结论部分成立：长历史确实会放大流式渲染开销，长模型输入也与轮间等待增长明显相关。当前构建中已复现一个具体的滚动停帧入口，并做了改善它的隔离对照。但不能把这些证据推广为“所有工具本身都会随着轮数变慢”，也尚未证明这个入口解释全部实际卡顿。**

数据见 [long-session-2026-10-14.json](long-session-2026-10-14.json)，脚本见 [benchmark_long_session.py](../../scripts/performance/benchmark_long_session.py)。

## 1. 当前构建的受控验证

前端源码与 `app/templates/dist` 的同步检查通过。实际测试主脚本为 `/assets/main-D7ns97ey.js`，SHA256 为 `72b37e11bc220930cdf2e45ab5cca49edd3aafbfbb4067589feb2302ab5264f3`。

使用 Edge 的隔离无头浏览器，1280×800、DPR 1、浅色主题、16px 字号，原版丝滑输出开启。所有浏览器请求都由测试路由返回本地资源或固定数据，不连接生产 API，不调用模型或执行工具。历史每轮 20 条执行记录，每条 720 字符；当前输出的初始正文及新增 1200 字符在各组一致，界面上的上下文数值保持一致。

### 1.1 缓存 SSE 批量到达：复现停帧

将同样的 150 条 `execution_update` 放进一个 SSE 数据块，交给当前原版 `consumeAgentSseResponseInner()` 消费。每种配置重复三次，第二遍反转顺序，以减少固定测试顺序的影响。

下表是三次结果的中位数。“最长帧间隔”指各次 RAF 最长回调间隔的中位数，不是屏幕实际 FPS。

| 条件 | 页面元素数 | 整批处理耗时 | 最长 RAF 间隔 | 每次超过 50ms 的间隔数 |
|---|---:|---:|---:|---:|
| 1 轮历史，21 条执行行 | 188 | 16.1ms | 16.8ms | 0 |
| 50 轮历史，1001 条执行行 | 8077 | 70.0ms | 82.3ms | 1 |
| 保留 50 轮 DOM，仅直接查找正在更新的执行行 | 8077 | 15.3ms | 32.8ms | 0 |
| 50 轮数据，仅保留最后两轮历史与当前轮 DOM | 349 | 16.8ms | 16.7ms | 0 |
| 保留 50 轮 DOM，SSE 每约 4ms 让出一次任务 | 8077 | 449.8ms | 33.0ms | 0 |

长历史基线三次均产生长任务，最长 RAF 间隔分别约 115.2 / 82.3 / 82.2ms。静态页面的帧间隔主要在 16.7ms 左右。

直接查找对照只绕过 `renderExecutionRecord()` 更新一个已知执行行时的全量选择器扫描，不移除历史 DOM、不改滚动曲线。第二组实验整批处理时间下降约 **78%**，所有组的最终完整文字校验通过。这是一个具体入口的因果证据，尚不是已经交付的生产修复：诊断只涉及一个正在生成的文本行，生产索引还需要处理历史补页、会话切换、分组移动、删除和重连。

单独让出任务能消除这组长任务，却增加约 6 倍整批处理耗时；不能直接把这个诊断写法作为最终方案。应先减少每个事件的工作量，并合并同一帧中重复的展示刷新，再对剩余解析/状态处理设置任务预算。

### 1.2 均匀到达：开销增加，但不必然产生明显停顿

另测 150 次新增，每次 8 字符、间隔 30ms，中间两次暂停 300ms，每组重复三次。

| 历史规模 | 单次记录渲染中位数 | 单次渲染 P95 的跨试验中位数 |
|---|---:|---:|
| 1 轮 / 21 行 | 0.3ms | 0.4ms |
| 10 轮 / 201 行 | 0.4ms | 0.6ms |
| 50 轮 / 1001 行 | 0.9ms | 1.8ms |
| 50 轮，仅直接查找当前行 | 0.3ms | 0.5ms |
| 50 轮，限制历史 DOM | 0.3ms | 0.4ms |

该组大部分样本没有超过 50ms 的帧间隔，部分长历史样本的 RAF P95 达到约 33ms。主机负载会波动，不能将所有帧波动归因于执行行扫描。直接查找也没有消除一个高负载样本中的全部慢帧。

由此可见：**历史规模增加的是工作量；连续主线程占用、批量事件、布局读写和系统负载共同决定是否形成可见停顿。** “轮数达到某个值就必然卡”不成立。

这一组没有真实文件改动记录或媒体，虽然正常加载了 change-review 插件，但不能据此排除实际改动审查路径。历史正文主要处于折叠状态，没有覆盖展开的大过程框、很长的当前输出、多子代理、图片/视频及桌面 WebView 合成器。

## 2. 轮间延迟与工具耗时

读取仓库 `logs/*.log` 中从 2026-10-11 起的日志，只接受有日期、日志级别和 `agent_harness` 来源的指标行，排除正文中的相似文本，按完整行去重。共 29,112 条指标，包含 2,030 次 `pre_api_timing`；模型为 `deepseek-v4.1-flash` 的有 1,910 次，`deepseek-flash` 的有 120 次。

按最近一次同会话请求准备记录的 `estimated_tokens` 分组。下表是观测相关性，未固定命令、供应商负载、缓存命中率和并发，不能视作严格的模型性能实验。

| 输入 token 估算 | 请求准备样本数 | 本地请求准备中位数 / P95 | LLM 调用首字等待中位数 | 工具结束到下一轮首字中位数 |
|---|---:|---:|---:|---:|
| <20k | 72 | 277 / 5425ms | 1647ms | 2808ms |
| 20–80k | 342 | 293.5 / 3001ms | 2180ms | 3123.5ms |
| 80–160k | 509 | 509 / 3480ms | 3924ms | 4964ms |
| ≥160k | 1107 | 509 / 2824ms | 7332ms | 8313ms |

首字等待使用 worker 的 `first_delta`，包含请求发送、网络和服务端等待，不能直接等同于服务端 prefill。不同列并非同一组完整配对请求，不应把中位数相加减进行耗时归因。若模型先输出思考，这里记录的是首个增量，不是最终回答的首字。

同会话对照也有支持：六个同时具备足够低/高输入样本的会话中，五个的本地请求准备中位数在高输入组增加，例如 `b25fdd57…` 从 186ms 增至 405ms，`bcae3807…` 从 142ms 增至 580ms；另一个会话从 300ms 降至 166ms。因此增长是常见趋势，并非严格单调规律。

本地消费还存在明显尾延迟：worker 完成到本地消费完成的中位数约 1.38s，P95 约 29.1s。这个条件统计排除了 ≥120s 样本；原始统计和排除数量仍保留。排除值可能涉及睡眠、暂停、极端负载或实际长等待，不能统一解释成某一种原因。该指标需要继续分解，不能直接归因于 JSON 写盘。

### 工具本身是否越用越慢？

现有数据**不支持普遍单调变慢**。`read_file` 在 <20k 和 ≥160k 输入组的调用中位数分别为 146.5ms / 25.5ms，`grep` 为 249ms / 119ms；高输入组并未普遍更慢。不同组读取的文件、命令和磁盘缓存不同，这些数字也不能证明工具变快。

工具存在长尾：全样本 `read_file` 中位数 56ms / P95 1736ms，`grep` 197ms / P95 3370ms，`run_shell` 4928ms / P95 44093ms。`invoke_ms` 的范围还包括工作区写锁和原生文件工具前后的改动审查处理，并不是纯文件 I/O 或纯命令进程时间。工具调用变慢的具体实例，必须比较同一命令和输入，再拆锁、审查、排队和真实执行。

此外，记录中的 `tool_result_post_timing` 多数非常短，中位数 0ms、P95 5ms；不能据此把全部轮间等待归因于工具结果的后处理。

## 3. 当前代码中的原因与边界

| 路径 | 当前行为 | 证据强度 |
|---|---|---|
| `message-rendering.js:1464–1474` | 每次 `renderExecutionRecord()` 都在整个 `ctx.stream` 查询全部执行行，再找目标；重复序号检查也在扫描之后 | 已通过当前构建的隔离对照确认增长及批量事件下的停帧影响 |
| `sse-handling.js:418–510` | 一个读取块内逐条消费全部 SSE；`execution_update` 分支逐条渲染并直接 `continue` | 本次复现的放大条件；缓存块会连续占用主线程 |
| `session-scroll-history.js:980–1011` | 缓存按 6 个会话限制，没有按 DOM 节点/字节预算限制单个会话；历史分页每页 5 轮，但持续追加或补页后没有对应的总规模上限 | 代码确认；限制历史 DOM 的对照有效，实际内存泄漏未证明 |
| `change-review.js:283–327` | 滚动安排 RAF，遍历改动聚合并读取布局；`scanExisting()` 仍可扫描工具行 | 次要候选；本次无真实改动负载，不能作唯一根因判断 |
| `agent_tokenizer.py:346–354,395–420` | 已有 token/文本前缀缓存，但全局前缀窗口较小，前缀比较仍遍历消息；失配后可能重新编码全文 | 代码确认；冷/热差异实测，但日常日志多为较快命中，不应优先推翻现有缓存 |
| `execution_journal.py:315–330` | 工具记录的一些回退查找构造全部记录的列表并反向扫描 | 随记录数量增长的候选，尚未量化它在真实慢工具中的占比 |
| `recovery_checkpoint.py:153–166` | 后台检查点在 journal 锁内冻结完整状态，然后锁外哈希/编码/写盘 | 可能形成锁等待；不是每个 token 同步写完整快照，需进一步分段计时 |
| `projector.py:163–227` | 增量投影已采用写时复制和增量消息投影，仍浅拷贝若干全量列表/字典 | 有线性开销，但本次 20→5000 行时中位数约 0.15→0.66ms，不足以独立解释秒级延迟 |

不要重复已经做过的优化：Runtime V2 已有增量投影、异步合并检查点；流式 bridge 已合并相邻同类增量；文本释放已有 RAF；流式正文使用文本展示，不能按“每 token 重跑完整 Markdown”来诊断这个仓库。

token 冷/热测量说明了缓存的重要性：30万字符的本地完整计数中位数约 3.0s，而相同对象的缓存命中约 0.14ms、追加小段约 3.66ms。该组运行期间观察到高 CPU 压力，使用了重复合成文本，绝对时间不代表空闲机器的日常请求；它证明的是缓存失配的成本可能随历史长度放大。正常日志中 ≥160k 输入的 `token_estimate` 中位数只有 35ms，应先定位失配和长尾，再决定缓存改造。

仓库此前的 [现场排查](../流式自动上滚卡顿-反馈与排查结论-2026-10-09.md) 已记录改动审查滚动回调的强制布局、主线程长任务及后端等待；这些是历史构建证据。本次没有用它们替代当前构建测试，也不把本次单一入口的改善称为全部问题解决。

## 4. 优化顺序

| 优先级 | 具体改动 | 收益、成本与验收 |
|---|---|---|
| P0 | 给渲染上下文维护 `execution_id → DOM行` 索引；新增、恢复、移动、删除时同步索引；以行是否仍属于该 stream 校验有效性 | 成本较小。本次固定流的诊断将整批耗时降低约 78%。目标：查找不随已加载历史行数增长，重复事件无需扫描整个会话 |
| P0 | SSE 先更新数据，再把同一执行行的文字展示更新合并为每帧一次；审批、终态、错误和历史边界保持有序处理；剩余循环使用 4–8ms 预算 | 成本中等。消除连续批量渲染；避免单纯大量 `setTimeout` 引入本次 70→450ms 的吞吐退化。验收完整文本、顺序、终态与停止/重连行为 |
| P1 | 为持续追加和历史补页增加 DOM 总预算；较早过程框仅保留摘要/高度占位，用户查看时再加载；很长的单个过程框也按执行行设窗口；会话缓存按节点/估算字节与数量共同约束 | 成本中等到较大。试验限制 DOM 后恢复短历史的开销。可先以 200–400 行作为测量起点，最终阈值根据实际正文/媒体定；保留滚动锚点和完整持久记录 |
| P1 | 为模型输入设置独立的软工作预算，按任务选择例如 32–64k 或 128k；旧工具结果按引用按需取回，稳定摘要保留需求、约束、决策与证据，完整原始历史继续留档 | 成本中等，涉及任务质量。当前已有压缩机制，应扩展预算策略而非另造一套；也不要把模型声明的硬上下文窗口直接改小。用滞回和稳定摘要避免每轮压缩、破坏前缀复用 |
| P1 | 给工具调用和 stream delivery 补齐分段指标：线程池排队、journal 锁、记录更新、检查点冻结、文件锁、前后审查、真实工具执行；按 session/run/react_iter 对齐 | 成本较小。先解释 1.38s 中位数和 29.1s 消费 P95；证明占比后再决定是否拆专用持久化线程池、批处理或优化检查点冻结 |
| P2 | 对已确认的后端热点缩小活动工作集：按 run/tool_call 建索引、按会话/模型版本保存前缀计数、减少无关事件对全量容器的复制；插件滚动查询缓存与布局读写分阶段 | 成本中等。保留跨进程一致性、重写/压缩后的失效规则和恢复能力；不以牺牲审计或丢事件换取速度 |

对于屏幕外的独立历史区域，可以评估 `content-visibility: auto` 与尺寸占位，减少布局/绘制工作，但它不会消除 JavaScript 的全量选择器扫描，也不能替代 DOM 预算。依据 [MDN 的属性说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/content-visibility) 和 [Chrome 的布局性能说明](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)，应避免在反复改 DOM 后马上读取全页几何；这些属于一般设计依据，不是本仓库根因的额外证据。

不优先调整弹簧参数、字速、字体或禁用所有动画；本次直接查找对照没有更改这些参数便消除了这组长任务。也不建议先重写工具执行器或单纯提高并发。

## 5. 上线前验收

1. 固定新增文本、事件节奏、工具命令和系统负载，分别改变模型输入量与已加载 DOM 规模，避免把两个变量混成“轮次”。覆盖均匀、小批量、缓存批量和启停。
2. 流式路径在 50/1000/5000 条已加载执行行下测量，比较逐帧间隔、Long Task/Long Animation Frame、强制布局与文字位置；在实际前台浏览器及桌面 WebView 复测，至少五遍。RAF 指标不代替画面验证。
3. 可采用初始目标：流式渲染/滚动工作 P95 <4ms，解析/状态处理连续任务 <8ms，受控回放不因该路径产生 >50ms 长任务；这些是验收目标，当前未宣称全面达到。
4. 同一个只读文件、同一个搜索范围、同一个固定命令在不同历史规模下复测。区分真实执行、锁等待、审查和下一轮首字；工具运行时间与供应商首字等待不能算入本地请求准备预算。
5. 校验全文、重复序号、终态、审批、停止、重连、历史补页、自动追问及子代理隔离。内存与 DOM 峰值在持续多轮追加后应稳定，不以刚刷新后的五轮小窗口替代长跑验收。

本次验证：前端源码/dist 同步检查通过；前端会话流、token 缓存和 stream bridge 相关测试 **25 项通过**。缓存批量实验 15 个样本、均匀到达实验 18 个样本，均通过全文校验且无页面脚本错误。生产修改和实际用户现场的完整改善仍属于下一阶段。
