# grep 队列与工具审批准备优化（2026-10-23）

## 1. 本批完成

在[历史复核](grep-history-review-2026-10-23.md)之后继续修复两条确定存在的本地路径：

1. **grep 不再与普通 `asyncio.to_thread` 任务共用线程池。** 独立池最多4个工作线程，已接受的运行及排队任务合计最多16个。等待准入、线程排队、后端执行共用默认30秒预算；不扩大默认线程池。
2. **排队中的 grep 到期或取消可先返回。** 原子状态门将未开始的任务标记为放弃，线程以后拿到它也不会进入工具函数、读取文件或启动进程。已经运行的任务仍设置停止事件，等待自有进程退出和管道关闭，再交付结果/取消。
3. **仅在真正需要审批时重建工具审查材料。** 原来每个工具经过 `authorize_tool` 后，无论允许、拒绝还是 full_access，都会调用 `_build_tool_review_context`，读最多4MiB日志尾窗；尾窗没有用户事件时还可能回读全文。现在 DENY 直接返回，ALLOW 无 Hook 审批时不构造材料；ASK 或有效 Hook 审批仍在 pending 之前冻结同一份材料，供自动审查及人工卡片使用。所有工具仍执行授权检查，批准后仍重新绑定最终请求。

主代理与 task 子代理使用相同执行闭包和 grep 入口。工作目录、单次目录授权和调用身份继续通过复制 ContextVar 传入；没有把授权结果缓存为永久放行，也没有改变事实提交或 ownership 边界。

## 2. 队列与取消的边界

- 不直接取消线程池 Future 并释放配额：标准 ThreadPoolExecutor 中，已取消的工作项仍会占据物理队列，反复超时可能积累。放弃任务的占位项只有在 worker 真正取走时才释放配额；等待准入的协程不向池内继续堆积工作项。
- 已运行任务的取消仍等清理，重复取消也不会提前交付。停止原因首次确定后保留，避免超时通过取消事件唤醒清理线程后被误记为取消。
- `grep_timing` 新增 `admission_ms` 和 `queue_outcome`；未进入 worker 的调用 `worker_queue_ms=null`。总耗时仍包含实际等待；空值不能按零排队解释。`admission_ms` 是准入锚点，包含于 `worker_queue_ms`，不可相加。
- 4个工作线程是有界并发取舍。超过并发容量会在搜索自己的队列等待，并可能明确超时；没有承诺任意数量的并发搜索都同时开始。
- event loop 本身长时间不能调度、Popen 尚未返回句柄或进程清理仍会增加尾部。预算不是绝对墙钟上限，也未缩短为500ms。

## 3. 受控对照

源码前后快照与原始 JSON/日志位于 `.analysis/grep-queue-20261023/`。以下是本批与修改前版本的对照，不与历史宽口径耗时混算。两种 invoker 使用相同最终搜索后端、预算对象和 ContextVar，以隔离排队实现的差异。

| 场景 | 修改前中位数 | 修改后中位数 | 样本与边界 |
| --- | ---: | ---: | --- |
| 默认线程池被一个事件屏障占用300ms，小文件 grep | 307.950ms | 2.436ms | 各5次；没有CPU/磁盘压力 worker |
| 已在线程池排队后取消，屏障300ms后释放 | 281.207ms | 0.319ms | 各5次；新旧各阻塞实际使用的搜索执行池 |
| 普通小文件 grep | 3.605ms | 3.587ms | 各16次，交替顺序；不能宣称稳定倍数提升 |
| 普通源码目录 grep | 72.103ms | 64.679ms | 各8次，交替顺序；结果多重集合一致，rg文件输出顺序可能不同 |
| 8533会话：已获准工具的审批前缀 | 97.881ms | 0.838ms | 各3次，19,325,825字节日志快照 |
| 9a002b3e会话：已获准工具的审批前缀 | 109.432ms | 1.720ms | 各3次，141,140,030字节日志快照 |

审批前缀使用真实 `_execute_one_core` AST，在实际工具调用前截断；授权/pending/steer接口用本地夹具，日志解析和材料冻结使用真实函数。每次 `asyncio.run` 的固定成本包含在内；数字不是完整工具端到端耗时。两份冻结会话快照每个旧样本各读一次尾窗，未触发全文回退；新样本均为零次历史读取。因此这里证明的是删掉一次约百毫秒的无用本地准备，不能证明历史数十秒外围差额都由它造成。

普通查询24对结果多重集合相同。初次基准对目录直接比较字符串顺序失败；改为保留重复项的行多重集合比较。第二次取消基准让新搜索在线程池隔离后已经正常完成，随后再取消，夹具错误；改为新旧各自阻塞实际搜索池。两次原始失败日志保留为 `benchmark-initial.log` / `benchmark-second.log`，没有修改生产实现来迁就夹具。
