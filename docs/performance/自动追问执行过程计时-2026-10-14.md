# 自动追问执行过程继承上一轮耗时

## 原因

自动追问在 `_continue_with_queued_turn` 中沿用同一个 run 和 SSE 连接。前端新建执行过程框时，原来始终用 `ctx.runStartedAt` 初始化计时，因此第二条及后续条目会从整个 run 的起点计算，包含前面轮次的时间。

还有两个覆盖入口：重新接入 SSE，以及会话状态定期对账。这两个入口原来都把服务返回的 run 起始时间写入执行过程框。仅在自动追问到达时清零，刷新页面或下一次对账后仍会恢复成累计时间。

后端 ReAct 的 `react_wall_start` 在每次调用时重新建立，`process_metrics.duration_ms` 是本轮耗时。历史回放直接采用这个值，所以实时显示和刷新恢复时的起点处理是本次修复重点。

## 修改

- `app/agent_loop.py` 保存普通用户轮次提交事件的时间，并将它作为 `created_at` 随真实轮次序号一起发送，保证实时消息与历史投影采用相同时间。排队输入的入队时间不会作为本轮开始时间。
- `frontend/src/app/modules/message-rendering.js` 新建执行过程框时，通过 `turn:<runtime_seq>` 找到对应用户消息；未编号的实时分组按当前用户消息位置定位。将这条消息的时间保存为分组自己的 `procTurnStartedAt`。
- 历史回放也保存这一时间，重新接入 SSE 时可以恢复本轮已用时间。
- `applyRunStartedAtToProcessGroup` 优先使用分组自己的轮次起点，重新接入和定期对账不能用 run 总起点覆盖它。已封存且未恢复为运行状态的执行框不会被对账重新启动计时。
- 没有用户轮次锚点的续接分组继续使用原有 run 起点作为兼容回退。

## 检查与生效

检查范围为源码审查、Python/JavaScript 语法检查、差异检查和前端生产构建。没有新增或运行测试，没有发送模型消息，也没有重启后端。未完成浏览器实机验证。

前端重新加载页面后使用新的分组计时逻辑。旧后端实时追问消息缺少 `created_at` 时，用户消息的本地接收时间可以作为起点；刷新后使用历史记录的提交时间。后端下次重启后，实时消息也直接提供这个提交时间。

保留工作区中既有的桌面在线状态及打包相关改动；没有修改会话事实记录。
