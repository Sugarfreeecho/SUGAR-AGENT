# 睡眠恢复后重复执行过程：77dc386c

## 现场证据

会话：`77dc386c-fe09-4863-a50d-1a3233060de2`。

读取最近一轮的 `history_snapshot` 时，当前分组为 `turn:21658`。持久化执行记录里的工具名称、参数与结果完整，没有空工具记录。一次现场读取约 186ms。

随后以历史快照的 `last_runtime_seq=27239` 发起只读 SSE 重连观察，收到以下旧帧：

| 内容 | 现场结果 |
| --- | --- |
| 上一轮工具状态 | 27 帧，对应 15 个工具执行 ID，分组为 `turn:20557` |
| 上一轮工具状态的事实序号 | 20925—21613，均早于快照游标 |
| 摘要等待提示 | 14 帧，`stream_seq=22` |
| 睡眠恢复提示 | 2 帧，睡眠约 17852 秒、21895 秒 |
| 同一轮的完整记录 | 已由历史快照恢复，但事件总线仍再次发送其旧临时状态 |

上一轮和当前轮使用同一个 `run_id=aeb6ed0b-557f-4d82-881d-0ca836e34551`。因此按 run_id 合并执行过程会混淆不同用户轮次。

## 原因

1. 事件总线把 `tool_execution_state` 留在最近 400 条临时事件中；工具结果提交时只清理 pending/参数/输出草稿，未清理工具状态。
2. SSE 先恢复持久化记录，再无条件回放临时缓存，未用历史快照的运行时游标过滤已恢复的工具状态。
3. 最新一轮模式没有加载上一轮完整工具记录。旧工具状态只有状态、工具 ID 等字段；前端原先又未读取状态帧中的工具名称，便生成“工具({}) / 执行中...”的空行，并创建上一轮分组。
4. 摘要等待和睡眠恢复提示没有执行记录游标，也进入回放缓存。它们随后追加到旧帧选择的分组。
5. 浏览器刷新清空本地页面，却没有清空服务器内存里的回放缓存，因此现象会重现。

睡眠触发了连接恢复，同时积累了等待提示。多余框来自旧事件的重放，没有证据表明这些工具被重新执行。

## 修复

- `session_event_bus.py`：工具状态按稳定执行 ID 保存最新状态；完成工具结果清理相关状态；压缩等待只保存当前一条，并在持久化进度或正文提交时清理；睡眠恢复仅通知在线订阅者，不进入重连缓存。
- `session_event_bus.py` / `webui.py`：订阅恢复使用 `after_runtime_seq` 过滤；持久化追赶之后再次过滤队列中已被恢复的执行帧，覆盖订阅与追赶之间的竞态。
- `sse-handling.js`：在运行状态归约和分组选择前，跳过不新于已恢复游标的临时执行帧；依据同一 run 已恢复的请求序号，过滤旧摘要预览和旧睡眠提示，兼容尚未重启的旧后端。
- `message-rendering.js`：部分更新不再用 undefined 覆盖完整元数据；工具状态帧提供的名称、参数、结果与进程信息会被保留。

## 生效与检查范围

前端构建更新后，重新加载页面即可应用客户端过滤。后端缓存修复在服务下次重启后生效。

现场诊断只读取历史快照及事件流，没有修改会话事实记录或终止运行。实施阶段仅进行语法检查、差异检查与前端生产构建；没有执行回归测试，也未进行睡眠恢复实机复现。
