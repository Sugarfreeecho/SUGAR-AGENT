# grep 执行优化与验收（2026-10-23）

## 1. 结论

已实施过滤参数修复、流式管道处理、候选范围统一、可终止正则 worker、统一预算和逐调用计时。主要收益是消除可复现的错误扩搜与额外等待；普通已经很快的查询没有稳定倍数提速。

**整体轮间低于 500ms 尚未据此验收。** 原深圳舆情目录查询在本轮初次回放仍触发 30 秒超时，后续热缓存回放完成。保留这一失败，不能只摘取后面的快样本。生产加载与实际 Agent 运行收益另验收；本轮没有重启或中断用户服务，也没有执行真实模型调用、发送交互卡片或启动压力 worker。

前置证据、48小时分布和历史事实见 [分析报告](grep-latency-analysis-2026-10-23.md)。本篇的受控对照、历史参数回放和生产日志统计是不同口径，不能合并为一个 P95，也不能用过去的宽口径总耗时直接计算本批加速倍数。

随后扩大历史复核已确认：现存执行段≥30秒251次、明确30秒超时204次，包含旧 `status.duration_ms` 和带完整结果的 `tool_started` 记录；204次超时中只有11次传入字符串include。本批对参数缺陷的修复有独立证据，整体历史根因仍须覆盖目录扫描、执行队列和外围交付，不能由近48小时样本外推。逐周统计、子代理、严格配对和两份完整CSV见[历史复核](grep-history-review-2026-10-23.md)。

## 2. 具体修改

| 环节 | 原实现 | 本批实现 |
| --- | --- | --- |
| include/exclude | 遍历字符串字符，`*.py` 被拆为 `*`、`.`、`p`、`y` | 字符串按一个完整模式兼容；数组/tuple 逐项校验，错误类型在启动前拒绝；不拆逗号或空格 |
| stdout | 非 TTY 时 rg 默认块缓冲，已有命中可能迟迟不交付 | `--line-buffered`；保持行/字节上限立即终止 |
| stderr | 读完 stdout、wait 后才读取，有管道互等可能 | 同时持续排空，统计真实字节数，最多保留 8192 字节诊断；不把诊断正文写入耗时日志 |
| 排除目录 | rg 与 Python 的嵌套规则不同 | 一份默认目录定义，rg 使用不锚定根的目录规则；显式以被排除目录作为搜索目标仍可读取 |
| 兼容正则 | rg 任意非零错误后隐式 Python 全扫 | 仅正则解析/引擎不支持才匹配回退，I/O 错误明确失败；使用同参数 `rg --files --null` 枚举候选后由独立 Python 进程匹配 |
| 没有 rg | Python 不解析 ignore 文件却继续目录搜索 | 默认明确报错；显式单文件保持可用；调用方明确 `include_ignored=true` 才允许不解析 ignore 的目录回退 |
| 复杂单文件表达式 | Python re 可占用 GIL，取消线程不能停止匹配 | 重复、断言、引用及超出保守快路径条件的表达式在可终止 worker 执行；不依赖本机 rg 的缺失 PCRE2，也未新增第三方依赖 |
| 单文件快路径 | 所有表达式均在工具线程匹配 | 64KiB 内、表达式不超过 128 字符且无重复/断言/引用时保留进程内路径；超限使用 worker，付出一次启动成本 |
| 预算与取消 | rg 独立 30 秒，Python 回退无统一预算 | 默认仍 30 秒，从线程提交前起算；后端切换、枚举与匹配共用；取消事件传到自有进程，结束后等待并关闭管道 |
| 部分结果 | 超时可能丢失命中，读文件错误可能看作正常结果 | 保留已有命中，错误放在开头并标明未完成，使既有工具状态适配器记录失败；不伪装完整无命中 |
| 定位 | 只有 invoke 和宽口径总时长 | 每次 `grep_timing` 关联 session/run/iteration/tool_call_id，记录队列、后端、启动、首输出、消费、读取、stderr、清理、退出码和停止原因 |

主代理和 task 子代理共用 `agent_loop._invoke_plain_tool` 的 grep 分支。异步取消会设置该次搜索自己的事件，并等待线程处理进程清理；主循环被取消时也向 grep 传播。并发调用通过 ContextVar 保持工作目录、安全上下文和身份隔离。事实提交、权限审批、ownership、审查捕获及结果耐久边界沿用原路径。

显式文件保持旧 Python 的 UTF-8 `errors=ignore` 及二进制读取行为；目录兼容后端使用替换解码，并跳过前 8KiB 含 NUL 的候选。目录全文件二进制探测与 rg 内部细节并非逐字节等价，未宣称所有引擎的正则/二进制语义完全相同。行数、文件大小和输出字节限制继续生效，敏感文件在候选阶段排除、输出继续清洗。

## 3. 计时字段与边界

- `elapsed_ms` 从搜索提交前至实现完成附近计时；实际日志写入、外层审批/pending 交付和结果提交不全在内。
- `worker_queue_ms` 是提交至搜索入口；直接同步调用接近零，没有会话身份时不伪造 ID。
- `first_hit_ms` 是相对提交的首条保留结果锚点，不是独立可加的区间。
- 每个进程的 `read_ms` 从启动前计时，包含 spawn、首输出和消费，不能再把它们加到 read_ms 上。`consume_ms` 是消费/清洗/收集结果的累计子区间；`cleanup_ms` 单列资源回收。
- 默认预算没有降到 500ms。Popen 自身若阻塞，Python 无法跨平台在它返回句柄前强制终止；结束进程与清理也有短尾，不能把搜索预算描述成绝对的墙钟上限。
- 本篇初次实现仅在worker进入时检查队列预算，等待原future仍可能延后回执；随后已实施独立有界队列、事件循环侧deadline与放弃门，见[后续补修与对照](grep-queue-and-tool-preparation-2026-10-23.md)。已运行进程仍等待清理，预算不是绝对墙钟上限。
- 兼容目录搜索会先完整枚举候选再启动 Python worker，大目录仍有枚举成本；没有新增全文缓存、无命中缓存、后台 watcher 或扩大默认线程池。

旧函数从修改前源码 AST 提取至私有命名空间，相关外部辅助函数和运行环境相同。普通查询按轮交替新旧顺序。管道夹具中只有本地合成进程/实际 rg，没有 API 请求；stderr 夹具临时设 1 秒预算，仅用于复现互等，不改变生产默认配置。

## 5. 保留的真实慢例

`9a002b3e` iter22 参数：根为 `workspace/深圳运营商舆情_202610`，表达式 `1,848|1848|42%）|（42%|42 %`，max_results=40。

1. 本轮首批回放仍有 **30006.168ms 超时**，保留 18 行左右的部分结果并明确未完成。这一失败在 `benchmark-initial.json/log` 中。
2. 相同范围候选枚举有 **4373 文件、549479641 字节**；其中 `_browser_profile_social` 有 **4238 文件、534792183 字节**。不仅是用户产出的 JSON/报告，还包括浏览器缓存、数据库和无后缀文件。
3. 单独 rg 诊断一次 2723.864ms，单线程且禁用 mmap 的一次为 730.146ms；去掉整个 profile 的诊断一次为 89.982ms，但结果由 18 行变为 10 行，**这不是语义相同的加速方案，没有改为默认排除**。这些单次实验的顺序和缓存不同，也没有足够证据默认改线程策略。
4. 后续当前实现剖析约 **257ms**，其中结果读取等待约 215ms、结果清洗累计约 1～2ms；再一次热回放为216.338ms。没有强制清空系统缓存，也未重建当时文件打开/读取负载，不能把首个 30 秒细分为已证明的 OS、硬盘或并发百分比。

结论限于：确定性扩搜/管道/无期限匹配已修；未达上限的广域搜索仍需要扫描候选。保留大目录的实际工作量与冷/热差异，不将未测到的耗时归到上下文长度或服务器响应上。后续若需改变默认范围，应单独设计缓存目录准入或由调用方提供 include/exclude，不能用静默漏搜作为性能通过。
