# 主/子Agent轮间优化覆盖与补修（2026-10-21）

## 1. 结论与口径

主、前台子代理、后台子代理共用ReAct、请求池、请求整理/计数缓存、工具目录刷新及Runtime V2增量读取。原先子代理专用交付未接通的三处已补齐：journal/UI组合及已完成工具批次、心跳/普通UI线程写入并等待、真实子run ID的计时及结束清理。随后将主/子共用的完成事件提交改为一次追加和一次投影。**cd20此前12场景72轮全部<500ms；§8追加负载仍失败；§9重启后真实3个run、50轮间仍27次≥500ms，真实总目标尚未完成。**

严格端点为最后一个工具`execute_one_core`返回，到紧邻下一轮第一次实际`http_send_entered`，排除工具core执行。工具若早于上一模型工作线程结束，严格区间仍会含两者重叠的尾段，必须另列`local_ready=max(tool_returned,previous_model_worker_done)`口径，不能把重叠算作纯本地处理。按主、前台子代理和后台子代理分别测量。本文不将本地耗时笼统归因于上下文长度或模型服务器响应；长历史只是固定工作负载之一，必须看实际本地步骤。

**最新真实截面见§12：14:42重启后4会话、8个run、508个严格轮间，355次≥500ms，P50 800.432/P95 4543.236/最大12337.229ms。新增计时已出现；目标仍未完成。** 其中一个run仍在执行；仅7个已结束run也有211/323次超标。工作线程重叠单列后仍352/508次超标，不能把这批长尾解释成全部来自早启动工具。

随后按§13实施等待式普通事实线程提交、整组Hook准备及发送细分。两次自然重启必须分开：23:22进程的13个配对全部超标，P50 3568.220ms；23:28进程的3个已中断恢复run中只有1配对，为22345.197ms。目录SWR初版回退已补修，随后按§15缩短运行写栅栏全局锁。最终相关113项通过、源码无漂移；完整门禁原693通过/3失败/1跳过中的2项测试问题已修正，插件退役断言仍失败，不能算整套通过或500ms验收。

基准组P50为中位数，P95为nearest-rank；§9真实数据沿用既有分析器的nearest-rank P50/P95。小组仅6个配对，P95即最大值，不能声称95%可靠性保证。不相加父子span或各阶段分位数。后台线程只用于派发执行，事实提交仍须完成后才能发下一API。

## 3. 两批实现及正确性边界

### 3.1 子代理交付与运行身份（8f基线）

`agent_subagent.py`中child_emit使用同一`persist_execution_event(commit_ui=True)`，挂接`tool_batch`，整批耐久成功后再逐条发布子页/父级事件。过滤`_runtime_v2_committed`私有回执；前后台原通知过滤不变。每个子代理交付锁串行化自身事件，不能拿跨loop父回调当后台结果通道。

心跳、普通UI、指标注册/结束在线程中写入，仍等待完成。取消先结算已开始的写，防止线程晚到把interrupted改回running或遗留心跳。ReAct的`_run_error`即失败，不能因存在展示文字而标成功。state与metrics复用已有预约run ID；没有另建所有权协议，子代理仍按既有注册表取消。

源码清单[baseline-source-sha256.json](../../.analysis/interround-500ms-implementation/20261021-subagent/baseline-source-sha256.json)，生产覆盖文件集合SHA256为`8f023da2fa65cf35378f8a5a74921fa9d085c4cbd89fda895b853c05912649a6`。这些依赖指纹包括已有工作区修改，不代表本批修改了全部文件。

### 3.2 主/子共享完成事件批量追加（cd20阶段）

原组合提交虽然共用外层事务及句柄，四个工具仍逐条追加execution/UI并更新投影，八次显式flush。新增`runtime_v2/execution_ui_batch.py`私有预演原journal规则，交错准备相同execution/UI事实及真实seq引用；源身份/尺寸/时间与next_seq重验成功后一次写入并flush，随后投影一次、普通journal补尾，最后返回提交回执。单条reasoning/response终稿也将两次追加合一。

原EventLog追加未显式调用`os.fsync`，因此收益为减少flush/投影调用，不能描述成减少八次fsync。原型保留[flush计数结果](../../.analysis/interround-500ms-implementation/20261021-subagent/atomic-ui-prototype.json)：12批×4工具，96→12次flush，批次中位数86.675→41.679ms；每批语义状态相同、快照与全量重放一致。这只证明局部机制，不证明完整轮间已<500ms，也不是生产用户会话因果实验。

预演不发布状态；自定义manager协议、特殊/不持久化事件、未知源身份及首次bootstrap保留原路径。源变化时写前拒绝，投影失败后由既有事实重放恢复。取消写后仍先保持派生视图一致，再传播取消，不公开成功批次。文件部分写失败仍可能留下已有事实，不新增跨事实崩溃回滚承诺。用户、模型助手/工具、摘要及所有权边界仍同步完成于下一API前。

最终覆盖清单见[native-source-sha256.json](../../.analysis/interround-500ms-implementation/20261021-subagent/native-source-sha256.json)，生产覆盖集合SHA256为`cd20198eee10c2a81138bce3a9c7ee6f78d3bf0aa44425d032333ec3b740e59c`，36个生产文件、1个基准、9个测试文件共46个编译通过。基准的`--reference-ui-row-commits`只在隔离基准中选择原逐条路径，不改变默认生产路径；用于相同源码和相同事实的机制对照。

### 8.2 阻止Shell验收的长路径兼容缺陷

既有`runtime_files`将子进程TEMP放在run专属目录，已有Windows helper仍用.NET FileStream写nonce。受控新票据对照确认：304字符标记名在首次执行时即报“nonce已使用”，文件实际不存在；同一旧程序257字符路径首次成功、重放拒绝。C#原catch把所有IOException都叫作重放，不能据错误文字认定真的复用票据。见[原探针](../../.analysis/interround-500ms-implementation/20261021-subagent/shell-nonce-path-probe.json)。

按§12实测的同步提交/恢复延迟增加`app/agent_fact_commit.py`：普通助手中间消息、已完成工具的单条检查点、已有工具批次及其普通补偿路径，将原同步函数交给线程执行，调用协程仍等待。没有将事实提交放到下一API之后，原事务、写栅栏、flush、源/seq检查和事实顺序全部保留。

此入口处理的是已选定的已完成事实；取消即使发生在排队期间，也先等待原写函数处理，不能丢弃已完成工具结果。写函数仍可按原实时所有权/写栅栏拒绝写入。重复取消同样先收敛，成功后在原loop同步发布内存历史、checkpoint集合及`_history_persisted`，再传播取消；失败不发布成功回执。使用future避免取消包装Task导致“Task结束、同步writer仍在运行”的假完成。初始用户、控制结果替换、压缩摘要、所有权转交以及其他同步旧调用点不在本次线程化范围。

复制上下文时，会话路径缓存增加线程和async task所有者检查；另一线程/task只能重新解析并创建自己的事务作用域，不能借用/清空父缓存。目录替换、session子索引变化、别名/reparse/未知身份以及源校验保持。没有为减少Path.resolve而增加无条件长期缓存。

### 13.2 Hook整组准备及重复根解析

`dispatch_hook/warm_hook_pipeline`的目录加载、runtime定义、配置签名、manager构造合并到一次等待式线程执行；manager仍关联调用者的原loop，实际Hook和审计继续在所属loop按序执行。worker请求陈旧manager刷新时，用`call_soon_threadsafe`回到所属loop做去重、future注册和完成清理，关闭的loop不再安排刷新。没有新增跨派发授权缓存或删掉实时信任/启停检查。

旧`hook_runtime_definitions`计时现在是同一worker内的定义区间，新`hook_prepare_await`才表示整组往返，不能继续直接与旧版await定义包络同比。默认状态路径在一次调用复用项目根，源根解析2次→1次；返回路径相同，迁移和每次身份守卫保持。这减少重复准备，不代表目录revision全部免I/O。

主、前台/后台task子代理共用上述ReAct调用点、Hook以及发送worker；子代理仍未共用主delta桥，历史/部分终态也仍独立。675项功能组合包含实际前后台子loopback、子run身份、工具事实和恢复验证，不能替代新生产子任务性能验收。

### 13.3 新的发送与线程恢复证据

- `fact_commit_await`作为外层根，关联session/run/iter，≥50ms保留；提交、worker进入/结束、loop恢复及内存回执区间与原内层model_commit分开。Hook有同样的整组端点。LocalOperationTrace新增mark_threads，取消的端点顺序不能按成功路径强减。

### 15.2 保留事实边界的锁范围补修

注册/清理使用进程内逐session注册锁，外加原逐session OS事务；文件检查、owner身份验证、临时写入和replace均在全局map锁外，原写入/replace成功后才短暂取全局锁发布`_ACTIVE_STEER_RUNS`，不将此说成新增fsync保证。保留同session串行顺序，避免把原无界线程排队换成同进程OS锁重试超时；锁对象按session在进程生命周期内保留，不回收仍可能有等待者的锁。

实时token读盘、未知/其他活进程归属拒绝、失败不发布、旧owner不能删新fence均保留，没有把所有权转交放到API之后。其他线程/loop的内存归属查询和abort不再等待另一个session的文件I/O；同一loop直接同步注册及自身路径/读盘仍可能阻塞，本批未将所有启动入口异步化。增加`write_fence_local_lock / write_fence_session_path / write_fence_disk_read`与`steer_fence_register_io`计时，供下一批自然数据区分。

4个新增并发回归验证：另一session在注册I/O被阻塞时仍能查fence及abort、同session按事务顺序发布、replace失败不发布、旧清理与新注册交错不删新fence。首次测试辅助函数误名`setup`被pytest识别成xunit入口，67项通过/4项setup错误；改名后复验，不把它记作生产故障。
