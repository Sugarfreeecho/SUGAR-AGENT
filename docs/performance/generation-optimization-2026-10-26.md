# 生成期间的前端优化与验证

2026-10-26。承接 [生成性能分析](generation-performance-2026-10-26.md)，本轮已实施长历史分组索引、工具交互卡片按需挂载、后台文字合并刷新。前端已重新构建，无需重启后端；已打开的页面刷新后使用新代码。本轮未发送测试模型请求，也未强制刷新用户页面。

## 实际改动

**执行分组索引。** 原来每条执行更新都查询所有 `.process-aggregate`，再按分组或运行 ID 查找。现在按 stream 建立 WeakMap 索引，稳定输出期间直接查表。MutationObserver 只将分组增删、分组身份/结束状态、分组 class 成员资格变化标记为失效；普通文字、运行样式、折叠样式不导致全量重建。每次查找先取尚未派发的 mutation，确保同步前插历史、替换节点或修改归属后立即得到正确结果。仍选择同身份中 DOM 顺序最后一个分组，运行 ID 查找仍排除已结束分组。

**交互卡片挂载。** 工具行创建、工具调用 ID 补齐或变化、恢复快照时仍关联审批和问答卡片。稳定文字/输出增量不再重复查询整个会话的卡片与空槽。后到的卡片仍通过原交互渲染路径直接挂到工具行，恢复时仍可重新关联。

**后台显示合并。** 对 `.is-offscreen` 中已有执行行，继续同步更新权威 execution record，只将显示更新按执行 ID 合并，默认 250 ms 刷新。覆盖思考、回复、工具参数及工具持续输出。新行、工具开始运行、工具 ID 补齐、审批/输入状态变化、失败、完成和恢复快照仍立即处理；前台更新不降频。后台新行也不启动逐帧文字动画。

离开正在生成的会话前先收齐已排队的平滑文字；切回运行中或缓存会话时同步显示最新内容。完成、中断、清理时先处理待显示文字并取消定时器。定时器验证原行仍在 stream 中、消息身份未变、序号未被更新状态超越，防止历史重载、节点复用或缓存淘汰后重新插入旧消息。

这些变化没有减少接收的事件、截断文本或修改上下文估算及压缩阈值。

## 测量方式与范围

使用本机无头 Edge 和实际 `renderExecutionRecord`、记录归并、分组查找、交互挂载函数，加载隔离 DOM。原版源码在修改前备份。历史是合成数据，外围统计/滚动等有 fixture 替代，不是完整应用界面，也没有模型、工具进程或真实 SSE 网络请求。后台容器采用应用相同的屏幕外定位规则，活跃执行位于最新分组。

初始历史先完成两帧布局，再开始持续输出计时；输出结束也等待两帧。最终持续输出测试单独运行，与本轮的 pytest、构建和另一组 benchmark 不重叠；机器其他应用和系统负载未被控制。前后顺序交替，保留全部三轮结果。原始数据、脚本和源码指纹在 `.analysis/generation-optimization-20261026/`。

### 按时间持续输出：1 个前台 + 4 个后台会话

每个会话有 1,000 个历史分组。名义每 20 ms 给每个会话一个文字增量，100 轮后发送完成状态，共 505 次执行更新。初始行与首次建立索引在计数窗口之前。前后全部样本的最终文字与权威记录一致，状态均为 completed。

| 窗口内工作量 | 修改前（三轮一致） | 修改后（三轮一致） |
|---|---:|---:|
| 前台文字/完成显示更新 | 101 | 101 |
| 后台文字/完成显示更新 | 404 | 36 |
| 全量分组查询 | 505 | 0 |
| 被观察到的 DOM 变更 | 3,030 | 822 |

后台显示更新减少约 **91%**。这是该回放的渲染次数，不能解释成全机 CPU 下降 91%。前台没有以减少更新次数换取这些结果。

| 轮次 | 前 ScriptDuration | 后 ScriptDuration | 前 TaskDuration | 后 TaskDuration |
|---|---:|---:|---:|---:|
| 1 | 362.515 ms | 34.147 ms | 2,462.855 ms | 366.338 ms |
| 2 | 154.687 ms | 30.596 ms | 1,127.663 ms | 325.085 ms |
| 3 | 135.561 ms | 25.175 ms | 1,034.553 ms | 223.609 ms |
| 中位数 | 154.687 ms | 30.596 ms | 1,127.663 ms | 325.085 ms |

这是浏览器 Performance 域在隔离页面上的累计主线程任务/脚本耗时差。第一轮原版波动较大，未删除；原版实际回放墙钟为 2.012–2.493 秒，修改后为 2.007–2.021 秒。不能据此推算真实会话生成速度、后端 CPU、风扇转速、首次打开耗时或整机功耗改善比例。

### 集中到达的 1,000 个工具文字更新

分别测试 10 和 1,000 个分组，前台和后台各一组。在已经创建的工具行上发送更新，最后同步刷新队列并确认最终参数一致。两种历史规模的稳定工作量相同：

| 工作量 | 修改前 | 修改后 |
|---|---:|---:|
| 全量分组查询 | 1,000 | 0 |
| 交互卡片/空槽查询 | 2,000 | 0 |
| 前台显示更新 | 1,000 | 1,000 |
| 后台显示更新 | 1,000 | 1 |
| 后台 DOM 变更 | 7,000 | 7 |

这是集中到达场景，不能拿后台一次刷新直接代表平稳输出；上面的持续回放用于补充验证。索引首次创建有成本，因此脚本另外记录新 stream 的首次查找时间，而非只记录命中缓存的时间。首次建立索引不代表会话完整冷加载，仍需读取和显示历史。

同一脚本交替顺序执行十轮，单轮处理 1,000 次更新的脚本耗时中位数如下，不含逐次强制布局：

| 历史分组 | 显示位置 | 修改前 | 修改后 |
|---:|---|---:|---:|
| 10 | 前台 | 12.65 ms | 11.40 ms |
| 10 | 后台 | 15.45 ms | 2.45 ms |
| 1,000 | 前台 | 249.35 ms | 14.70 ms |
| 1,000 | 后台 | 249.80 ms | 2.55 ms |

新建 stream 首次查找另测 20 次：1,000 分组样本的中位数由约 0.45–0.50 ms 增至 1.30–1.55 ms，约增加 1 ms 的索引初始化；10 分组样本多数低于浏览器计时分辨率，显示 0 不等于没有成本。这笔一次性开销换取稳定输出期间免除全量扫描，不能将缓存命中的数据写成冷加载提速。

## 持久化处理的决定

复查当前代码发现 `SessionEventLog.session_transaction` 已接入 `_session_path_resolution_scope`，SessionManager 会在操作内复用带目录身份、调用方和作用域校验的路径。流式队列也已有默认约 12 ms 合并及结束边界等待。不能把这些现有机制重复列为本轮新增优化。

本轮没有扩大写盘合并窗口、删除源文件检查或改变“持久化后发布”的顺序。进一步后端优化应以当前版本的生成剖析为依据，单独验证跨线程、目录变化、断线重放和故障恢复。当前的改善针对前端重复工作，不能声称已解决后端生成高占用、启动峰值或约 3.9 GB 驻留内存问题。
