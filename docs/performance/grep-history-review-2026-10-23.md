# grep 前几周与全部保留历史复核（2026-10-23）

## 1. 修正结论

**超长查询远不止6次。** 原“6次”只对应截至10月23日02:20的近48小时 invoke 日志中≥30秒的样本。原7天 invoke 统计已经有11次；同期工具宽口径≥30秒还有16次。这个窗口和样本不足以代表此前数周。

本次对现存历史重算，结果如下：

| 范围 / 来源 | 有时长的 grep 记录 | ≥5秒 | ≥10秒 | ≥30秒 | ≥60秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全部保留事件，执行段，7/11～10/23 | 9114 | 518 | 378 | **251** | 24 |
| 全部保留工具宽口径，7/12～10/23 | 9079 | 843 | 494 | **275** | 36 |
| 9/25～10/23，事件执行段 | 3955 | 193 | 105 | **48** | 2 |
| 9/25～10/23，工具宽口径 | 3957 | 489 | 211 | **64** | 5 |

251次执行段≥30秒中，**204次明确返回 `Error: ripgrep timed out after 30 seconds ...`**，47次没有这个超时诊断。9/25～10/23的48次中，29次明确超时。每个≥30秒执行段都已回到原事件核对时长、身份和来源字段；251/251找到原始记录，204个超时预算全部为30秒。

执行段包含工具线程排队、叶子检查、搜索和返回处理；不能当成纯正则或磁盘扫描时间。工具宽口径还含更早的本地流程。两者经常对应同一次调用，**不能把251和275相加**，也不能用总体分位数相减估算外围耗时。

## 3. 此前为什么少算

1. **时间窗口太短。** 近48小时仅覆盖近期一小段，未纳入9月的主要超时集中期。
2. **仅依赖 invoke 日志会漏更早记录。** 当前361份日志从10/5起保留有效 logger 头；这不意味着此前没有慢查询。更早的时长存在事件事实和 execution_metrics 中。
3. **旧字段被遗漏。** 旧工具 UI 事件把耗时放在 `payload.status.duration_ms`，并非只有 `payload.duration_ms` 或 `payload.tool_status.duration_ms`。本次9114个有时长记录中，6874个使用旧 status 字段。
4. **旧事件名不能直接等同执行状态。** 一些带完整结果和最终耗时的历史导入记录仍叫 `tool_started`。251个超长记录中，119个来自这种旧类型，116个来自 `tool_finished`，16个来自 `execution_recorded`。本次依据结果、时长和调用身份识别，没有把任意 started/pending 草稿视为已执行完成。
5. **子代理要递归覆盖。** 本次扫描包含嵌套 subagents；251个超长执行段中43个来自子代理。9/25～10/23的48个中有21个来自子代理，约44%。原顶层指标和选择性事实抽取不能代表完整主/子集合。

## 4. 对根因判断的影响

### 4.1 字符串过滤缺陷有确定证据，覆盖不了历史主体

204次明确超时中，include 为字符串11次、数组94次、未提供99次。字符串占约5.4%；不能将另193次归到字符串拆字符。

251个≥30秒执行段中，字符串12次、数组112次、未提供127次。先前近48小时“6次中5次字符串”的样本偏向，不能外推为此前数周的主要成因。

过滤参数修复、stderr持续排空、行缓冲早停、兼容正则的可终止执行仍有独立复现证据，实施结果见[优化报告](grep-optimization-2026-10-23.md)。当前证据没有证明历史204次超时全部来自同一种管道等待或范围问题。

### 4.2 还有正常单文件查询也很慢

47次未报告 rg 超时的长执行段中，8次参数明确指定源码文件，13次来自子代理。例如：

| 时间 / 会话 / iteration | 目标 | 执行段 |
| --- | --- | ---: |
| 9/29，94c48d93，iter5，子代理 | sessionStorage.ts | 63.864秒 |
| 10/3，0a194bee，iter6 | change-review.js，普通函数名和标识符搜索 | 60.589秒 |
| 9/29，1374f3d4，iter2，子代理 | hermes_constants.py | 53.745秒 |
| 9/29，490837f5，iter37，子代理 | Deepseek Harness 的 tools/src/index.ts | 47.884秒 |

这些单文件样本不能用“仓库全量搜索”直接解释。旧记录缺少 worker 入队/进入、打开文件和逐行匹配的完整分段，尚不能断定是线程排队、文件读取还是 Python 匹配各占多少；也没有依据将其归到上下文长度或服务器响应。

### 4.3 确认存在显著的执行段外围等待

只对 `(session_id, run_id, react_iter)` 中两侧都只有一个 grep 的请求做配对，不用最近时间猜测。共得到3819对，其中133对宽口径≥30秒；10对执行段本身低于5秒。举例：

| 会话 / iteration | 工具宽口径 | 执行段 | 两者差额 |
| --- | ---: | ---: | ---: |
| 1952493b，10/21，iter1 | 92.964秒 | 3.338秒 | 89.626秒 |
| 9a002b3e，10/21，iter398 | 43.057秒 | 2.945秒 | 40.112秒 |
| 22093e5d，10/19，iter131 | 34.923秒 | 0.912秒 | 34.011秒 |
| 9a002b3e，10/16，iter40 | 32.789秒 | 0.988秒 | 31.801秒 |

差额定位到工具外围范围，尚未逐条拆分为权限、pending交付、状态访问或其他准备；不能将所有差额直接标成一个锁等待，也不能与内部重叠 span 再次相加。执行段自己的线程排队则仍在执行段内，需要另看 worker_queue_ms。

### 4.4 修正后的优化优先级

后续实施状态：已修复共享线程池排队、未开始搜索的到期/取消返回，并去掉无需审批工具的历史材料准备；受控收益和仍未定位的历史差额见[队列与准备优化](grep-queue-and-tool-preparation-2026-10-23.md)。下面的优先级保留复核当时的证据口径，不能把新夹具数字回填成旧样本的根因。

- 对目录超时，按实际文件范围和进程读写分段核查：204次全部是目录/默认根查询；是否缓存目录、诊断管道、启动/读取阻塞，须逐样本确认。
- 对单文件及主/子并发，优先检查提交至 worker 进入的队列，以及 worker 内打开/匹配时间。当前版本新增计时为这一步提供证据，历史大部分样本没有这些字段。
- 对宽口径高、执行段低的调用，优先检查执行前的状态、权限和 pending 交付。搜索引擎加速只影响其中一段。
- 当前总预算从提交前起算，并在 worker 入口检查是否过期；这不能单独保证线程池排队时一到deadline就立即返回。排队下的返回时效需单独验证，不把“预算起算覆盖排队”描述成绝对墙钟封顶。

本次历史复核没有新增生产性能通过结论，也未重启服务或复跑用户任务。前一批修复的确定性收益保留；“历史主因已完全解释”及“整体500ms已达成”均无证据。

## 5. 数据覆盖与校验

- 361份日志，共约264MB，原始grep invoke行2013，跨文件去重后2009；同一文件内同毫秒同参数计数按最大重数保留。日志按行内session识别，不按文件名归属，也未按mtime提前裁剪历史。
- 564份 execution_metrics，包括207份子代理文件；9079个grep工具项，按请求和位置核查没有重复文件记录。缺时长不填0。
- 782份事件文件，共约3.00GB，其中33份修复/截断备份用于补全核对。按 session/run/tool_call_id 去重；所有≥30秒记录有稳定调用ID，跨run别名重复组为0；备份未贡献额外独有调用。
- 10490个grep相关调用身份中，9114个有时长，1376个没有。缺时长的生成、pending、取消或旧记录没有被自动计为慢，也没有填成0。
- 全量事件读取没有JSON坏行或截断尾行；对活跃日志与事件按清单记录的初始字节边界读取，防扫描过程中不断追尾。
- 全部251个≥30秒执行段再次核对原始时长字段和事件seq，并保存原行SHA256。204个明确超时回执均核到30秒预算。两份仓库根ZIP检查后均不含可补充的历史日志/指标/事件。
