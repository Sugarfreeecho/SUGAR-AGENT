# 空闲 CPU、风扇与后台历史回放排查

2026-10-26，Asia/Shanghai。用户报告打开 SugarAgent 后，即使不生成会话，风扇也明显转动。本轮已完成复现、三处优化、回归和两轮重启验证。**确认有不必要的后台工作；优化后占用下降，但启动峰值和约 3.9 GB 后端驻留内存仍存在，不能宣称空闲资源问题已彻底解决。**

## 测量范围

机器为 i5-1130G7，4 核 8 逻辑处理器。记录进程 CPU 时间差、进程树和 RSS。本文“单核百分比”是进程树累计 CPU 秒 / 墙钟秒 × 100；“全机百分比”再除以 8，用于便于理解的归一化，并非温度、功耗或实测风扇转速。

最初服务未运行，日志最后退出记录为 13:41。未据此否认用户的历史体验。经用户允许后于 18:51 启动，未创建测试会话、发送测试消息或主动调用模型对话；应用既有启动流程仍会启动 MCP、加载 Tokenizer 并进行连接预热。未修改插件启用状态、安全软件或系统散热设置。

当前 Edge 页面的只读 CDP 观察：5,531 个 DOM 节点，2 个执行过程容器，0 个运行中容器，0 个持续动画。43.879 秒内主线程 TaskDuration 增加 0.193147 秒，ScriptDuration 0.040645 秒，LayoutDuration 0.008487 秒。该页面在当时约占 0.44% 的单核时间，不是当次主要热点；这不代表生成状态下的浏览器也低占用。

最初的全进程扫描自身开销明显，且首段时间边界不够准确，保存在 stopped-baseline.json 中但**不用于性能改善计算**。后续改为仅采样获准启动的托盘进程及其后代；采样器和 py-spy 不属于该进程树。健康接口 500 ms 超时记录为 null，不能将 null 解释为运行任务数为零；成功读取的观测点均为 0，重启确认影响也均为 0 个任务/作业/终端。

## 实际复现

18:51 首次启动后，未发会话消息，10–115 秒的 22 个观测点，进程树平均约 89.75% 单核、最高 137.05% 单核；折算全机约 11.22%、17.13%。后端 RSS 从约 1.4 GB 持续增长，随后独立观测约 3.6–3.8 GB。

启动日志还有 628 个历史运行记录的恢复和巡检：一次 orphaned 扫描墙钟 36,293.744 ms，一次 stale 扫描 50,057.633 ms。墙钟包括等待和调度，不能全部算 CPU；它们也不是唯一热点。

对 Python 后端进行 20 秒、25 Hz 的非阻塞 py-spy 采样，得到 396 个活跃样本。按采样权重，`AutomationService._bridge_session` 约 83.8%，`ControlStore.set_cursor` 约 80.8%；线程监控插件的 Windows 线程枚举约 6.3%。这是活跃栈样本占比，不是准确的 CPU 时间占比，已经足以定位调用链，不能把这些数字直接写成全机 CPU 百分比。

## 三处问题与修改

### 1. 事件桥对普通事实逐条提交游标

`app/session_control/automation.py::_bridge_session` 每批最多读取 500 条运行时事实。没有产生控制事件的 token、trace、execution_recorded 等事实，原先每条都调用 `set_cursor`；每次又独立创建 SQLite 连接、开启事务、提交并关闭。

现改为只保留本批最后一个待写游标。遇到业务事件时，仍由原 `append_event(..., cursor=...)` 原子提交事件及游标；批末仅提交最后一段普通事实的游标。中间失败不会越过尚未持久化的业务事件，崩溃后普通事实可以安全重放。

同样的 500 条普通事实、独立新事实文件和新 SQLite 库：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 游标写入 | 500 | 1 |
| 数据库事务（含初始游标读取） | 501 | 2 |
| 墙钟 | 5,884.541 ms | 92.415 ms |
| 线程 CPU | 2,437.5 ms | 31.25 ms |
| 最终游标 | 500 | 500 |

这是隔离用例，不等同于整个应用的提速幅度。

### 2. 规则消费者在没有启用事件规则时也逐条处理

第一轮重启证明只修事件桥仍不够。`consume_events` 原先每个事件重新查询一次规则，再分别提交 rules 和 event_highwater 两个游标，即使没有任何事件规则也如此。

现在没有事件时不写游标；没有启用的事件规则时，一次读取后直接批量推进水位。有规则时保留逐条规则读取、权限判断与动作逻辑，但将本批水位合并提交。`ControlStore.set_cursors` 在同一事务写入两个水位；任务动作保留原稳定幂等键。回归实际验证了“动作已接受但水位提交失败”后重放不会重复创建任务。

同样的 200 个事件、没有事件规则、新 SQLite 库：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 数据库事务 | 602 | 4 |
| 墙钟 | 3,573.849 ms | 19.103 ms |
| 线程 CPU | 2,125 ms | 31.25 ms |
| 两个最终水位 | 200 / 200 | 200 / 200 |

### 3. 空队列也触发历史就绪检查

`app/session_control/service.py::adopt_followups` 每约两秒检查旧浏览器追问队列。原先为每个会话先执行 `followup_state`，之后才读取队列。回调经过 `_queued_followup_start_state → can_continue_react_session → has_unanswered_user`，可能完整重建历史 UI 索引。第二轮启动采样中该链约占 45.8% 活跃样本，日志同时出现大量未打开会话的 UI 重建。

现在先读取并筛选真正 queued 且 after_turn 的项目。无待发追问时跳过历史就绪检查；有待发项目时保持原状态、安全校验与单条幂等接纳。测试覆盖空队列、已发项目、非 after_turn 项不触发回调，以及 ready / recovering / paused 状态下的原有行为。

## 两轮部署及真实对照

两次均通过应用的 runtime_lifecycle 确认卡片，在用户逐次明确授权后重启，影响均为 0 个任务、0 个后台作业、0 个终端。第一轮只部署事件桥批处理，未把这轮仍然高占用的数据当作成功。

| 部署状态 | 启动后观察窗口 | 样本 | 平均单核百分比 | 按 8 逻辑核折算 | 窗口末后端 RSS |
|---|---|---:|---:|---:|---:|
| 只修事件桥 | 120.484–205.500 s | 18 | 95.573% | 11.947% | 3,946.2 MiB |
| 三处完整修复 | 120.188–205.219 s | 18 | 36.153% | 4.519% | 3,957.3 MiB |

这两个窗口长度、采样方式和“没有会话生成”的条件相近，观察到 CPU 下降约 62.2%。但不是严格控制的 A/B：重启前后历史桥游标继续推进，OS 文件缓存、索引预建状态和其他程序负载也在变化，因此不能把全部下降单独归因于某一处改动。隔离用例的事务数量减少则是确定的。

最终窗口 18 个健康接口观测均为 active_run_count=0。启动前约 80 秒仍存在高占用，峰值没有被修掉；最终 120–205 秒区间，进程树仍有 26.33–51.10% 单核占用。不能称为接近零开销的空闲。

后续 20 秒采样中热点已经分散：路径解析、历史桥的剩余处理/数据库事务、Goal 状态读取及 Windows 线程监控仍可见。后端 RSS 仍约 3.9 GB，没有取得内存改善，也没有完成堆分析去确认各缓存的实际占比。下一步应优先查这些周期性扫描的必要性、频率和缓存边界，避免继续以更多预加载来换取表面加载速度。

## 验证与产物

相关测试 94 项通过：第二轮主组 93 项通过，随后新增的动作幂等重放用例通过所在 11 项测试组（其中 10 项与主组重叠）。其中本轮新加 17 项，涵盖游标批边界、进程重建后续读、业务事件原子性、业务写入失败、尾部游标失败、代数变化 gap、无规则快速路径、空队列检查、就绪门控及任务接纳重放。Python 编译通过，生产改动仅限 automation.py、service.py、store.py 的相关小范围代码，保留共享工作区其他改动。

`.analysis/idle-cpu-20261026/` 保存：原实现副本、各轮进程采样、三份 speedscope 采样、调用栈、bridge-benchmark.json、consumer-benchmark.json、重启请求及诊断脚本。py-spy 仅安装在该诊断目录，没有修改生产依赖。

当前服务保持运行。没有测量实际风扇转速或温度，因此本报告确认的是额外后台工作与 CPU 改善，不能声称噪声或散热已被测量并修复。
