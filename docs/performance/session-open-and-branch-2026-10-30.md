# 会话打开与分支加载修复（2026-10-30）

## 本轮结论

恢复新加载会话的短滚动；把后台追问的目录/文件扫描移出 HTTP 事件循环；优化分支历史读取，并补齐创建、打开、超时和重试的反馈。

最终 178 项相关回归通过，前端构建与 dist 同步校验通过。真实会话冻结副本的三轮交替对照显示，后端分支创建中位数下降约 35%～38%。这不是线上点击到内容可用的完整耗时，也不是 P90 验收。

## 1. 新加载会话的动画与打开阻塞

原入口将所有新物化的会话统一设为 `bottom`，直接置底。现在使用 `entry-bottom`：在最新内容附近做 260 ms 过渡，距离最多 320 px，加载完成和流连接恢复不等待动画结束。缓存命中仍恢复阅读位置；运行中会话直接显示最新内容。

用户滚轮、触摸、指针、键盘操作，以及切换会话或开始生成都会停止过渡；减少动态效果的系统偏好会直接置底。单独的 `history.entryAnimation` 指标记录完整动画时间，避免将动画省略误报成数据加载变快。

`7cdb75ef-2f17-51d6-8a27-9ee6b5700bf2` 的故障记录显示：客户端 30,040 ms 超时，历史构建 2,273 ms、响应 1,314 字节，但服务端请求发送完成耗时 23,761.561 ms。这次故障发生在历史渲染前，不能归因于滚动动画。

现场非阻塞采样发现 `SessionControlService.adopt_followups` 在主 HTTP 事件循环逐个解析会话路径、读取追问队列。已将整段扫描移到工作线程，并在扫描后重新检查会话是否已进入运行状态。扫描完成后保留 2 秒间隔，避免慢扫描结束后立即再扫。

受控实验：114 个模拟会话、每个队列读取延迟 2 ms，三轮交替执行。扫描本身中位数 1,595.44 → 1,631.88 ms；事件循环最大心跳间隔的三轮中位数 1,595.63 → 21.82 ms。该修改降低对其他请求的阻塞，没有减少扫描工作量，也没有证明这一个热点解释了原故障的全部等待。

证据：`.analysis/session-open-20261029/incident.json`、`backend-live.speedscope.json`、`scan-results.json`。

## 2. 分支创建慢的具体修改

- 分支点校验与 UI 下标映射复用同一次可见历史读取，删除重复的原始日志查找、UI 读取及边界投影。仍校验目标为可见的最终回答。
- 模型分支检查点将来源识别、锚点之前的事实、之后针对历史的改写/删除合并为一次扫描。仅保留与锚点有关的内容和必要来源元数据，不保留无关未来执行记录或未来模型种子的完整消息。
- 保留递归来源检查、压缩上下文、嵌套分支局部改写/删除的语义。没有改为依赖祖先实时内容的引用分支，也没有省略原有同步提交。
- 前端使用最终回答的稳定 runtime seq，包括 `assistant_final_committed` 和导入的 UI 最终回答，避免只认旧事件类型而退回易过期的 UI 下标。

## 3. 等待反馈与防重复提交

点击分支后、确认弹窗之前即锁定同一来源会话的分支操作。确认创建后显示持续的状态条、旋转标记和已等待秒数，创建按钮禁用；创建完成后切换为“分支已创建，正在加载会话”。没有伪造百分比。

创建成功但打开失败时保留新会话 ID，按钮改为“打开分支”，重试打开已有结果。请求超时时显示“创建结果待确认”和“继续检查”，复用同一请求标识。等待中离开源会话不会在响应回来后强制跳走，已创建结果仍更新到会话列表。

前端合并同一锚点的在途请求；后端合并相同来源/请求标识的调用，客户端断开不会取消已开始的创建。相同标识但不同分支边界返回冲突，失败允许重试。

**防重范围**：后端是当前进程中最多 128 条、完成后 10 分钟有效的回执缓存；容量淘汰和服务重启后不提供持久幂等保证。前端待确认标识保存在当前页面内存中，不宣称刷新页面或重启后仍然恰好创建一次。

## 4. 实测结果与限制

使用已有真实会话的冻结副本，每轮启动独立子进程、复制到临时目录，不改原始会话，不调用模型。两个规模各做三轮 before/after，交替执行顺序。before 在子进程中恢复本轮修改前的三个方法，其余代码相同。测量期间不并行运行回归、构建或 profiler。

| 冻结事实日志 | 后端创建中位数 before → after | 降幅 | CPU 中位数 before → after |
| --- | --- | --- | --- |
| 4.77 MB，104 条模型消息 | 1,217.49 → 753.95 ms | 38.1% | 1,187.50 → 750.00 ms |
| 15.61 MB，647 条模型消息 | 4,409.64 → 2,870.34 ms | 34.9% | 4,265.62 → 2,812.50 ms |

中等样本 wall 范围：before 1,211.05～1,254.20 ms，after 743.41～1,067.12 ms。长样本：before 4,133.23～5,153.94 ms，after 2,768.78～2,907.01 ms。两种规模的完整可见 UI 投影调用均为 2 → 1；事件日志迭代调用（含源和目标）均为 7 → 4，不将迭代次数等同于物理磁盘读取次数。

12 次均校验了用户/最终回答文本、完整模型消息及源事实日志 SHA256。过程状态行存在原有的瞬时指标过滤，不用所有 UI 行逐字段相同来代表分支正确性；执行细节和历史语义由回归覆盖。

这些是新进程下的后端创建计时，操作系统文件缓存没有清空；不包含 HTTP 调度、插件回调、浏览器获取和正文渲染。三轮中位数不是线上分布的 P90，也不保证任意长度、任意并发和机器负载下同样快。

首轮只去重 UI 读取时，没有稳定加速，两种样本中位数反而变慢（约 16%、14%）。保留在 `first-pass-results.json`，没有将其算作成功；随后才加入模型检查点单次扫描。两轮环境负载不同，不横向比较它们的绝对耗时。

完整数据及脚本：`.analysis/branch-loading-20261030/benchmark-results.json`、`benchmark-summary.json`、`benchmark_branch.py`。
