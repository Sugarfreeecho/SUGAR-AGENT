# 生成期间的本机开销分析与局部优化

后续实施与前后对照见 [生成期间的前端优化与验证](generation-optimization-2026-10-26.md)。下文保留分析阶段的范围和结论。

2026-10-26。用户询问生成期间还有哪些优化空间。本轮检查了流式事件传递、持久化、前端执行记录和后台会话显示路径，使用已有日志与隔离浏览器测试，没有发送测试会话消息、调用测试模型或重启后端。

结论：仍有优化空间，尤其是多个会话同时生成时的重复渲染和长历史扫描。已完成统计栏节点复用，但这是一项局部减少重复工作的改动，不能据此声称整机 CPU、风扇或生成总时长下降某个百分比。

## 已完成

`renderProcessAggregateStats` 原来在每次执行记录更新后清空统计栏、创建两个 span，再追加到父节点。多数文本增量不会改变步数、工具数或缓存统计，却仍重复这些操作。现在复用两个 span，仅在文字变化时写 DOM；容器被清空后仍会正常重建。

`setUiRuntimeText` 原来每次调用都写相同的 `data-ui-runtime-text` 属性。现在只在属性不符合预期时写入，仍更新原始中文文本并按当前语言翻译。模型名称、Token 和缓存值继续排除翻译。

这些改动只涉及展示；没有修改上下文估算、压缩条件、消息顺序、持久化确认或流结束边界。

## 隔离实测

使用本机无头 Edge，加载修改前备份与实际修改后函数。两页各有 1,000 条历史占位节点；耗时测试不强制逐次布局，单次执行 10,000 次函数调用，交替前后版本顺序，共 10 轮，取中位数。DOM 工作量另用 MutationObserver 观察 1,000 次调用。没有连接实际运行页面。

| 统计刷新方式 | 修改前 DOM 变更 / 1,000 次 | 修改后 | 修改前耗时 / 10,000 次 | 修改后 |
|---|---:|---:|---:|---:|
| 所有值不变 | 3,000 | 0 | 24.60 ms | 2.50 ms |
| 仅数据栏变化 | 3,000 | 999 | 20.40 ms | 7.95 ms |
| 两栏均变化 | 3,000 | 1,999 | 21.75 ms | 16.50 ms |

两个 span 均保留。计数不包含已脱离观察树时发生的新节点初始化，因此不是全部节点分配量。上述耗时仅为统计栏函数的脚本执行时间，不包含完整页面绘制、事件处理或模型输出，也没有测出用户页面的 CPU 降幅。这处脚本自身的绝对成本较小，后续应优先处理下面的扫描和后台显示路径。

复现和原始数据：`.analysis/generation-20261026/benchmark_stats.py`、`stats-benchmark.json`，修改前源码备份在同目录。

## 已有生成日志提供的线索

扫描最近修改的 12 个日志文件，找到 693 条轮次汇总。最近 40 条汇总时间为 2026-10-26 11:59:04–12:02:22，来自当天上午，早于本次空闲 CPU 修复的两轮部署。不能将其当成修复后的生成基线；不同会话和运行也不是独立随机样本。

按 nearest-rank 计算，这 40 条汇总中，每轮记录的单次事件处理最大墙钟耗时 P90 为 **106 ms**、最大 146 ms；每轮最大排队时间 P90 为 **79 ms**、最大 164 ms。此前进度中给出的 111 / 96 ms 使用了另一种分位点索引，本文统一为 nearest-rank。处理墙钟包含线程调度、等待和工作线程执行；主事件循环的 thread CPU 数值不包含工作线程 CPU，不能直接换算成整个后端 CPU。

慢事件的嵌套 span 指向 `execution_dispatch → journal_record → journal_state / fact_append`，以及 `journal_lock_key`、`journal_cache_key` 等路径解析。嵌套耗时互相包含，不能相加或当作各路径独立占比。每轮累计处理时间分散在整段流式生成中，也不能全部加到首字延迟或轮次完成时间上。

原始提取结果：`.analysis/generation-20261026/log-summary.json`。这是定位线索，不是优化后验收数据。

## 后续优化的优先顺序

1. **长会话的逐条扫描。** `renderExecutionRecord` 每条执行更新调用 `selectExecutionProcessGroup`，后者通过 `findExecutionProcessGroup` 查询全部 `.process-aggregate`；工具更新还会通过 `attachHumanInteractionCardsForToolCall` 查询该会话的交互卡片和空槽。执行行已有 WeakMap 索引，但过程分组和关联卡片还没有同等的更新边界处理。可增加有失效机制的分组/卡片索引，或者仅在归属变化时重挂卡片。必须覆盖历史前插、合并、恢复、节点替换，避免重现新消息插入旧分组的问题。本轮未改动这些路径，也未量化其整页收益。
2. **后台会话显示降频。** `stashVisibleStreamForSession` 把运行中会话移入 offscreenRoot，仍保持 DOM 和 SSE 上下文。执行更新仍调用同一渲染函数，平滑文字队列也没有按当前会话跳过的分支。可以让后台会话继续更新权威记录，以较低频率更新 DOM、停止逐帧平滑显示；切回时从最新记录一次补齐。不能简单丢弃事件或断开 SSE，否则可能造成恢复缺口、审批丢失和内容顺序错误。
3. **流式持久化的路径和状态复用。** 文本在工作线程侧已有默认 12 ms 合并，StreamEventBridge 也合并兼容的排队增量；并非完全没有合并。但合并后的增量仍写 execution journal，每次都会进行锁键解析、源文件检查、追加和刷新。可先在单次提交中复用已验证路径和 stat，之后再测更大粒度的有界合并。必须维持完成、失败、审批、工具结果之前的提交顺序与断线恢复能力。
4. **可见页面的非关键 UI 合并。** 文本已有帧级增量写入，溢出测量也已有双 RAF 队列；不应重复增加任意延时。可针对仍重复运行的统计、关联查找和自动滚动做脏标记，每帧处理一次；最终状态与交互事件立即提交。收益应通过长历史和多个并发会话的实测判断。

此外，AgentRunPowerGuard 使用 Windows Power Request 防止运行期间系统休眠，当前代码没有切换系统为高性能电源计划，不能把风扇现象归因于该防休眠机制。
