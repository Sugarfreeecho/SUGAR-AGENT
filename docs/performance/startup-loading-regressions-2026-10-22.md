# 会话打开、列表刷新失败：审查与修复（2026-10-22）

验收以真实页面完成打开、列表可用、临时故障后恢复为准。缓存命中接口的耗时、局部 history.hydrate 耗时不能替代整页体验。

## 已确认的代码问题

1. **打开会话会同步写整个索引并使列表缓存失效。** `/unread-result/clear` 在 async HTTP handler 中直接调用同步的 SessionManager 方法；已读会话也重写 metadata 和 sessions.json，随后无条件清空 `/sessions/state` 缓存。忙时写盘和索引锁一起阻塞 HTTP 事件循环。后端采样确实捕获主线程停在 `clear_session_unread_result → _save_index → json.dump`。修复为线程池执行、重复清除不写盘，实际未读变化由 manager 通知缓存失效。保留失败结果和 run_id 校验。
2. **列表错误响应被当成成功空列表。** 状态接口失败后，旧列表兼容接口没有检查 HTTP 状态及数组结构。503 的错误对象会被转换为 `[]` 并覆盖列表。现在两层接口均校验，失败保留已有列表，初次失败显示重试入口，并按 1/2/4 秒有限恢复。
3. **并发刷新共享 Promise 被旧请求清掉。** A 正在加载，强制刷新开始 B，A 结束后把 B 的全局引用置空，C 因而重复请求并使 B 过期。现在只由拥有该 Promise 的请求清理引用。
4. **超时仅覆盖响应头。** `fetchWithTimeout()` 在 fetch 返回后就取消计时，后续 JSON body 读取可无限挂起。新增消费回调，列表、首次历史和刷新索引请求的 JSON 读取均放在同一超时/取消范围。
5. **再点一次当前会话会取消它的加载。** switchSession 在同 ID 的提前返回之前取消历史请求。现在提前返回不会取消正在进行的加载，失败会话再次点击会重试。
6. **首次历史预取失败会再次完整请求。** 之前捕获错误返回 null，普通 loader 又请求一次，可能连续等待两个 30 秒。现在预取与 loader 消费同一个结果或错误，JSON 读取也在期限内；仅 502/503/504 或网络失败重试一次，超时不重开昂贵投影，切换会取消退避。保留历史请求优先于辅助面板请求的顺序。
7. **工作区失败提示写到已移除的节点。** 目录加载在校验响应前移除了 loading 节点，catch 再写它，用户看到空白。现在校验成功才移除，失败提示与重试保留；刷新会取消旧树的请求，并设置请求期限。
8. **工作区路径解析在 HTTP 事件循环上运行。** 元数据读取和 Path.resolve/is_dir 移到线程池，保留原路径授权及错误处理。慢目录不应阻塞其他 HTTP coroutine。
9. **刷新按钮在即将销毁的页面多拉取/渲染一次列表。** 保留索引重建，成功后直接重载；由新页面获取权威列表。省去旧页面重复请求、重绘及最多 1.2 秒等待，不改变磁盘会话发现能力。
10. **会话模型读取和 steer 队列读取也包含同步 I/O/锁。** 它们随每次打开会话发起；模型元数据/配置文件读取、steer 全局锁等待移到线程池，避免辅助请求暂停整个 HTTP loop。用人为阻塞测试覆盖三个读取入口。
11. **索引重建反复探测历史文件并重新解码未变化的日志。** 实际 sessions 根目录有 888 项、581 个 UUID 目录。有效元数据已经足以排除“删除后的空残留”，此前仍先逐个探测可能的历史文件；现在先检查元数据，并去掉读 metadata 前重复的 exists。正常非会话目录不再逐项 warning/flush。日志活动时间按文件身份、大小、纳秒修改时间/创建时间缓存，日志变化即失效；读取失败的 mtime fallback 不缓存，目录/元数据仍每次重扫，保证复制、删除、改名的会话能被发现。

## 测量方法与局限

- Edge headless，未降速，同一个会话 `00367f02-1d42-4785-8b45-7eb71db40e3c`，95 条可见会话，首屏历史最多 200 事件。可用条件同时包含权威列表、完成历史加载、显示消息和可用输入框。
- 记录最差耗时及失败，不能只选最快一轮；前后机器负载没有固定，不能把不同进程/负载的差值当作严格净收益。
- 第一轮修复后的冷进程仍出现 36.024 秒首屏可用，说明仅重试、取消与错误处理没有解决主瓶颈。该结果保留在 `.analysis/startup-failure-20261022/cold-after/results.json`，随后才定位并修复未读清理的同步写盘与缓存失效。
- py-spy 采样存于同目录 `browser-backend-profile.txt`；采样存在落后，且包含多个线程，不把样本比例解释为 CPU 百分比。采样运行中的页面测试只用于定位，不纳入最终速度比较。
- 另一次线程监控 readiness 探针误读了返回值层级，把已经就绪的进程记作 pid=null；`restart-readiness.json` 不作为启动耗时依据。第二轮使用旧 PID 退出与新端口监听，记录于 `second-restart.json`。

## 回归验证

最终合并运行相关 11 个 Python 测试文件：**253 passed（45.98 秒）**；覆盖其中调用的 Node 与真实浏览器回归。另已通过前端源码/dist 一致性检查和修改文件的 diff 空白检查。

- HTTP 错误不清空列表、强制刷新竞态、body deadline、有限恢复、重复点击、历史短暂失败及取消退避：Node 运行时用真实函数验证；旧代码能复现前述问题。
- 人为阻塞工作区根目录检查/清除未读写盘时，其他 HTTP coroutine 仍可执行。
- 真实 DOM 中工作区 503 错误可见，点击重试可恢复；刷新会中止旧请求。
- 实际构建页面注入列表 503 和历史 503 后自行恢复；加载途中重复点击当前会话可完成；使用真实刷新按钮完成索引重建和整页重载。脚本不发送聊天消息、不启动模型任务。
- 未读清理的重复调用不写 metadata/index，不触发缓存失效；实际清除只通知一次；失败结果及 run_id 保护仍受回归覆盖。

索引优化前最后一轮新进程的 8 次整页加载均成功：首开 6.564 秒，中位数 3.741 秒，最快 1.767 秒，最慢 6.564 秒；列表中位数 1.532 秒、最慢 3.664 秒。仍有较大波动，不能据此宣称全面解决高负载延迟。记录在 `final-cold-verified/results.json`。

索引优化后真实刷新按钮连续三轮（含索引重建、重载、历史与列表可用）：3.782 / 2.271 / 2.417 秒；对应索引接口 2.752 / 1.190 / 1.243 秒。前面的两次完整刷新实测分别为 8.307 和 7.977 秒。后测中位数较 8.307 秒低约 71%，但这些并非固定负载 A/B，不能把整个差值都归功于代码。确定省掉的工作包括旧页面重复列表请求、无变化日志重解码、重复文件探测及无效目录逐条日志写入。

最终同会话 8 次整页读取均成功、无页面脚本错误；浏览器首开 1.215 秒，可用中位数 1.960 秒，最慢 2.962 秒；列表中位数 0.798 秒，最慢 2.074 秒。本轮修改前 3 次的对应值为首开 3.021 秒、可用中位数 2.402 秒、最慢 3.021 秒，列表中位数 1.769 秒。观测中位数变化为整页约 -18%、列表约 -55%；样本较少且负载未固定，最差整页耗时仅小幅下降，不能据此推导高并发 P95/P99，也不能保证不会再出现高负载长尾。此处“首开”是新浏览器对当前进程的第一次读取，并非空磁盘缓存的纯冷启动。

最终整页测量与故障恢复数据位于 `.analysis/startup-failure-20261022/final-measurements/results.json`、`browser-recovery-final.json`；源代码本轮差异存于同目录 `final-source.diff`。当前构建的源码与 dist 一致性检查通过。
