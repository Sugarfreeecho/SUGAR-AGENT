# 历史回放修复与 DSH 加载路径对照

日期：2026-10-22。DSH 源码位于 `D:/AI/AI Agent/Deepseek Harness/deepseek-harness`，读取时 HEAD 为 `477b4f420553e8a52c2fbccc464d7561b239c443`。本轮没有启动 DSH、运行其性能基准或修改其仓库，因此以下是源码机制比较，不能据此声称相同机器/负载下快多少倍。

## 本轮修复

- `history`、`history-older`、`history-target` 的 token 事件不再发布当前上下文读数；历史压缩文本仍可显示，旧的进度不会写入当前进度 store。
- `cache_stats` 仅更新所属请求的过程统计，不再把上一次 API 输入用量当作当前上下文总量。
- token store 具有会话级更新版本。迟到 GET、打开时的快照不能覆盖请求开始后的更新；清除缓存也会作废在途读取。缺失阈值保留当前阈值，构成只在总量和阈值相同的情况下沿用；stale 检查点不计为新鲜缓存。
- provider-prefix 路径只预热文本构造缓存。供应方用量仍留在会话级校准缓存，不再写入全局本地 tokenizer 结果缓存，避免另一个会话的 `local_estimate` 受到影响，也避免工具 token 混入本地纯文本计数。
- 历史按实际约 12ms 预算让出；不再因廉价事件达到 64 条或循环已经结束而额外等待。使用支持检测的 `scheduler.yield()`，兼容回退为复用的 MessageChannel，再回退定时器；SSE 复用同一调度入口。增加让出次数、等待和最长循环片段统计。
- 修复补载旧页后的执行记录排序：同一运行在不同页的局部 generation 可能不同，代次冲突时优先用持久执行序号比较；同一代次内继续保持推理、正文、工具的阶段顺序。缓存追加边界避免每个增量都扫描整棵树。
- 补充修复后台诊断的 GIL 争用：执行统计按请求拆分编码；Windows 线程枚举使用会释放 GIL 的系统查询，并在采样昂贵时降低采样频率。
- 补充优化侧栏启动：标题括号/省略号修饰只测量候选项，在首帧后合并执行；中文模式不扫描新增节点做无效翻译；关闭的会话菜单不再参与布局。

## ad986c48-3e85-4981-9e91-7394ae0fa6bf 的复现

从实际实例只读获取最近 200 条及更早 149 条投影事件，在隔离浏览器加载相同数据，没有重放工具命令，也没有发送用户消息或调用模型。

初始窗口仅出现当前运行，前端编号为 generation 0；补载的旧页包含三个运行，同一当前运行在该页编号为 generation 2。重建过程统计/排序缓存后，第 78 轮新输出被插到第 1 轮之前，在 174 行的分组中排在索引 2。

修复后使用相同操作，新输出落在索引 173，即该分组末尾；同一轮推理、正文、工具的顺序仍保留。增加真实 DOM 浏览器回归，覆盖混合页代次、迟到旧记录和阶段顺序。

实例的一次只读历史快照请求约 102ms，后端构建报告约 70ms，响应约 1.01MB。该样本是在该会话已停止、索引已有缓存时取得，不能作为冷启动或其他生成任务并行时的性能保证。

## DSH 为什么有更好的结构基础

| 路径 | DSH 源码机制 | 本仓库的主要差距/对应动作 |
| --- | --- | --- |
| 浏览与运行分离 | `packages/api/session-controller/src/history.ts` 的 page 不激活 Agent；follow 先 yield snapshot，再 promote 已准备的会话 | 避免为了显示历史先等待运行恢复、模型准备或大量摘要扫描；首屏与运行恢复必须各自可完成 |
| 带版本的热读取 | `packages/session-query/session-query/src/observation.ts` 按持久化服务身份、会话、revision 缓存 prepared Session，未变化时复用；有容量和 lease 生命周期 | 缓存应复用已验证投影，按真实数据版本失效，避免每个状态接口重新全量反序列化/复制；不是只添加一个 TTL |
| 分页与一致性边界 | history 默认 maxMessages=50，快照携带 cursor/projections，follow 校验后续序号连续 | 保持有界首屏；注意“消息数”和“事件数”不可直接比较。将首屏投影及实时接续放在同一版本边界，减少多接口竞争 |
| 增量对象层 | `ui-conversation/.../conversation/assembler.ts` 以稳定事件序号组织窗口，prepend 去重，只回放受影响 Context | 本仓库大量行为仍绑定 DOM 和共享全局变量。应先将历史投影、当前运行、统计拆成有所有者的状态，不必先全量改框架 |
| 局部订阅和稳定节点 | `ui-chat/.../ChatView.tsx`、`ChatNodeSeat.tsx`、`ChatGroupSeat.tsx` 用稳定 key、节点订阅和 memo；group-store 复用未变化引用 | 更新一条输出应只触及该记录、所属过程摘要及必要滚动，不重建菜单、会话列表或所有旧消息 |
| 按帧发布 | `api/session-controller/src/client/sessions/notifier.ts` 结构更新按微任务合并，流式更新最多每帧发布一次，输入可同步发布 | 减少每个 token 引起的 DOM、统计、翻译、插件事件与布局工作；先减少重复工作，再讨论在哪里 yield |
| 当前统计独立投影 | `ui-conversation/.../ContextMeter.tsx` 读取 contextPressure/contextBreakdown projection | 当前上下文读数不应由历史渲染器逐条“重演”；本轮已修复这一边界 |
| 有针对性的虚拟化 | `ui-trajectory/.../TrajectoryTable.tsx`、`ui-chat/.../TurnNavigator.tsx` 使用 virtualizer | 轨迹表和导航栏可只挂载可见项；本仓库目录/过程框也可按热点渐进采用 |

两个容易误解的地方：

1. 当前 DSH `ChatView` 的正文根列表仍对已加载 entries 做 map，折叠过程的 GroupMembers 也仍被挂载；不能说“整个聊天完全虚拟化，所以很快”。已确认的虚拟化证据属于轨迹表和导航栏。
2. DSH 的 cold observation 缓存未命中时仍会读取/准备日志；page 在这个观察上选取窗口。不能描述成“每次只从磁盘读取最后 50 条，完全没有长历史成本”。它主要避免同一版本被多个消费者重复准备，并把浏览与 Agent 激活分开。

## 后续有明显收益的重构边界

优先把现有消息投影抽为可复用的按序号增量对象层，DOM 只消费差量；当前上下文、运行状态、每次请求用量分别有独立所有者。运行实例的慢请求需继续按排队、索引锁、文件读取、投影/复制、序列化和浏览器渲染分段验证。全面迁移 React 或一次性虚拟化全部消息的风险和成本较高，不能用这些名称代替热点测量。

### 额外定位：后台诊断也在争用执行时间

对正在运行的进程做 12 秒、49Hz 的只读 `py-spy --gil` 采样，523 个有效样本中，98 个落在线程监控插件的 `psutil.Process.threads()`，95 个落在执行统计写入的 JSON 编码；这是持有 GIL 的采样分布，不是整机 CPU 占比，也不能解释所有慢请求。投影的索引锁为每会话一把，当前证据不支持“所有会话被一把全局索引锁串行化”。

执行统计的 flush 虽在后台线程，单次 C JSON 编码仍会长时间持有 GIL。补充修改 `execution_metrics.py`，按请求记录拆分编码，保持完整字段、Unicode、数值语义、请求顺序、会话 I/O 锁及原子替换。没有改成逐字段 Python 编码，也没有新增周期线程。

使用实际 9,226,728 字节、32 个 run、1317 个 request 的只读数据，在独立进程交替比较旧编码与实际新函数；每组预热一次、正式三次。旁路线程的最大采样间隔中位数约从 393.0 ms 降至 17.8 ms；写入总耗时约 439.5 / 435.9 ms，线程 CPU 中位数均为 406.2 ms。此实验测的是同进程兄弟线程可运行性，不是 HTTP 或页面响应承诺。指标持久化及兼容性 15 项测试通过。

线程监控也已修改：Windows 上使用 Toolhelp 线程快照及 GetThreadTimes，保留 OS 线程身份和 CPU 统计；查询失败回退 psutil，其他平台沿用 psutil；所有成功打开的句柄均在 finally 中关闭。采样周期按开销退让，快照返回实际目标周期。实现依据为 [Windows 线程枚举](https://learn.microsoft.com/en-us/windows/win32/toolhelp/traversing-the-thread-list)、[线程 CPU 时间](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadtimes) 与 [ctypes WinDLL 的 GIL 行为](https://docs.python.org/3/library/ctypes.html#ctypes.WinDLL)。

使用实际新函数、只读枚举 PID 5372 的 36 条线程：三次正式样本中，psutil / 新路径的总耗时中位数约 46.4 / 54.9 ms，旁路线程最大间隔约 62.3 / 16.6 ms。新路径并不保证采样本身更快，收益是允许其他 Python 线程穿插运行；退让频率用于约束持续开销。4 项专项及监控完整自检通过，覆盖真实线程 ID/CPU 计数、失败回退、句柄清理和退让行为。

## 侧栏长任务与后续前端优化

使用实际完整页面、4 倍浏览器 CPU 降速做 CPU 采样，`normalizeTruncatedSessionNames` 自耗时约 1881 ms，侧栏渲染路径约 2126 ms；国际化新增节点扫描也有约 700 ms 的路径耗时。`(program)` 还有较多时间，但该类别不能全部归因为 JS 编译，需进一步 trace 拆分。

原逻辑会先读取所有标题几何，再判断是否以括号结尾；这些读取强制侧栏及关闭菜单布局。现在先筛选、首帧后合并修饰，并让关闭菜单 `display:none`，打开时恢复布局和键盘焦点能力。中文模式下，新插入的原生中文 UI 不需要翻译；显式切换英文仍完整捕获原文，新增英文 UI 的翻译与还原中文有浏览器回归。

对照固定了实际 HTML、JS、CSS 产物，对同一实际会话交替启用修改前/后代码，4 倍 CPU 降速，每组一次预热、三次正式样本。初轮测试期间发生了另一次构建更新，结果保留作诊断，**不作为性能结论**；以下仅使用固定产物的后续测试。

| 正式样本中位数 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 首屏可用 | 10424 ms | 8478 ms |
| 侧栏可用 | 6764 ms | 5318 ms |

此组仍连接真实后端、存在异步控件，DOM 约 4540–4573 个，机器和服务负载没有被锁定。修改后单轮还出现 23553 ms（后端历史约 5744 ms）的波动，因此只能作为本轮前端修改的观察证据，不能作高负载 SLA 或把全部差值归给一个函数。菜单、语言、标题及主题等相关 **42 项**回归通过。

后续汇总补算：正式三次首屏为修改前 10424/8798/11107 ms、修改后 6961/8478/23553 ms，平均值从约 10109.7 增到 12997.3 ms（**增加 28.6%**），最慢一次增加 112.1%；侧栏平均 8200→9966 ms（增加 21.5%）。因此，本组的结论仅是中位数更快，**不支持整页整体或稳定性已经改善**。负载未锁定，也不能将平均值退化全部归因给前端改动。完整正反向统计见 [页面加载与缓存优化总账](loading-cache-audit-2026-10-22.md)。
