## 2. 已确认的步骤与尚缺的因果证据

1. **工具返回后有未覆盖的同步等待。** 第14→15轮11054.327ms，其中工具返回→模型事实提交10734.993ms；日志中read_file实际invoke为8ms，工具事实追加仅13ms。第24→25轮9176.818ms，其中返回→提交8319.005ms；invoke71ms、事实追加31ms。因此不能把整个空档写成“事件事实写盘用了10秒”。
2. **执行草稿和状态的逐条交付确有开销。** 慢事件日志中，tool_call交付51条，P50 322.443ms、最大1353.258ms；llm_reasoning_delta 464条，P50 177.967ms；tool_call_delta 197条，P50 235.821ms，最大排队1785.365ms。这些只统计达到慢日志阈值的记录，不代表全部事件的无偏分布，也不能将重叠span加总。
3. **发送前原有计时漏了一段。** 第2轮准备→调度4403.754ms，旧pre_api仅374ms。工具目录构建中的host加载、定义复制和fork runtime配置不在旧定义回调子段内。追加总包络与未归属部分之后才可定位具体函数，不能将旧pre_api当作准备阶段全量耗时。
4. **后台扫描存在确定的全局锁阻塞路径。** 原 `scan_stale_runs` 在心跳共用的 `_lock` 内执行全目录枚举、全部文件读取、live_checker及集中flush；`reconcile_orphaned_runs`也在同一锁内扫描。工具返回后的 `record_tool→heartbeat_run` 会争用此锁。这是源码与并发回归能证明的阻塞机制；**历史日志缺少扫描与锁等待时间，不能据此断言上述10.7/8.3秒全部由watchdog造成**。
5. **worker发送路径不是这批样本的主要长尾。** 55个配对中worker→HTTP send最大44.882ms；请求转换另有嵌套计时，不与该包络相加。该判断不涉及远端响应时长。
