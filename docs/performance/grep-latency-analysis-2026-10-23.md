## 1. 结论与统计范围

用户所说的“有时很快，有时很久”有运行证据。此前按近期中位数把 grep 排为低优先级，低估了长尾。本轮发现一个会意外扩大搜索范围的确定性参数缺陷，以及已隔离复现的管道等待问题。

本轮只分析和复现，**没有修改生产 grep 实现，也没有重启服务**。统计截止2026-10-23 02:20:27 +08；日志逐行按时间/session识别，并去除跨文件重复日志，不按日志文件名判断会话。宽口径指标来自顶层会话 `execution_metrics.json`，未完整递归统计子代理。历史窗口包含多个版本，不能当成最终同一版本的性能实验。

## 2. 已确认的缺陷：字符串过滤条件被拆成字符

`app/agent_tools.py:grep` 直接遍历 include/exclude，没有先把单个字符串规范化为一项列表：

```python
include_patterns = [str(x).strip() for x in (include or []) if str(x).strip()]
```

因此 `include="*.py"` 变成 `["*", ".", "p", "y"]`。传给rg的 `--glob '*'` 使本应只找Python文件的查询扩展到其他文件，并可覆盖原有隐藏/ignore过滤。exclude字符串也存在同类缺陷，可能错误排除结果。

### 真实证据

- 会话 `5ccddc7c-b3b8-437d-8704-7d8ba527ca2a`，run `bd72cce1-e463-48c2-b365-3087e1920e1f`，iter2：`include="*.md"`，根为仓库；invoke **16291ms**，事实 seq58 的结果却包含 `.analysis/after-restart-stack.txt`。过滤语义已经错误。
- 会话 `c5f7dc4e-7760-4b35-bbf0-28cf48c6dd5e`，run `a560b1c4-c38e-462d-96a1-46acb9953ba7`，iter7：两次查询分别 `include="*.py"` / `"*.js"`，超时，invoke约 **33954 / 30515ms**，事实 seq21697 /21699。
- 其他48小时超时样本包括962c7d78的两次、5e3b06a8的一次字符串过滤，以及9a002b3e的一次未提供include的舆情目录查询。参数缺陷不是六次超时的完整因果解释；本轮未固定旧版本逐条重放原任务。

### 当前实现的隔离复现

只创建5个很小的文本文件，不扫描生产目录：

| 入参 | 返回 |
| --- | --- |
| `include="*.py"` | keep.py、outside.txt、.hidden/hidden.txt、ignored/ignored.py、nested/node_modules/lib.js |
| `include=["*.py"]` | keep.py |

这证明缺陷和搜索范围扩大，不把小夹具87.569/57.498ms的时间差外推成真实30秒任务的收益。

## 3. 已确认的等待机制

### 3.1 stdout默认块缓冲，限制返回条数无法保证早停

当前rg的stdout连接PIPE，未添加 `--line-buffered`。本机rg帮助明确说明：非TTY输出默认块缓冲。即使已经命中所需条数，Python读端可能尚未收到结果，不能触发既有的“到上限立即终止”。

使用实际rg，立即送入一行命中、400ms后才关闭输入：默认缓冲首行 **411.710ms** 才到；加 `--line-buffered` 为 **49.132ms**。进程总时长都约400ms，因为生产者仍保持输入打开。该结果证明首条交付问题；只有达到结果上限即可结束的调用才会直接缩短工具完成时间。未达到上限的罕见/无命中搜索，仍需继续扫描。

### 3.2 stderr未并发读取，可形成管道互等

当前 `_grep_with_ripgrep` 先遍历stdout、等待退出，之后才读stderr。诊断信息填满stderr管道时，子进程写stderr被阻塞，读端又在等待stdout/EOF，直到定时器杀进程。

用原函数的AST副本替换成一个小型合成子进程：它先写256KiB诊断，再打印一条结果。临时1秒预算下，现有读法 **1016.237ms超时**；无阻塞stderr对照 **61.417ms返回**。对照丢弃stderr仅用于证明阻塞机理，正式方案必须保留有界诊断并发读取。没有证据证明历史六次超时全由该管道问题造成。

## 4. 搜索引擎切换与范围差异

- 目录搜索先尝试rg；显式文件搜索直接进入Python。微型文件的Python复现仅1.457ms，而rg进程启动级别约50ms，因此不宜把所有单文件查询强制改成子进程。
- 本机 bundled rg 14.1.0 **没有PCRE2**，`--pcre2-version` 已核对。look-around/反向引用等Python正则可能使rg退出，再静默进入Python；单加 `--engine auto` 无法补上缺失引擎。
- Python回退没有与rg共用的总超时；复杂Python正则可能在一次 `re.search` 中长时间运行，在线程外套异步超时不能终止它。隔离复现已确认lookbehind导致回退；提取的历史中只找到一条明显lookahead调用，约115ms，**未将其认定为本次主要慢例成因**。
- 两条路径文件范围不一致：夹具中的 `nested/node_modules/lib.js`，rg路径命中，Python路径不命中。当前rg默认的 `!node_modules/**` 等规则没有覆盖所有嵌套情况；Python回退还没有完整实现隐藏/ignore语义，lookbehind复现搜到了隐藏和ignored文件。

## 5. 工具外围等待需要单独治理

会话1952493b，run `react-recovery-c7bc9e0acd804c339fe9f1b3b89a53e3`，iter1：宽口径grep **92964ms**，对应invoke日志 **3306ms**，相差 **89658ms**。事实结果只有manager.py的三处函数命中。

同一运行附近有 `event_delivery / execution_dispatch` **43300ms**、`tool_pending`交付内dispatch **9897ms** 等记录。这些区间可能重叠，不能相加覆盖整个差额，也不足以将89658ms完整归因到一个叶子函数。可以确定：仅加速搜索引擎不能消除该宽口径等待。该样本为旧版本，近期6小时的宽口径已明显较短，不能说旧问题仍以同样程度存在。

本轮没有把这些时间归到上下文长度或API服务器响应。

## 6. 实施顺序（待实现）

| 阶段 | 修改 | 收益依据 / 验收 |
| --- | --- | --- |
| P0 | include/exclude统一规范化；字符串作为完整单项；错误类型明确失败 | 首先修正确定性范围错误；字符串/数组返回一致，覆盖隐藏与ignore夹具和真实慢例参数 |
| P0 | 增加逐调用grep分段：backend、fallback原因、线程排队、spawn、first-hit、读结果、stderr字节数、清理、截断/超时 | 用同一tool_call_id区分“尚未开始搜索”和“正在扫描”，避免继续用总耗时猜原因 |
| P1 | 并发持续消费有界stderr；stdout行缓冲；保留结果上限立即停止 | 消除已复现互等，缩短达到上限后的额外等待；错误仍可解释 |
| P1 | 统一rg/Python候选范围和所有深度的默认目录规则 | 保留用户显式搜索目标与授权；后端切换不能扩大/缩小范围；不静默排除用户数据目录 |
| P2 | 总预算覆盖搜索进程启动/扫描/收尾，并绑定取消；复杂Python正则放进可终止隔离进程，或核对PCRE2构建后使用兼容引擎 | 不留下无法取消的扫描线程；超时/部分结果必须标明未搜索完成，不能报告完整无命中 |
| P2 | 按新计时复核公共状态交付、授权/归属检查及worker排队 | 保留事实提交边界；先确认当前版本是否还存在旧的几十秒外围等待，再做对应减量 |

优先落地前三项：参数修正、分段计时、管道处理。它们有确定缺陷与隔离复现，收益依据比扩大线程池或缓存搜索全文更充分。普通小文件Python快路径保留；语义、ignore、二进制和Unicode差异核对后再决定哪些大文件迁移到rg。

### 验收要求

1. 字符串/数组过滤条件等价；显式排除、隐藏/ignore、嵌套目录、单文件与目录、Unicode和兼容正则有固定结果对照。
2. 先小夹具验证stderr不会阻塞、首条可及时到达、达到上限即停、取消后进程及时退出，再回放真实慢例；禁止用把超时调小替代搜索加速。
3. 正常范围查询以invoke P95低于500ms为目标；宽口径同时统计，保留少命中/无命中/大范围的独立分布。超过预算的结果明确标注未完成。
4. 不保证任意全盘搜索都能在500ms完整结束；不缓存可能过期的“无命中”，不绕过权限/来源/事实提交边界。
