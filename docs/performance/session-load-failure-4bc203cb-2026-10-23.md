## 第一版修复的真实验证及失败

先在无运行任务时备份衍生索引，将其 row_version 标为过期后重启；未修改 events.jsonl。

1. **01:34:12 的前台打开成功，导航至 load_end 为 7,966 ms。** 请求 `d9d65f59-8153-4e29-a745-84abd9dccba6`，后端 4,009 ms，前端历史 7,137 ms。但后台已先处理索引，前台 index=extended，因此这不是完整重建验收。
2. **01:37:45 的完整冷路径再次失败。** 请求 `7f3f21f6-048b-47cf-a623-7dd3c4a115dc`，前端 history 30,047 ms 超时，导航至失败约 33,208 ms。后端 37,228 ms 才完成，index_lock_wait_ms=35,104.565，前台自身读取 UI 行仅 46.745 ms。
3. 独立新增的后台日志记录：该会话 row_version 过期后重建耗时 **41,618.107 ms**，线程 CPU **4,250 ms**。这发生在前台请求之前。源码 `_warm_ui_caches` 的后台线程会读取最近 12 个会话的完整五轮历史，并在同一把每会话索引锁内重建。前台被这项推测性工作挡住，无法抢先服务。

这证明第一版只减少扫描还不足以修复实际失败。41.6 秒中线程 CPU 仅 4.25 秒，余下包含等待/调度，具体各阶段必须由新增阶段日志进一步分摊，不能全当作纯 Python CPU、磁盘等待或某一款系统软件的影响。

早期测试选择器没有匹配当前前端 DOM，独立日志与页面观察仍确认第一条实际成功；没有重复刷新后冒充原来的冷样本。第二条是真实产品超时，完整保留。

## 最终修复内容

- `app/runtime_v2/event_log.py`、`ui_projection.py`：仅 UI 投影重建跳过不消费的 execution_recorded 图片迁移扫描及投影分支，继续解析、校验每条事件，保留最后序号和事件边界。普通消息、模型、执行恢复读取保持原有兼容处理。
- `app/runtime_v2/event_log.py`、`ui_row_store.py`：日志读取和 UI 行写入按实际编码字节累计位置，去掉每行 tell()，缓冲改为有界的 256 KiB。完整历史不一次性放入内存。逐行 tell() 在 Windows 会涉及底层文件位置查询；结合重建墙钟远高于线程 CPU 的现象，减少系统调用/线程调度交接是针对性优化。未取得系统级 trace，不能将所有等待都归到 GIL 或磁盘。
- `app/webui.py`：取消启动时最近 12 个会话的历史页预加载，避免启动推测工作持有索引锁、额外读取历史载荷。技能和扩展目录的后台预热保留；历史按实际请求读取。
- `app/execution_services/jobs.py`：恢复终态作业时，若结果和通知状态未变，仅恢复内存，不为 boot_id 变化重复追加事实、触发快照和索引失效。运行中作业被中断、旧通知需要抑制的变化仍持久化。
- 日志：所有完整索引重建（含后台恢复/摘要调用）记录原因、墙钟与线程 CPU；另记录投影、元数据、源校验、UI 行写入、索引写入、内存发布阶段，不记录消息正文。

回归包含：隐藏事实仍必须通过 schema/payload 校验；普通读取仍执行图片迁移；可见内容和消息顺序不变；旧索引版本真正从磁盘重建并记录原因；启动目录预热不读取会话历史；终态作业恢复不写无变化事实；实际中断和通知变化仍提交。新增 19 项针对性回归全部通过，包含非零偏移、空行、半条尾记录、多字节文本、大于缓冲区的 UI 行、乱序寻址和损坏检测。核心相关 225 项、启动相关 72 项、执行恢复分组 43 项和执行服务 6 项通过；最终日志读取相关 100 项通过，最后 UI/启动/作业组其他 68 项通过，修正新增测试的文件包装器后索引组 11 项通过。这些分组有重叠，不应相加为独立测试数。Python 编译及改动空白检查通过。
