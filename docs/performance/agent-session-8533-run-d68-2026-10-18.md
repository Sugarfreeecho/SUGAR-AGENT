## 4. 实跑后实现：隔离阻塞LLM请求的共享线程池

### 4.1 先复现具体的排队机制

生产原来将整个阻塞LLM stream放进`asyncio.to_thread`，与本事件循环的短文件I/O共用默认线程池。独立进程中固定占用12个通用worker，确认全部进入后在320ms释放；这些worker只等待，不制造CPU或磁盘压力。保持生产astream、HTTP发送、真实工具和提交路径，仅比较提交位置：

| 私有顺序对照 | 3个请求提交→worker ms | 2个轮间最大 ms | 超标 |
|---|---|---:|---:|
| 原共享线程池 | 328.460 / 329.882 / 332.380 | 553.883 | 1/2 |
| 私有独立请求池原型 | 0.169 / 0.077 / 0.097 | 222.276 | 0/2 |

这个实验证明共享队列可以引入约330ms，并验证隔离能消除此机制；它不是实际d68中313ms来源的完整证明，也不能代替一般重载验收。原始[对照整理](../../.analysis/interround-500ms-implementation/5234-request-queue-comparison.json)保留。

### 4.2 新生产实现及边界

- 新`agent_request_executor`惰性创建一个进程级LLM stream池，容量沿用Python3.10默认池的`min(32, cpu_count+4)`，线程复用；仅承接原阻塞流worker，不移动事实提交、工具执行或权限判断。
- 与原`to_thread`一样复制ContextVar；排队取消不启动请求，已开始的worker仍依靠原stream abort事件停止，原异常原样返回。
- 原`worker_queue_ms`包络保留；新增安排→async派发、派发→提交线程池、提交→worker三个端点，区分事件循环/设置开销与实际executor队列。不记录payload或公开SSE字段。
- WebUI服务关闭时取消池内排队请求，正在执行的流沿用原终止路径；池关闭可重复调用，后续生命周期能新建。池仍有容量上限、操作系统仍负责调度，不是硬实时保证。

## 7. 最终所属事件循环修正（ca4cd3阶段）

最后审查发现`load_plugins`的陈旧快照后台刷新依赖当前running event loop；若把其门面调用一起移到普通worker，陈旧命中可能退为同步重扫。已在所属ReAct事件循环取得插件tuple，保留既有后台刷新调度，再把tuple交给线程中的同步host构建。`bundled_host_tool_definitions`接受已取得的tuple，此时不再在线程中重复加载；原调用方仍可不传。MCP异步生命周期保持原loop。
