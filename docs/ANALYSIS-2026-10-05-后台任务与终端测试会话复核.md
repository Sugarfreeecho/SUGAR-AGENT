## 证据与修正

### SIGINT：现象可信，根因推测和建议不够严谨

第二个终端 PID 25708 的命令输出为 `sig-begin 09:32:03` / `sig-end 09:32:48`，中间 `terminal_signal(SIGINT)` 在 09:32:18 返回 `delivered:true`。另一个 120 秒任务也在信号调用后打印了 `never-reached`。这能证明测试中没有达到中断效果，不能把 delivered 当中断已确认。

MyAgent [signal 实现](<D:/AI/AI Agent/MyAgent Developer/app/execution_services/terminals.py:424>) 只执行 backend.write("\x03")。DSH [Windows signalForeground](<D:/AI/AI Agent/Deepseek Harness/deepseek-harness/packages/subprocess/subprocess-local/src/terminal.ts:206>) 同样写 Ctrl-C。应该检查 backend、控制台输入模式、传递/确认机制，并验证“旧命令末行不出现、提示符恢复、shell 保留、下一条命令产生独立结果”。现有测试允许 inferred_idle、主要检查 job 状态及输出子串，未严格证明 Ctrl-C 终止了原命令。

不能直接认定改成 `GenerateConsoleCtrlEvent(CTRL_C_EVENT, pid)` 即可解决。微软文档要求调用方共享控制台，而且 CTRL_C_EVENT 不能限定到非零 process group；API 返回成功也不保证该组收到 Ctrl-C。[微软 API 文档](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent)

### pty-send：send 完成不能表示命令完成

45 秒任务的 job `8dd30a…` 在约 **4.58 秒**后 `status=completed, detail=inferred_idle, exit_code=null`，命令直到 09:32:48 才打印末行。120 秒任务 `7c1702…` 在约 **7.33 秒**后同样 settle。4 秒任务的 job 时间字段是约 **3.92 秒**，不是总结中的严格“3.2 秒”；其 job 文本未包含后来出现的 `bg-send-done`。

原因是 [_send 的静默边界](<D:/AI/AI Agent/MyAgent Developer/app/execution_services/terminals.py:300>) 和 [monitor 的 settle](<D:/AI/AI Agent/MyAgent Developer/app/execution_services/terminals.py:362>)：观察操作结束后 monitor 不再复制终端后续输出，真实终端读循环则继续保留输出。

DSH 的 [readiness](<D:/AI/AI Agent/Deepseek Harness/deepseek-harness/packages/terminal/terminal-bash/src/session.ts:580>) 与 [background job 映射](<D:/AI/AI Agent/Deepseek Harness/deepseek-harness/packages/terminal/tool-terminal/src/index.ts:272>) 有相同边界。因此应保留兼容的 waitReason，给模型/界面/通知增加完成范围，例如“send 观察结束，命令退出未知”，不能直接宣称命令成功。需要真实退出状态的一次性任务优先用 run_shell 后台 job；依赖终端状态的任务继续依据新提示符/业务输出确认。

### shell exited：存在明确的空读误关路径

第一个终端在提交 `Start-Sleep -Seconds 120` 的约 **1.48 秒**后，job 就以 `session_exit` 完成。最终 PID 不存在只能证明进程已消失，不能证明其自然退出；Windows 应用日志没有崩溃条目也不能排除主动清理。

本机 pywinpty 的 [_read_in_thread](<D:/AI/AI Agent/MyAgent Developer/python/Lib/site-packages/winpty/ptyprocess.py:353>) 把某些空读编码为 `0011Ignore`，[PtyProcess.read](<D:/AI/AI Agent/MyAgent Developer/python/Lib/site-packages/winpty/ptyprocess.py:198>) 将它还原为空字符串，此时 flag_eof 仍为 false。SugarAgent [_pump](<D:/AI/AI Agent/MyAgent Developer/app/execution_services/terminals.py:206>) 遇到空字符串直接 break，finally 写 `closed / shell exited` 并执行 `backend.close(True)`。

隔离复现结果（模拟字节输入和 backend，无真实进程被创建/关闭）：

```text
pywinpty_read_result: ''
flag_eof: false
session_status: closed
detail: shell exited
forced_close: true
was_alive_before_read: true
```

这证明适配缺陷及误导性 detail 存在，但原日志未记录当次 raw read/EOF/isalive/exitstatus，尚不能认定原会话恰好触发该 sentinel。后续修复应区分“无数据、真 EOF、进程退出、读取故障、主动关闭”，保留原因和退出状态；读故障需要清理时，也应报告 read_error/forced_cleanup，而不是自然退出。

### 测试状态字段也有误导

该会话显示 7 次 tool_failures，但包含预期 SIGTERM 拒绝、主动取消及文件读取诊断，不能等同于后台任务失败率。多个 job_output 的 result 内 `truncated:false`，UI status 却是 `truncated:true`。[_tool_result_status](<D:/AI/AI Agent/MyAgent Developer/app/agent_loop.py:4716>) 用文本中是否出现 truncated/timeout 推导状态；代码文件包含 timeout 字样也会被标为 timed_out。这类状态应优先使用结构化事实，避免把字段名或源码当运行事实。

## 建议顺序

1. 先修空读误关 shell，补“活进程空读→继续观察”的回归；增加退出/读取故障证据。
2. 收紧 SIGINT 回执为投递信息，建立中断效果确认；分别覆盖 PowerShell builtin 与外部子进程，不能只检查 job.killed 或命令回显子串。
3. 保持 DSH waitReason 协议，明确 pty-send 的完成范围和后续输出获取方式，避免 inferred_idle 发出命令成功通知。
4. 模型终端对齐 DSH 的安静环境配置；用户终端继续按交互体验选择环境。输出展示区分终端画面和按命令分段的文本。
5. 修正工具状态的文本启发式误判，并补重启、子进程树、权限与并发覆盖。
