## 4. 仍未解决的是什么

**不是**「该不该标红」的判断错，**而是**「页面内存里的失败态没有被后续成功/服务端成功覆盖」：

1. 失败态设计上具有粘性：
   - `frontend/src/app/modules/shared-state-and-dialogs.js:175` `markSessionResultComplete` 内，
     `normalizedStatus === 'success' && sess.unread_result_status === 'failed' && (!resultRunId || sess.unread_result_run_id === resultRunId)`
     → 会把 success **翻回 failed**。
   - `frontend/src/app/state/session-store.js:107-121` `recordConfirmedResult`：同一 run 的失败结果「粘住」，
     迟到的 success 不覆盖失败。
2. 快照合并对失败态只做「加」不做「减」：
   - `session-store.js:150-162` `reconcileSessionUnreadResult` 只在 `status === 'failed'` 时强制写回 failed；
     success 时直接返回原对象（不主动清除本地 failed）。
   - `session-store.js:84-95` `inheritUnreadResult`：当 `resolveSessionResult` 返回 `null` 时，
     **继承上一份本地状态**（含 `unread_result_status='failed'`），失败态因此可跨快照存活。
3. 快照可能整批被拒：
   - `session-store.js:63-77` `shouldAcceptSnapshot`：`pendingMetadataMutations.size > 0` 直接 `return false`；
     若某个 metadata mutation 的 token 未 commit / cancel，**之后所有快照都被丢弃**，页面状态冻结在失败那一刻。
     （此时轮询仍会照常发出并成功返回，与实测现象吻合。）
