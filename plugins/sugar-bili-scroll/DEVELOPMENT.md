## 1. 项目目标与已确认的边界

在 `plugins/sugar-bili-scroll/` 继续开发 SugarAgent 原生 `trusted_host` 插件。上游 `dsh-bili-scroll` 是移植来源；新增 UC 在 SugarAgent 版本落地。

| 范围 | 用户已明确的要求 |
| --- | --- |
| 基础值班 | 搜索视频、读字幕/评论、挑选与日报、全局判重、可选评论/私信/收藏；无字幕时按需调用转写 |
| UC1：表情库 | AI 从评论中收藏表情图到本地、自动打标签；页面管理；按标签搜索；自行选择表情码或图片发送 |
| UC2：入站互动 | 监听私信、@我、回复我；白名单可调用工具，陌生人只回复；禁止本机能力与泄露日报/他人私信；默认同人冷却 1 分钟、全站每小时 6 条 |
| UC2：即时回复 | 私聊按用户各建一条会话，保留记忆；新消息通过 append/steer 插入生成中的会话；最新要求的发送内容是会话“回复条目” |

## 3. 本轮已修复并回归的缺陷

| 问题 | 原行为 | 修复及验收 |
| --- | --- | --- |
| 自动调度自阻塞 | `_scheduler` 先设 `busy=True`，`scan_tasks` 再把它当作其他轮次忙，所有任务均被跳过 | 调度器将自身已占用的状态显式传给扫描器；其他调用仍遵守 busy；测试实际执行一轮调度 tick |
| 任务会话 ID 没落盘 | 修改 `row` 后保存重新读取的任务表，丢掉新 ID；下轮会再建会话 | 对新读任务表中的对应任务只更新 `session_id` 后保存；测试连续两轮复用同一会话 |
| 删光任务后默认任务复活 | 空任务表被当成未迁移，每次重新生成默认任务 | 以任务文件是否存在判定迁移；已存在的空表保持为空 |
| 无效任务 ID 跑错任务 | 找不到指定 ID 时退回第一条启用任务 | 精确查找；不存在返回错误，任务运行接口返回 404；没有启用任务也不创建临时任务开跑 |
| 停用任务仍可开跑 | 默认选择可能退回停用任务 | 未指定任务时只选启用任务；运行停用任务返回错误 |
| 迁移吞掉零值 | `daily_quota=0` 变为 3，`min_interval_minutes=0` 变为 45 | 只有缺键才采用默认值，保留显式 0 |

源码改动限于 `host.py`、`tasks.py`；新增 `tests/test_sugar_bili_scroll_tasks.py`，含上述行为及冷工具实例恢复存储的隔离回归。未修改真实任务配置、凭证、原会话事实日志或运行中宿主。

## 4. 尚未通过验收的关键项

### P0：UC2 权限与发送目标

1. `inbound_tick()` 计算了 `whitelisted`，但 dm/at/reply 都直接进入会话分支，权限没有按此分流。陌生人与白名单实际拿到同一组 B站工具；页面的“陌生人·只回话”与实现不符。
2. `inbound._event()` 把 `bvid/rpid/root` 放在 `event.target`，而 `_task_for_event()` 和 `_reply_prompt()` 读顶层 `bvid`，提示词也未附楼层 ID。真实轮询事件会丢失目标，现有自查的手造事件无法覆盖这个问题。
3. `run_dm()` 当前要求模型调用 `bili_send_message`，没有把会话回复条目作为即时私聊回复发送，且不满足陌生人无工具的要求。
4. 写工具可见性仍由全局值班设置控制，任务字段与入站回复上下文没有贯穿到目录和执行校验。需要分别验收查资料权限、发送目标限制和当前任务开关。

验收：用轮询器真实形状的事件驱动到发送适配器；白名单和陌生人分别验证目录与实际调用；回复只能落在原私聊对象/原评论楼层，不能由外部文本改变收件人；所有测试使用本地替身，不向真人发送。

### P1：UC3 每任务状态独立

1. `scan_tasks()` 的配额和间隔仍读全局 `duty-state.json`；A 任务的消耗会影响 B。
2. `build_prompt()`、`run_once()` 仍按全局目录读取配额、写报告与状态；`_snapshot_task_report()` 只是复制整份全局报告，不能表示该任务独立挑选结果。
3. `GET /tasks` 未返回每任务今日条数，页面也未展示；原会话“页面已含今日条数”的说法不成立。

验收：两任务不同额度/窗口/间隔，A 跑完后 B 的额度与计时不变；报告及归档按任务隔离，全局判重仍共享；页面今日计数来自对应任务事实。旧单任务数据迁移需要单独制定映射，不能把全局历史复制给每一条任务。

### P1：UC2 会话并发、记忆与回执

1. `run_dm()` 每次先 steer，再无条件起一个 agent loop；它没有区分正在运行和空闲会话。入站监听又在等待整轮结束，下一次轮询不能在生成期间持续递送新消息。
2. `_reply_lock` 只串行评论回复，未和同会话值班轮共享占用；任务会话的创建/更新也发生在锁之前。
3. `_RUN_TOOL_SCOPE` 以 `session_id` 存在全局字典中，并不是严格按 `run_id` 隔离。同会话重叠运行需要先解决所有权，不能仅凭函数名认定是可靠的运行级边界。
4. `_task_for_event()` 实际回退到第一条启用任务，没有建立视频到任务的可靠归属；评论回复复用值班会话，尚未清楚落实“值班任务”和“回复任务”的边界。
5. 私聊和评论路径会把“会话跑完/已提交”当作 `sent=True`，未确认发送动作；评论路径甚至不检查 `outcome.ok`。
6. `inbound.poll()` 在回复前就保存游标；模型或发送失败后事件可能不再重试。需要持久待处理项、明确的重试/放弃状态与防重复发送语义。

验收：同一用户连发消息只进入一个运行中的会话；不同用户记忆隔离；评论按任务顺序处理；失败、已提交、已发送、可见性未查到分别记录；重启后可恢复待处理事件。

### P2：UC1 与文档/维护

- 表情读取、收藏、标签、去重、检索和管理接口已有实现；仍需补齐“读评论 → 收藏打标签 → 搜索 → 选择发送”的组合验收，以及收图 6MB/发图 2MB、每轮图片限额的边界测试。
- `_runtime.pictures_round` 是模块内计数；工具模块重载/隔离实例下，不能仅凭它承诺稳定的每轮限额。
- README/INBOUND 仍同时保留数代设计。文档描述、UI 标记与当前实现需随 UC2 重构统一。
- `duty.log` 未轮转，上游差异清单已注明；作为维护优化处理。
